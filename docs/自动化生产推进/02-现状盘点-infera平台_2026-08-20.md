## 二、infera 已落地能力清单

### 二.1 11 阶段 SDD 交付图（R5-R9 落地，R12 前端，R13 修复）

运行图（`server/internal/engine/graph.go:43-70`）：

```text
intake → spec → spec_approval ─[small/'']→ test_gen → code_gen → unit_test → code_review → DONE
                      └[large]→ design → design_approval ─┬[拆分]→ 父跳过 tasks/tasks_approval/test_gen，停 code_gen 合并
                                                       └────→ tasks → tasks_approval → test_gen → …
```

- **复杂度分叉**：spec agent 末尾附 ` ```infera-complexity ` 块给建议，spec_approval 门呈现 `complexity_suggestion`、人工可改判（approve body 带 `complexity`）；老数据（`''`）按 small 走。
- **design / design_approval**：大需求产独立设计文档（架构/模块边界/接口/取舍）；拆分建议（` ```infera-split ` 块）与拆分编辑器从 spec 门迁至 design 门。
- **tasks / tasks_approval**：` ```infera-tasks ` 结构化清单（JSON），门页可编辑清单，approve body 可带 `tasks` 覆盖（`tasks_overridden` 事件）。
- **按任务逐条 code_gen**（R8/R9）：有 tasks artifact 的交付逐任务调用 agent（prompt 注入"当前任务 i/N"），每任务落 `task_done` artifact + 事件；**unit_test 失败回环只重跑剩余任务**（进度持久不丢）；无清单的老数据单次整体实现。
- **子需求上下文注入**（R9）：子需求跑 spec 时 prompt 注入父的 spec + design artifact 作背景约束。
- 数据模型：migration `0005_complexity`（`deliveries.complexity`）；任务进度由 artifacts 推导，不加列。
- 前端（R12，`3b0885e`）：阶段条按交付模式派生（small 7 段 / large 11 段 / 拆分父跳过段虚线圈）、三道新门页、任务进度卡。
- 依据 commit：`2176095`（R5-R7 引擎）、`637a577`（R8/R9）、`3b0885e`（R12）、`a868f70`（R13 补 design/tasks 可绑定）。

### 二.2 拆分交付：wave 并行 + 父级增量合并

- 大需求在 design 门批准拆分 → 子 Delivery 各自完整流水线（复杂度各自判定），按 **wave** 调度执行（`server/internal/engine/split.go`、`startDueWaves`）。
- 父 Delivery `split_mode`：跳过 tasks/tasks_approval/test_gen，停 code_gen 做子需求**增量合并**；冲突可暂停、人工修复后恢复（merge ledger 机制）。
- 前端：拆分计划编辑器、父子树、冲突横幅（`517b3f7` 等）。
- 依据 commit：`e193186` / `ff3b9c0` / `517b3f7`（0818 窗口前已有，0818 §2.1 已确认）；窗口内变化 = 拆分入口迁至 design 门（§二.1）。

### 二.3 Agent 编排：注册表 + 绑定 + 四类 runner（R1/R2）

- **Agent 注册表**（migration `0004_agent_bindings`）：`agents` 表（name / runner / config），前端 CRUD 管理页 + 删除引用检查（`ae2e627`）。
- **节点绑定**：全局默认 + 项目级覆盖（`项目覆盖 ?? 全局默认`）；可绑定节点 8 个：`spec / design / tasks / test_gen / code_gen / code_review / spec_conformance / code_quality`（`server/internal/orchestration/orchestration.go:19`）；基准必绑节点 6 个（design/tasks 可选，缺绑走引擎兜底 runner，旧默认绑定免重 PUT 升级，`a868f70`）。
- **runner 四类**（`orchestration.go:118-138`）：
  - `cli`：服务器子进程（`sh` 语义，`INFERA_ROLE/WORKDIR/PROMPT` 环境变量 + prompt 写 stdin，stdout+stderr 合并即产物，非零退出=阶段失败）；
  - `http`：`POST config.url {"role","prompt","workdir"}` → `{"output"}`；
  - `docker`：一次性容器，workdir 挂载 `/work`，prompt 作命令末参；
  - `local`：本机交互停车语义（`local_stage_pending` 事件，见 §二.6）。
- **保存时校验**（R2，`67b182a`）：绑定保存原子事务（单事务替换无半写）、runner config 预校验（保存时暴露而非交付期 blocked）、基准节点缺绑定 → 新交付立即 blocked 且事件写明缺哪个节点。
- 依据 commit：`f7012bc` / `c3d07f5` / `ae2e627`（R1）、`67b182a` / `f92be40`（R2）。

### 二.4 R10 双道审查：规格符合性 + 代码质量（只呈现不拦截）

- code_review 人工门前编排两道独立 agent 审查：**spec_conformance**（有任务清单时逐项核验，`task_based=true`）+ **code_quality**（质量维度）。
- **`infera-findings` 结构化契约**（已冻结）：`[{task_index, severity(critical|major|minor|info), message, evidence}]`，fenced block 协议家族（与 complexity/split/tasks 同源）；畸形输出容错为空意见，原始输出留档 `raw`。
- 报告存 artifact（kind=`<道名>_findings`，append-only 保留历史，最新生效）；两道**都产出**才挂人工门，缺绑定/失败 → `stage_failed` + blocked；某道绑 local → 跳过该道（人工即审查员）。
- **意见只呈现不拦截**：findings 不参与流转判定，批准/打回由人工决定。
- 门页：两道意见卡片（严重度分级 badge、任务关联 chip、证据引用）与真 diff 并列。
- 依据：`docs/superpowers/specs/2026-08-19-r10-dual-review.md`、commit `0f79b62` / `309d24c`。

### 二.5 MCP 服务：外部 agent 驾驶流水线（R3）

- `POST /mcp`（与 HTTP API 同进程），无状态 Streamable HTTP + JSON-RPC 2.0，手写协议层（仅 initialize/ping/tools 三类 method）。
- 鉴权：专用 Bearer token（`INFERA_MCP_TOKEN`，未设置=端点禁用 503）；常数时间比较；带 Origin 头的请求只接受 localhost。
- **五工具**：
  | 工具 | 作用 |
  |---|---|
  | `get_context` | 交付全量驾驶上下文（需求/当前阶段/门禁/产物全文/仓库与 workdir 信息/`pending_local` 角色 prompt） |
  | `get_gate` | 门禁详情（待审产物全文、AI 建议、PR 地址；code_review 门附真 diff 与双道意见） |
  | `approve_gate` | 批准门禁（引擎 Approve 单入口，选项按门校验 complexity/split/tasks） |
  | `reject_gate` | 打回（reason 注入回退阶段重跑 prompt） |
  | `submit_stage_output` | 本机绑定节点交回产出，按节点产物契约落盘后自动推进 |
- 门禁裁定与阶段交回全部走引擎单入口，与 HTTP 面共享同一把 per-delivery 锁（`a1a0fa2`）。
- 真实客户端冒烟通过（2026-08-19，claude CLI 全五工具 round-trip，含打回回环）。
- 依据：`docs/mcp.md`、commit `14e098b` / `293bce1`。

### 二.6 本机交互通道：infera-link helper（R4）

- 常驻用户本机的守护进程（Go 标准库、无第三方依赖）：网页「在本地处理此阶段」按钮 → `POST /handle` → 在交付 workdir 拉起带 MCP 配置与初始提示的 claude/codex 终端会话 → 交互在本机完成 → CLI 经 MCP `submit_stage_output` 交回 → 流水线自动推进。
- local 绑定节点从"停车占位"变为完整闭环；code_review 审查角色绑本机时门禁页同样可拉起本机预审（get_gate/approve/reject）。
- 每次拉起的 MCP 配置与初始提示落盘 `~/.infera/link/<id>/`（0600，可审计）；codex 以内联 `-c` 覆盖拉起（端到端只在 claude 验证过）。
- 已知环境限界：`--terminal auto` 的 osascript 开窗在无头沙箱被 AppleEvent 超时挡下（`--terminal none` 可绕过，其余链路一致）。
- 依据：`helper/README.md`（含 2026-08-19 端到端实录）、commit `2b5a0af` / `781986b`。

### 二.7 workdir 生命周期

- workdir 是一等资源：delivery 创建即 intake（绿地建目录 / 已有仓库 clone），全程共享各阶段，终态后**延迟清理**（默认 30min 留排查窗口）。
- **重启安全**（R13 加固）：workspace 注册表在内存，启动期 `Sweep` 清扫孤儿 workdir（`server/internal/workspace/workspace.go:142`）；重启前仍 active 的交付重新点火后台驱动（`server/cmd/infera/main.go:99`）；同 ID 窗口内 re-Acquire 有守卫（`a1a0fa2`）。
- workspace Acquire 为 per-delivery 锁（clone 不再持全局锁串行所有交付，`cb9035e`）。

## 五、有效差距清单（已有 / 部分 / 缺失 三档）

> 自本文起以此清单为准（替代 0818 §3 的口径）。"部分"项括注缺什么。

### 五.1 已有（可执行主路径）

1. 需求 → PR 交付内核全链：11 阶段 SDD、复杂度分叉、4 道人工门（spec/design/tasks/code_review）、逐任务实现、失败回环（≤3 次、只重跑剩余任务）。
2. 拆分交付：design 门拆分、子需求 wave 并行、父级增量合并、冲突暂停/恢复。
3. Agent 编排：注册表、默认/项目两级绑定、保存时校验、cli/http/docker runner + local 停车。
4. R10 双道结构化审查（呈现层，见五.2 第 3 条的边界）。
5. MCP 驾驶面（五工具，引擎单入口，真实客户端冒烟通过）。
6. 本机交互通道（infera-link：网页按钮 → 本机 CLI → MCP 交回，真实端到端通过）。
7. workdir 生命周期：一等资源、延迟清理、重启恢复、孤儿清扫。
8. 交付分支 commit/push + GitHub PR 尝试；时间线/产物/WS 事件（已鉴权）；项目/交付/门禁/编排/Agent 管理前端。

### 五.2 部分

1. **Agent 执行契约**：文本输出 + fenced block 家族已有；缺结构化 envelope（usage/evidence/版本/retryable）、schema 校验、预算、取消、能力声明。
2. **测试质量门**：回环机制已有；默认 `TEST_CMD=true` 假绿，无测试发现/多层测试/覆盖率门槛。
3. **Code Review**：结构化 findings + 双道已有；只呈现不拦截，无必修项闭环、增量复审、策略门。
4. **置信分流**：固定人工门 + AI 建议预填已有；无置信特征、风险分级、版本化放行策略。
5. **排期调度**：拆分 wave 已有；无跨需求依赖图、容量/预算约束、优先队列。
6. **持久化执行**：阶段记录、重启点火、workspace 清扫已有；无 durable workflow（租约/heartbeat/幂等 effect/补偿/配额）。
7. **认证治理**：密码 + session + 登录限流 + body 上限已有；无用户/角色/RBAC/审计。
8. **真实 agent 接入**：三种接口形态契约已定义并验证（http 形态线上真实验证）；三产品接入信息缺失，真跑未做；runner 层集成缺口 P2-P5 未修。

### 五.3 缺失

1. **执行前需求控制面（整段）**：Signal/Demand 聚合、来源连接器、清洗/分类、聚类去重、评估、产品上下文、优先级、成本估算——数据模型、API、执行图均为零。
2. **执行后发布反馈控制面（整段）**：Release 聚合、合并队列、CI/check 跟踪、验收、Changelog/发布物料、部署、灰度/健康/回滚、线上观测与反馈回流、复盘与知识沉淀——均为零（止于"PR 已尝试创建"）。
3. **无人值守自治**：自治白名单/黑名单、预算与并发额度、kill switch、运营治理——均为零。
4. **服务端主导 Agent**（见 §四.2 第 9 条）。
5. **横向底座**：policy engine、向量/检索、评测集与评测注册、成本观测——均为零。
