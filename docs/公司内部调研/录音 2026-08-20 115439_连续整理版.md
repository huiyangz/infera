## 一、讨论背景：怎样建设 AI 软件生产闭环

**访谈人：** 目前公司希望推动全自动的软件生产闭环。我昨天分别了解了 Bugfix 和 Code Review 团队的情况：Bugfix 团队主要负责收集 Issue、定位并修复问题；Code Review 产品则提供审查能力，作为闭环中的一个环节。InfoTest 未来可能也采用类似方式，在测试后生成报告并接入整个闭环。

现在相对缺失的是需求到研发这一段，例如需求如何发现、分析、拆分、设计和交付。还有一个设想，是主动追踪竞品与行业动态：针对上下文压缩、Memory 等重要方向设置关键词，持续抓取竞品的 GitHub 和其他信息源，整理成需求线索，再进入后续流程。

我希望了解你们目前如何处理这些事情，以及最终期待形成什么样的产品和流程。

## 二、神州项目的经验：效果取决于输入文档

**访谈人：** 之前为神州项目建设的自动开发链路，现在效果如何？

**受访人：** 那个项目针对特定行业的核心系统后端，输入不是普通需求描述，而是结构化、分层且字段完整的文档。它更接近设计规格或 Spec，所有必填信息都必须存在，否则流程无法继续。

客户最初提供了三个模块。其中一个模块的文档质量非常好，代码生成和测试效果也不错，最终只有少量测试错误，再迭代一段时间就能解决。另外两个模块的文档质量很差，无论怎样调整，生成效果都不理想。

这说明当前效果高度依赖输入质量。文档越接近结构清晰、信息完整的 Spec，后续生成越稳定。文档不规范，Agent 就很难补足缺失的业务和设计信息。

项目本身也有架构问题。例如，一个业务场景可能串联五十多个接口，而当时的实现方式是先自下而上完成单个接口，再组装完整场景，最后才发现接口之间对不上。这属于开发链路和架构设计问题，不完全是文档问题。

更大的瓶颈仍在前端输入。三个模块的文档总量大约已经达到几十万字，而一个完整核心系统可能包含上千个模块。业务人员通常写不出如此接近设计规格的文档。客户曾通过业务建模平台和 AI 辅助生成一部分文档，我们也考虑过让 AI 承接文档生成环节，但相关项目目前已经暂停。

## 三、为什么不直接设计一个大而全的闭环

**受访人：** 我们希望先在自己的研发中建立样板，但不认为一次性设计一个巨大的全流程系统可行。更现实的方式是从多个小场景切入，验证后再逐步拼装。

现在主要尝试两类场景：一类是 Bugfix，另一类是很小的产品需求，例如新增按钮、补充说明或修改文案。小需求由 Agent 完成通常没有太大问题，真正的障碍反而是团队流程和协作机制。

例如，研发可能认为一个需求很好，就直接开始 Coding，完成后再交给产品验收；但产品有自己的工作节奏，双方容易失去同步。技术上能做，不代表端到端流程就能顺畅运行。因此，现阶段会优先把 Bugfix 的端到端闭环做好，再继续向需求前端延伸。

## 四、当前设计到开发的尝试

产品和设计团队已经建立了一套 Design System，通过 Skill 和组件封装，明确哪些场景使用哪些组件以及组件如何组合。

当前流程大致是：

1. 设计人员使用 AI 生成一套 HTML 页面。
2. HTML 使用统一 Design System，尽量覆盖页面状态和交互效果。
3. 设计稿和简短需求说明一起交给研发。
4. 研发把这些材料交给 AI，还原前端并补充交互与业务逻辑。

这条链路在视觉还原上有一定效果，但仍存在明显问题。产品说明和 HTML 之间没有稳定的关联关系，很多逻辑通过口头传递。研发拿到材料后，需要重新理解产品意图，再决定前后端如何衔接，因此返工仍然很多。

另一个问题是缺乏全局业务视角。需求往往按单个页面或局部模块提供，不同页面和功能之间的关系没有系统表达，AI 很容易只完成局部还原，无法理解整个产品。

## 五、用页面反推结构化 PRD

为减少口头沟通，产品团队正在尝试同时提供两类材料：最终页面效果，以及结构化 PRD。

计划编写一个 Skill，根据已经生成的 HTML 反推 PRD。PRD 不再重复描述颜色、间距等视觉信息，而是重点记录：

- 页面与模块之间的业务联系；
- 每个按钮、反馈和状态的具体行为；
- 输入、输出和异常情况；
- 不同页面之间的跳转和上下游关系；
- 研发实现必须知道、但视觉稿无法表达的信息。

内部试验表明，这种方式能显著改善研发对需求的理解和页面还原质量。不过，目前缺少专人持续迭代，只能在每个项目和需求中一点点优化链路。

## 六、业务知识库与 DeepMap 的定位

单个 PRD 只能描述一次需求。要让 Agent 理解整个产品，还需要长期维护更大的业务知识库，保存业务背景、模块关系和历史变化。PRD 与业务知识库结合后，Agent 才可能持续理解新需求并保持实现一致性。

DeepMap 当前主要进行代码建模，但建模方向偏技术视角，尚未充分考虑最终使用者要消费什么信息。技术模型或业务模型本身并不等于可用，关键是它能否支撑具体场景。

长期希望把 DeepMap 建成一个知识和资产支撑引擎，至少汇总并关联以下信息：

1. 代码的技术结构；
2. 代码承载的业务逻辑；
3. 需求、PRD 和其他业务文档；
4. 代码及业务逻辑的负责人；
5. 每次变更修改了什么、由谁修改；
6. 需求、代码、测试和其他研发产物之间的关联关系。

因此，DeepMap 更接近研发资产管理和知识关联平台，而不仅是代码图谱。第一阶段最重要的是代码技术模型、业务逻辑模型、负责人和变更历史，并为未来其他类型数据预留扩展能力。

## 七、为什么必须从“建模”走向“可消费”

当前一些代码图谱生成了大量节点和关系，但用户难以浏览，根本原因不是信息不够，而是没有围绕消费场景突出重点。

更理想的流程是：新需求或新 Issue 进入后，系统利用已有知识理解背景，生成可执行的变更计划；再通过交互把计划拆成多个任务，交给不同 Agent 或人员处理；完成后更新代码、测试和知识资产。

这意味着 DeepMap 承担的平台责任很大，不可能一次完成。近期重点不应继续雕琢已有知识的展示细节，而应扩大信息覆盖，并用最小 MVP 跑通一条真实消费链路。只要知识能在实际开发中被使用，客户就会看到比“静态图谱”更大的价值。

## 八、需求分流 Agent 的内部设想

内部需求通常来自客户反馈，内容可能只有一句话。部分需求可以直接交给 Agent 完成，部分则需要产品判断优先级并设计方案。

曾设想建立一套每日分流机制：产品经理每天用约半小时处理需求工单，给需求打标并分流。

- 简单需求直接交给研发 Agent，研发确认任务后触发执行，第二天检查结果；
- 需要产品设计的需求进入 Design System 和 PRD 链路，再交给研发；
- 信息不足的需求继续补充背景或向反馈方追问。

但人工分流压力仍然很大。产品人员需要查看竞品、理解反馈原因并结合规划判断优先级。如果需求 Agent 已经掌握行业知识、竞品信息、当前产品状态和业务规划，它就可以先完成需求分析、竞品比较和方案草拟。产品人员只需消费分析结果、做少量调整，最终结果甚至可以直接形成 PRD。

难点依然是知识积累：行业背景、竞品情况、产品现状和业务优先级都必须持续更新，单靠一次 Prompt 无法解决。

## 九、标准化场景中的接入方式

内部产品可以围绕自己的系统定制知识和流程，但对外部企业，工作入口可能是 Jira 或其他工单平台，执行环境也可能不同。

标准化产品至少要提供连接器，能够接入客户的需求或工单系统，完成业务理解和任务分流，再把任务派发到客户实际使用的研发空间。执行结果、变更记录和知识资产还要沉淀回来，供后续二次使用。

因此，完整形态不只是一个 Coding Agent，而是“需求入口、知识理解、任务编排、执行、审核、测试和资产沉淀”的连续链路。

## 十、平台需要分层建设

双方认为，未来平台至少包含三层：

1. **基础资源与调度层**：管理算力、模型和基础资源调度。
2. **Agent 能力与编排层**：提供通用 Agent、工具、编排和可插拔机制。
3. **业务场景层**：围绕 SDLC 设计 Agent 调度、人机协作、权限控制、任务派发和结果消费方式。

当前产品更多在建设中间的能力层和部分业务支撑层。下一阶段平台侧需要从企业管理视角补齐成本、权限、安全和治理，并在平台上搭建基本 SDLC 链路，支持人员管控、工单派发及与 Jira 等系统对接。

不过，标准平台脱离具体业务知识就只能成为演示。真正有效的闭环必须与业务团队共建，把行业背景、流程机制和知识资产放进去。

## 十一、先做可落地样板，再谈完整自动化

完整的需求到交付闭环非常难落地，但 Bugfix 已经具备现实基础。当前 Bugfix 修复批入率约为 50%，已经能节省一半左右的人力；继续向 80% 提升，就会产生更明显的价值。

因此可以并行走几条路线：

- 把 Bugfix 做成稳定、可量化的落地场景；
- 在交付项目中针对具体行业建设端到端样板；
- 逐步完善 Agent 和平台能力，再将成功经验标准化为更完整的流程。

平台可以讲完整故事，但必须有几个真实节点能够明显节省人力。只有真实团队持续使用，完整闭环才不会停留在概念层面。

## 十二、PRD、代码与变更必须双向溯源

当前设计稿通常按完整页面交付，但产品知识体系和研发知识体系仍然隔离。未来增量开发的前提，是先建立原始产品和业务模型，然后才能表达每次需求修改了什么。

一种设想是把 PRD 和相关产物放入 Git 仓库，通过版本记录分析每次变更，识别谁修改了什么，并把变更关联到任务、代码和负责人。

客户对此有明确需求：

- 从需求可以找到对应代码；
- 从代码可以追溯原始需求；
- 新项目出现类似功能时，可以找到并复用历史实现；
- Bug 出现后，可以追溯到引入它的需求和变更。

这类增量追踪是多个客户共同提出的问题，也是 DeepMap 和知识资产平台应重点解决的能力。

## 十三、内部闭环应先选协作成本低的团队

公司级闭环比单团队闭环更难，最大的障碍之一是人员和部门工作方式差异。产品、设计、研发和测试各自有不同节奏，强行统一流程容易影响项目进度。

更适合的办法是先选择人员结构简单、端到端职责集中的团队建立样板。先形成使用习惯和共同认知，不急于立即发布一个大平台。等链路在小团队跑顺，再逐步扩展到其他部门和客户。

当前内部项目进度较紧，暂时不适合强推全项目改造。可以等当前项目阶段结束，再以增量方式试验 PRD、知识关联和 Agent 分流。

## 十四、竞品研究不容易完全自动化

主动发现需求是另一个重要话题。对于已经明确的问题，可以定向研究几个竞品；但当产品处于创新阶段、方向尚未定型时，竞品研究通常是广泛收集文章、开源项目和行业信息，再由产品人员亲自试用和判断。

推荐系统和 AI 摘要可以帮助发现信息，但很难替代产品人员的体验。界面截图或视频只能反映表层交互，无法说明代码索引、语言服务等底层技术能力。产品和技术人员仍需要分别从用户体验和技术实现角度判断价值。

因此，竞品扫描可以辅助，但暂时难以形成一条完全标准化、自动执行的流程。产品判断中包含大量经验、手感和隐性知识，这部分仍需要人负责。

## 十五、产品闭环与公司流程闭环的区别

访谈人更关注把现有产品串成一个可以向客户展示的闭环；另一项公司级目标则是打通内部实际生产流程，不限定使用哪款产品。

两者可以互相促进，但目标不同：

- 产品闭环用于展示和销售，强调各产品能力如何协同；
- 内部流程闭环用于真实提效，强调人员、流程和业务知识如何运转。

目前市场上还没有真正成熟、顺畅的全自动产品形态。如果内部能先建立一个真实样板，团队就能明确人在什么环节介入、产品承担什么职责、成本和效果如何，这也会反过来指导产品发展。

## 十六、运营与小企业样板探索

会议最后讨论了两项配套安排。

第一，计划由一位偏运营的同学负责官网和用户侧产品迭代、反馈链路及运营体系建设。他将与 FDE 团队保持更多沟通，把目前依赖人工解析和跟进的反馈流程进一步自动化，并协调内容素材、活动和用户运营。

第二，可以探索小企业或小团队场景。大型客户需求广、周期长，很难快速验证新方案；小企业虽然系统规模较小，但供应链、客服或其他局部业务场景与大企业可能相似，更容易快速完成 PoC 和样板间。

这项探索不以短期收入或签约数量为目标，而是希望更快获得行业认知和真实案例。可以通过小型沙龙、分享会等方式接触团队，找到合适场景，快速验证业务逻辑。成熟样板随后可以用于增强大型客户的信任。

## 十七、结论与后续动作

会议形成的核心判断是：AI SDLC 技术上具备可行性，但真正瓶颈是高质量输入、业务知识资产、跨角色协作和可消费的平台设计。

后续重点包括：

1. 继续提升 Bugfix 修复批入率，将约 50% 的现状向 80% 推进。
2. 用小需求和具体交付项目验证需求到开发链路，不一次性改造全流程。
3. 继续完善 Design System、HTML 反推 PRD 和详细交互逻辑描述。
4. 规划 DeepMap 的知识资产模型，优先关联代码、业务逻辑、负责人和变更历史。
5. 建立需求、PRD、代码、测试和变更之间的双向溯源。
6. 探索需求分流 Agent，但保留产品人员对优先级和方案的最终判断。
7. 平台侧逐步补齐 Agent 编排、企业治理、权限、安全、成本和外部系统连接器。
8. 选择协作成本较低的内部团队先建立端到端样板。
9. 将真实落地效果与产品闭环演示结合，形成可复用的客户案例。
10. 通过运营、小型活动和小企业 PoC 获取更快的市场反馈与行业认知。
