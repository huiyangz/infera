## §1 小鱼儿 Bugfix Agent 现状

### §1.1 定位与范围边界

1. 当前只做 Bugfix，不做需求开发。理由（发言人 A 陈述）：Bugfix 的输入通常比较明确——问题表现、运行环境、需要收集的信息，因此前置流程相对容易搭建；需求场景复杂得多——产品提出需求后还要做调研，形成产品方案、UI 方案和技术方案才能进入开发，参与人员与前置步骤都更多。（来源：〔163757〕§五）
2. 切入点优先是"线上运维中出现的问题"；Bugfix 闭环跑通以后，再探索需求开发流程。（来源：〔163757〕§五）
3. 发言人 B 的评价性陈述（照实记录）：向前或向后扩展都比较复杂，把每个环节真正串起来很难，"全自动"本身不容易落地；流程表面通用，落到细节会与项目和团队工作方式深度绑定；通用平台还需解决系统如何自动理解团队特点、部署适配流程、为每个环节配置特定 Skill。（来源：〔163757〕§五）

### §1.2 Agent 组织与流程形态

1. Agent 数量约 3 个：发言人 B 转述"你刚才提到有三个 Agent"（指本次录音未覆盖的会议前半段内容）；三个 Agent 之间如何协作、是否有负责调度的 Agent，发言人 A 表示"这个细节我再向相关同学确认"。**该数字与协作机制均属待确认。**（来源：〔163757〕§一）
2. 职责拆分与 Skill 配置：改进方向之一是"把职责拆得更清楚，并为不同职责配置不同的 Skill"。（来源：〔163757〕§一）
3. 流程形态已从固定 Workflow 迁移到 AI 自主决策：原来采用固定 Workflow 编排，现在改为由 AI 根据问题和上下文自主决定下一步动作，以减少固定流程对真实问题处理的限制。（来源：〔163757〕§一；录音补充背景亦确认"将固定流程编排改为 AI 自主驱动"）
4. 理想使用形态：用户直接私聊机器人把信息丢给它，或新建话题群 / 在当前话题群里把材料交给它，机器人拿到材料后自动开始分析；"这和我们现在内部使用的方式差不多"。（来源：〔163757〕§三）

### §1.3 上下文接入现状

1. 历史缺口：之前系统没有打通用户上传的日志和 Langfuse 日志，导致 Agent 能获取的信息不足，因此近期持续补齐相关信息。（来源：〔163757〕§一）
2. 本期已接入：部分内部测试日志、测试效果对应的 Trace（Langfuse）、话题群中的附件。（来源：〔163757〕§一）
3. 尚未接入：视频内容、客户端日志。客户端日志未接入导致有些问题只能停留在现象分析阶段，进一步定位需要客户端日志辅助。（来源：〔163757〕§一）

### §1.4 验证与证据能力

1. 问题解决后，系统可以运行 E2E 测试进行验证，并自动截图留证，使修复结果不只停留在代码修改层面，具备基本的闭环验证能力。（来源：〔163757〕§三；录音补充背景同述）
2. E2E 验证之外，配套的自动化测试资产建设现状见 §1.9。

### §1.5 效果指标

1. 当前修复批入率约 50%，目标提升到 80%；这是当前试验的核心目标，也是现阶段投入最多精力的方向。（来源：〔163757〕录音补充背景、§一、§四）
2. 人力换算口径（发言人 A 陈述）：如果 Agent 能处理 50%，至少节省一半人力；做到 80%，则只需约 20% 人力处理复杂或异常问题。（来源：〔163757〕§六）

### §1.6 去重、分类与需求资产现状

1. 去重："我记得有一定的去重能力，系统会根据 Bug 信息拉取相关的历史 Bug，不过具体机制还需要再确认。"**机制待确认。**（来源：〔163757〕§二）
2. Issue 分类：目前还没有正式的分类体系，只能做简单判断（看起来像界面问题、逻辑问题或效果问题）；发言人 B 提议的分类维度（要不要修 / 界面 / 逻辑 / 作业状态 / 效果）未被采纳为现状。（来源：〔163757〕§二）
3. 需求资产整理：对"一个 Issue 延伸出新需求是否整理归类"——"这件事有必要做，但目前还没有完成"，原因是还没有规范化整理需求资产，直接把所有历史需求交给 Agent 可能带来很多干扰信息。（来源：〔163757〕§二）

### §1.7 已知失败案例与决策缺口

1. 失败案例：真正的问题出在后端，但系统分析完问题后没有进行"是否应该修复"的必要判断，就直接生成修复报告并开始动手。该案例被归因于过去固定编排留下的惯性；即使流程已转向 AI 自主驱动，仍需明确增加"是否应该修复"的决策能力和必要的人工介入点。（来源：〔163757〕§三）
2. 介入边界的形成方式（发言人 A 陈述）：很难一次性把边界定义清楚，这类判断依赖经验；更现实的方式是先让整套流程跑起来，定期复盘它处理过的问题（哪些应该解决、哪些不应该），再逐步把经验沉淀到规则、Style 或 Prompt 中。（来源：〔163757〕§三）

### §1.8 人工角色参与

1. 现状：流程中有多类角色参与（测试、产品、研发等）。（来源：〔163757〕§四）
2. 未来的两种设想：① 值班机制，或给 AI 一份"找人地图"让它自动找到对应负责人；② 测试人员在流程前面直接指定问题负责人，由该负责人评估修复方案是否正确，并在代码提交或合并时做最后检查。（来源：〔163757〕§四）
3. 走向上述模式的前提：修复批入率和整体解决效果从约 50% 提升到 80%。（来源：〔163757〕§四）

### §1.9 配套自动化测试建设

1. 现状：由一位实习同学负责。第一项工作是把从早期版本到现在所有需求中的冒烟用例和回归用例，转成集成测试或端到端自动化测试；第二项工作（如何随版本迭代持续补充）还在设计中。（来源：〔163757〕§八）
2. 定位：自动化测试是整个 AI 闭环中的验证环节；当前发布速度慢的主要原因之一是测试不够准确或验证成本过高；现阶段先建传统自动化，后续希望 AI 参与测试用例生成和维护。（来源：〔163757〕§八）
3. 第一版验收目标：上一个版本在代码合并后暴露的问题，新的自动化测试必须能够测出来。（来源：〔163757〕§九）
4. 上版本典型问题：Sub-agent 与 Worktree 相关的两个需求由不同同学并行开发，单独开发时都没暴露问题，合并代码后才发现相互影响，导致回归验证被动。期望的改进：在合并代码阶段由 AI 判断多个需求之间是否关联，有关联则自动补充测试用例并执行自动验证（第一类场景）；覆盖人工难以验证的边缘环境——Windows、macOS、Linux 及统信等国产系统（第二类场景）。（来源：〔163757〕§八）
5. AI 生成测试用例的难点（发言人 B 陈述）：常规 / 正向用例问题不大；困难的是边界条件和代码分支——如果用例只根据需求文档生成而 AI 看不到代码和分支，容易漏掉场景；需求变化时用例必须同步更新，涉及长期维护。（来源：〔163757〕§九）
6. 曾考虑直接使用 InfTest（转写稿原记作"InfoTest（名称待确认）"，经确认为 InfTest），但它强依赖需求文档、接入流程可能较长，因此目前先自行补齐基础能力；未来还计划通过这些测试分析需求影响链。（来源：〔163757〕§九）

### §1.10 所在团队研发流程现状

1. 日常开发流程基本传统：产品提出需求 → 需求评审 → 设计 → 设计评审 → 开发；除了最后的 Code Review 使用了机器人，前面流程仍为传统方式。（来源：〔163757〕§七）
2. 产品和设计环节近期有 AI 改进：设计同学可以直接提供 HTML 再进入后续开发；研发阶段整体仍比较传统，主要由个人完成开发和提交。（来源：〔163757〕§七）

### §1.11 推广与平台化口径

1. 推广路径（发言人 B 陈述）：先在当前团队验证，试验成功后逐步推广到其他团队（例如 UTest，名称待确认）；如果有三个团队都能跑通，就可以开始沉淀相对通用的能力。（来源：〔163757〕§五）
2. 协同与平台化：多个团队在做类似事情，需要考虑怎么协同（发言人 B）；小鱼儿团队表示不排斥共同参与（发言人 A）；双方均认为平台团队承接通用能力更合适，业务团队探索最终可能纳入平台整体建设，当前安排人做首先是为解决现场人力接不过来的实际问题。（来源：〔163757〕§六）

## §2 infReview（AI Code Review）现状

### §2.1 能力构成

1. 当前审查主要依靠 AI：AI 探索仓库、分析代码、发现潜在问题，把问题写入审查报告。（来源：〔185618〕§二）
2. 传统静态扫描没有作为主能力接入，但存在独立的漏洞扫描工具。（来源：〔185618〕§二）

### §2.2 问题分级与合并阻塞

1. 审查结果会分类：高优先级或严重问题需要修改后才能合并；其他问题可能只是建议。（来源：〔185618〕§二）
2. 严重程度大致按 Critical、Major 等级划分，具体规则仍在持续调整。（来源：〔185618〕§二）

### §2.3 多轮 Review 与历史

1. 支持多轮 Review：开发者修改代码并再次提交后，下一轮审查会带上上一轮报告和历史问题，同时重新检查整个仓库及本轮增量；新报告会说明哪些旧问题已修复、哪些仍存在、本次是否引入新问题。（来源：〔185618〕§九）

### §2.4 人工介入边界

1. 审查过程本身希望尽量自动化，系统内部一般不增加固定人工节点；最终是否修改、是否合并由使用团队决定。（来源：〔185618〕§九）

### §2.5 可配置性（规则 / Skill / MCP）

1. 系统支持用户配置部分审查规则和开关，也允许用户挂载自己的 Skill，覆盖或补充默认规则；整体可理解为"一个审查 Agent 配置若干工具和 Skill，共同决定审查方式"。（来源：〔185618〕§七）
2. MCP：Agent 已有一些代码工具但能力还比较粗；后续可以考虑提供 MCP 接口与其他产品或平台能力联动。当前很多配置仍放在产品内部由产品页面控制；长期看 Skill 和 MCP 都会成为扩展审查能力的重要方式，但目前还没有形成明确、统一的需求方案。（来源：〔185618〕§八）

### §2.6 自动修复现状与计划

1. 现状：系统不会自动修复报告中的所有问题，仍需研发人员阅读报告并自行处理。（来源：〔185618〕§二）
2. 下一版本计划：继续建设自动修复入口；自动修复不是在 Review 中给出一小段 Patch 建议，而是一个更完整的项目级修复过程，需要更强的上下文和服务能力。（来源：〔185618〕§二、§七）
3. 产品侧未来可提供更正式的自动修复入口，但具体产品设计还没有完成。（来源：〔185618〕§三）

### §2.7 与小鱼儿 Bugfix 机器人的接入现状

1. 对方（小鱼儿团队）的 Bugfix 机器人已经能读取 infReview 的审查结果；Bug 修复后把代码交给 infReview 做 Code Review，目前处于内部测试阶段。（来源：〔185618〕§一）
2. 接入方式：小鱼儿团队没有通过 infReview 的业务系统接口读取报告，而是直接从代码托管平台读取——因为 infReview 的报告本来就会回写到代码托管平台；GitHub 场景类似，通过原生接口或 `gh` 命令即可取得必要信息，不需要额外一套集成 API。上周对方原本想找 infReview 开接口，后来发现可直接读取，因此先自行接入。（来源：〔185618〕§三、§四）
3. 修复完成后的代码不会自动合并，仍然需要人工做最后检查。（来源：〔185618〕§三）
4. 闭环定位：小鱼儿团队是当前最明确、最迫切的需求方（已有真实客户反馈和 Bugfix 机器人），会率先把链路跑起来；infReview 的代码审查既可以作为闭环中的一环，也可以独立使用。（来源：〔185618〕§四）

### §2.8 通用性

1. 原则上可适用于任意仓库：只要系统能访问目标仓库，并把问题分配给有权限的负责人，Agent 就可以拉取代码、分析问题并尝试修复。（来源：〔185618〕§四）
2. 小鱼儿团队的方案更贴近自己的业务场景；infReview 更偏通用能力；双方目前还没有系统地对齐整体方案。（来源：〔185618〕§四）

### §2.9 上下文边界（无需求文档）

1. 需求文档目前没有进入审查上下文，主要原因是系统没有稳定入口来收集需求文档；现在只能根据仓库和本次代码变更推断开发意图，理解程度依赖代码本身提供的信息。（来源：〔185618〕§五）
2. 如果未来能稳定获取需求文档，可以加入审查上下文用于检查实现与需求是否一致；这被列为产品链路向前延伸时需要补齐的一环。（来源：〔185618〕§五）

### §2.10 质量目标与已知弱点

1. 近期最主要的工作：提升审查准确率、召回率、稳定性和成本表现。AI 审查可能一次产生大量问题，准确率不够时用户面对成千上万条结果无法使用；因此结果数量不是越多越好，必须控制噪声并提高有效问题比例。（来源：〔185618〕§七）
2. 对"不改"评论的理解弱：开发者回复"这是故意这样写的，暂时不改"时，用户反馈会被记录，但如何可靠地把自然语言解释转成后续审查约束还没有完全想清楚；用户不一定认真回复、回复方式不统一，反馈闭环仍需继续设计。只有用户真正持续使用，系统才能收集足够反馈判断哪些规则有效、哪些误报需要调整。（来源：〔185618〕§九）

### §2.11 评分与外包验收场景

1. 有给审查结果总分的产品计划。（来源：〔185618〕§十二）
2. 现状：已有客户通过自定义 Skill 给代码打分，用于外包验收——研发任务外包后，收到代码先用 AI Review 评分，再把报告退回给外包团队修改。（来源：〔185618〕§十二）
3. 已知边界：评分规则可能很激进，甚至出现负分；评分是否可信取决于规则质量、模型能力和审查上下文。（来源：〔185618〕§十二）

### §2.12 模型、成本与私有化约束

1. 模型稳定性与成本：内部服务偶尔不稳定、调用会中断；长任务 Token 消耗可能很高；如果成本统计不准确，团队很难判断真实投入。（来源：〔185618〕§十三）
2. 上下文压缩是长任务的关键能力：系统可自行压缩，但压缩超过能力边界后效果明显下降；部分客户使用的模型能力较弱、上下文窗口小，Agent 几轮分析后就容易丢失信息或得出浅层结论。推理参数同样重要——思考不足时代码审查容易只看表面；内部使用优先选更强模型与推理配置，交付客户时必须针对客户实际部署的模型做验证。（来源：〔185618〕§十四）
3. 私有化部署现实：很多客户私有化部署使用较早采购的硬件和较弱的模型，旧硬件跑新模型吞吐量低——内部环境十几分钟能完成的任务，客户环境可能需要数小时；同一套 Agent 不能只做一种固定配置，不同模型在工具调用、上下文理解、指令遵循和推理方式上都有差异，可能需要分别调优 Prompt、工具说明和调用策略；公有模型可参考官方资料，私有模型往往只能到客户现场测试。（来源：〔185618〕§十五）
4. 该挑战被表述为跨产品问题：代码审查、Bugfix 和其他 AI 产品都会遇到，后续需要考虑是否由平台层沉淀模型适配、上下文管理和私有化部署能力。（来源：〔185618〕§十五）
5. 部分内部产品源于开源项目二次开发（例如基于 Kilo Code，名称根据语境推测），持续跟进上游版本、合并更新和维护私有化能力需要专门投入。（来源：〔185618〕§十六）

### §2.13 infReview 团队自身 AI 研发实践（事实记录）

1. 团队无统一研发模式（未统一采用 SDD、TDD 等），成员各自形成工作体系。（来源：〔185618〕§十）
2. 受访人个人做法：先阅读现有代码、写清楚任务指导和约束，让 Agent 按脚本持续工作；需要业务判断或架构决策的地方由 Agent 交回给人，其余尽量自动推进；要求 Agent 小粒度提交以便回退；任务可能运行一整晚，次日查看报告、决策点和提交记录决定继续、调整或回退；完成后重新让 Agent 对照最初目标检查实现是否偏离，不一致则整理成新任务进入下一轮。（来源：〔185618〕§十）
3. 大规模 AI 变更风险的事实观察：AI 容易过度设计，见过单次增删数万行的情况，其中相当部分是没有必要的结构调整；任务拆分和决策仍依赖有经验的人；AI 把工作拉平后，人仍需重新阅读核心代码和设计、识别值得质疑的地方；方案不能假设天然完整，AI 在实现或审查时发现方案漏洞应回到人判断。（来源：〔185618〕§十一）

### §2.14 双方共识的后续动作清单

访谈结尾双方给出的后续建议（原文 9 条，照录要点）：① 让真实团队继续使用现有 Code Review 和 Bugfix 闭环，收集准确率、误报、成本和稳定性反馈；② 与已落地 Bugfix 机器人的团队对齐接口和责任边界，避免重复建设；③ 为客户演示准备完整闭环材料（视频、PPT 或演示环境）；④ 继续提升审查准确率、召回率、稳定性和成本表现；⑤ 完善多轮 Review 中对用户 Comment 和"不修改原因"的理解；⑥ 探索需求文档接入，让审查从"只看代码"升级为"对照需求检查实现"；⑦ 评估 MCP、Skill 和代码托管平台原生接口的统一接入方式；⑧ 针对客户私有模型和旧硬件建立分层适配与验收标准；⑨ 由平台团队逐步沉淀模型适配、上下文压缩和私有化部署等通用能力。（来源：〔185618〕§十六）

## §3 飞书×小鱼儿三 Gate 蓝图

### §3.1 背景与问题来源

1. 现状问题：用户在飞书话题群记录问题后，需求 Bot 会在飞书项目中创建需求或缺陷；用户还需再次 @小鱼儿才进入 Bug 修复或需求实施——登记和执行是两条依赖人工记忆连接的链路。（来源：〔三Gate蓝图〕§1）
2. 未来进入 AI 研发流程的问题来自三处：① 飞书项目中已有的需求或缺陷；② CI、E2E 和定期巡检发现的技术债；③ 飞书内部反馈群中的问题和需求信号。（来源：〔三Gate蓝图〕§1）
3. 设计张力（原文陈述）：这些渠道只是把需求或问题收集起来，不代表 AI 可以马上开始改代码——如果来一个就自动做一个，可能重复处理同一件事、把时间花在不重要的事情上、甚至在没人确认的情况下改错地方；但如果每一步都要人手动转发和盯进度，AI 又无法真正独立完成交付。（来源：〔三Gate蓝图〕§1）

### §3.2 设计原则

1. 借鉴原则（引自 ClawSweeper 调研）：事件、Issue、评论和 CI 结果只是输入信号，自动化必须经过 Intake、明确授权和 Gate，才能逐步获得 Review、Repair 和 Merge 权限。（来源：〔三Gate蓝图〕§1）
2. 总体原则一句话：**飞书承载候选工作和人类决策，Multica 管理已准入工作，AI 完成高频执行，Git/CI/E2E 提供验证事实。**（来源：〔三Gate蓝图〕§1）

### §3.3 目标（原文 10 条，编号照录为 4–13）

1. 将飞书项目、CI/CD 巡检和内部反馈统一接入候选工作池（飞书项目）。
2. 候选事项经过明确准入后，才进入已受理工作池，由 Multica Issue 承载。
3. 每个已受理的 Multica Issue 都是一项可独立交付的工作，并一对一绑定飞书话题群中的一个话题。
4. AI 在修改代码前生成修复方案或需求 Spec，并由人批准。
5. 方案批准后，AI 自主完成开发、测试、E2E、Review 和失败修复。
6. AI 形成绑定固定代码版本的交付证据包，并通过小鱼儿请求用户验收。
7. 验收失败时，用户补充上下文，同一 Issue 回到 AI 修复阶段。
8. 验收通过后，只允许合并被批准的候选版本。
9. 只有合并成功，Multica Issue 才进入 `Done`。
10. 飞书展示状态和承载决策，但不维护第二套可写的执行状态。
（来源：〔三Gate蓝图〕§2.1）

### §3.4 非目标（原文 7 条）

1. 本阶段不决定 Webhook、Bridge、插件或 API 的实现方式。
2. 不定义数据库、事件 Schema 和部署结构。
3. 不默认允许 AI 自动合并、发布或部署。
4. 不把完整 Agent transcript 和工具日志同步到飞书。
5. 不让飞书和 Multica 同时维护一套可写的 Issue 执行状态。
6. 不为每个临时子 Agent 创建独立飞书机器人身份。
7. 不在本阶段确定全部低风险任务的自动准入策略。
（来源：〔三Gate蓝图〕§2.2）

### §3.5 总体分工

| 参与方 | 主要责任 | 不承担的责任 |
|---|---|---|
| 飞书项目 | 候选需求、缺陷和业务上下文 | AI 派发和执行状态 |
| 飞书话题 / 卡片 | 讨论、准入、方案批准、阻塞决策和验收 | 成为第二套任务状态源 |
| 需求 Bot | 从反馈归纳并创建或关联飞书项目工作项 | 派发 Agent |
| 小鱼儿 | 推送 Multica 卡片、收集决策、展示状态和证据 | 独立维护另一套 Issue 状态 |
| Multica | Issue、Task、派发、重试、阻塞、证据和最终状态 | 未经授权决定业务优先级 |
| AI Agent | 调研、规划、开发、测试、E2E、Review 和修复 | 绕过批准直接合并 |
| Git / CI / E2E | 保存代码版本和验证事实 | 判断产品意图和业务价值 |
（来源：〔三Gate蓝图〕§3.1）

### §3.6 候选工作来源与准入

1. 所有候选工作统一进入飞书项目（候选池）；工作准入通过后，系统创建 Multica Issue，并按类型绑定对应话题群中的一个话题。（来源：〔三Gate蓝图〕§3.2）
2. 候选来源处理规则：飞书项目需求/缺陷直接进入候选池；飞书内部反馈由需求 Bot 归纳、澄清和去重后创建或关联飞书项目工作项；CI、E2E 和定期巡检的问题清单拆分或合并为可独立交付的技术债候选。（来源：〔三Gate蓝图〕§3.2）
3. 候选事项只表示问题已记录；未经工作准入，不创建执行承诺，也不授权 AI 修改代码。（来源：〔三Gate蓝图〕§3.2）

### §3.7 话题群与交付单元

1. 固定一对一关系：一个已受理工作项 = 一个可独立交付的 Multica Issue = 一个飞书话题。"工作项"指业务交付单元，不是 Multica 内部拆分的 Task，也不是 Agent 的某一次 Run；一个 Issue 可包含多个 Task、多次 Run 和多个候选版本，但整个交付生命周期始终在同一个飞书话题中协作。（来源：〔三Gate蓝图〕§3.3）
2. 初步规划两个话题群：需求 & 缺陷话题群（来源：飞书项目需求/缺陷、内部反馈归纳出的需求或 Bug；一个话题 = 一项可独立验收的需求或 Bug）；技术债务话题群（来源：CI、E2E、定期巡检及其他工程质量问题；一个话题 = 一项可独立验证和交付的技术债修复）。（来源：〔三Gate蓝图〕§3.3）
3. 拆分规则：一个候选事项包含多个可分别验收的目标时，应在准入阶段拆成多个 Issue 和多个话题；Agent 内部拆分 Task、重试 Run 或更换执行者，不创建新话题。（来源：〔三Gate蓝图〕§3.3）
4. 状态源：话题是人类协作和决策入口，Multica Issue 仍是执行状态的事实源。（来源：〔三Gate蓝图〕§3.3）

### §3.8 三 Gate 概览

1. 三个 Gate（Gate 0 工作准入 / Gate 1 方案批准 / Gate 2 交付验收）都通过飞书卡片请求人工决策；卡片只展示当前决策所需的信息，并明确批准对象、授权范围和交付负责人。（来源：〔三Gate蓝图〕§3.4；该节含流程图，图片内容不在本文转述范围）

### §3.9 四阶段主流程

**阶段一：工作准入（Gate 0）**

1. 核心问题：这件事是否值得成为组织承诺推进的研发交付？（来源：〔三Gate蓝图〕§3.5）
2. Gate 0 按事项类型展示最小准入信息——需求：交付目标、价值或影响；缺陷：实际行为、预期行为、影响或证据。（来源：〔三Gate蓝图〕§3.5）
3. 准入人同时指派一名交付负责人；该负责人在一期默认负责 Gate 1 的方案批准和 Gate 2 的交付验收。（来源：〔三Gate蓝图〕§3.5）
4. Gate 0 的四种结果：受理并指派（建立 Multica Issue 和飞书话题，允许 AI 调研和规划）/ 信息不足（补充上下文后重新审核）/ 延后或拒绝（保留事项和决策原因）/ 合并（关联到已有事项，避免重复工作）。（来源：〔三Gate蓝图〕§3.5）

**阶段二：方案批准（Gate 1）**

5. 核心问题：准备怎样做，范围、风险和验收方式是否正确？（来源：〔三Gate蓝图〕§3.5）
6. AI 生成修复方案或需求 Spec，内容包括：目标、范围、非目标、实施思路、影响面、验证计划、验收标准和待决风险；小鱼儿把方案卡推送到飞书，由交付负责人批准实施、要求修改、补充信息或取消。（来源：〔三Gate蓝图〕§3.5）
7. 授权边界：只有方案批准才授权 AI 修改代码。（来源：〔三Gate蓝图〕§3.5）

**阶段三：AI 自主完成**

8. 核心问题：AI 能否独立形成可信的候选交付？（来源：〔三Gate蓝图〕§3.5）
9. 流程链：开发 → 单元测试、类型检查、Lint、构建 → E2E 与真实行为验证 → 独立 Review → 候选交付。测试、E2E 或 Review 失败时，AI 自动修复并重新验证；只有缺少业务判断、权限、关键上下文，或多次修复不能收敛时，小鱼儿才请求人的决策。（来源：〔三Gate蓝图〕§3.5）
10. 阶段产物：绑定固定代码版本的证据包，包括行为变化、验收标准、测试/E2E 结果、Review 结论、已知限制和验收入口。（来源：〔三Gate蓝图〕§3.5）

**阶段四：交付验收（Gate 2）**

11. 核心问题：这个候选版本是否满足真实需求？（来源：〔三Gate蓝图〕§3.5）
12. 小鱼儿推送 Gate 2 交付验收卡，集中展示：单元测试、CI、E2E 和独立 Review 的结果摘要；E2E 验收截图或录屏；直接进入当前候选版本的验收环境链接；本次人工验收目标。（来源：〔三Gate蓝图〕§3.5）
13. 验收结果：验收通过 → 授权该候选版本进入合并；验收失败 → 用户补充实际表现和期望结果，同一 Issue 回到 AI 自主完成阶段。（来源：〔三Gate蓝图〕§3.5）

### §3.10 状态事实源与终态规则

1. E2E 截图、录屏、验收环境和人工验收结论都绑定同一个候选版本；候选代码变化后，旧证据和旧验收批准同时失效。（来源：〔三Gate蓝图〕§3.5）
2. 只有被批准的版本成功合并，Multica Issue 才进入 `Done`。（来源：〔三Gate蓝图〕§3.5）
3. 全局状态规则：Multica 为执行状态唯一事实源，飞书展示状态和承载决策但不维护第二套可写的执行状态。（来源：〔三Gate蓝图〕§1、§2.1、§3.3）
4. 合并边界：验收通过后"只允许合并被批准的候选版本"；非目标明确"不默认允许 AI 自动合并、发布或部署"。（来源：〔三Gate蓝图〕§2.1、§2.2）

### §3.11 遗留 TODO 与待讨论项

1. 通知闭环一节原文为"TODO"，未展开设计。（来源：〔三Gate蓝图〕§3.6）
2. 待讨论一：谁拥有工作准入权限。原文列出三种候选口径：① 触发入口——内部反馈直接在群里 @小鱼儿，自动推送 Gate 0 卡片；② 自动——满足 Gate 0 的上下文字段要求时 bot 自己派发；③ 手动——研发负责人 & 产品经理。（来源：〔三Gate蓝图〕§4）
3. 待讨论二：飞书内部反馈群只作为收集，具体实施在需求 & 缺陷话题群、技术债务话题群。（来源：〔三Gate蓝图〕§4）

### §3.12 已排期三项

1. CICD 巡检问题日报问题（先完成 E2E 的问题修复），自动记录到飞书项目。
2. Gate 0 准入后，自动在对应的话题群拉起一个话题，并且 @负责人。
3. Multica 完成方案设计后，推送方案 Gate 1 审核卡片，并且 @负责人。
（来源：〔三Gate蓝图〕"任务排期和拆分"一节；第 3 项原文中"Gate 1"对应 §3.9 阶段二的方案批准）

## §4 外部 BugFix 调研启示（Symphony / ClawSweeper / OpenHands Resolver）

### §4.1 调研口径

1. 调研对象为 Symphony（OpenAI）、ClawSweeper（OpenClaw 仓库体系）、OpenHands Resolver 三个项目；ClawSweeper 部分基于 `openclaw/clawsweeper` main 分支提交 `c712241…`（2026-07-23）。（来源：〔外部调研〕§1、附录 2）
2. 交集分析忽略各项目在触发方式、复现强制程度、GitHub 写入方式和自动合并策略上的差异。（来源：〔外部调研〕§1）

### §4.2 共同架构

1. 核心结论：三者都采用"确定性外层工作流 + Agent 执行循环 + 验证与人工反馈边界"。确定性系统负责准入、环境、状态和权限，Agent 负责开放式分析、修改和命令执行。（来源：〔外部调研〕§1）

### §4.3 交集九阶段

1. 任务输入（Issue、PR 评论、Tracker 工单、定时扫描等信号）。
2. 准入与调度（状态、标签、权限、账户、阻塞关系、并发额度或仓库策略检查，避免无权限执行和重复运行）。
3. 隔离环境（任务级 Workspace/Sandbox，检出固定代码版本，Setup/Hooks/仓库脚本准备依赖）。
4. 上下文组装（问题描述、评论、日志、代码、仓库规范、测试命令和执行 Prompt）。
5. 诊断与复现（Agent 阅读代码、运行测试或脚本、必要时 Browser/E2E，建立问题存在的证据）。
6. 修复循环（"搜索—假设—修改—执行—观察"循环中完成代码修改并迭代）。
7. 验证门禁（目标测试、回归测试、Lint、类型检查、Build、CI 或二次 Review；失败进入有限重试或 Repair Loop）。
8. 结果交付（回写任务状态，按项目能力创建或更新 Branch、Commit 和 PR）。
9. 反馈与终态（成功进入 Review/Merge/关闭；无法复现、缺少权限、需产品决策或验证失败时进入 Blocked、No-op 或人工评审）。
（来源：〔外部调研〕§1.2）

### §4.4 共性能力与实现边界差异

| 流程环节 | 三个项目的交集 | 主要差异 |
|---|---|---|
| 任务准入 | 执行前都有资格检查与去重机制 | Symphony 依据 Tracker 状态；ClawSweeper 使用严格 Implementation Gate；OpenHands 检查触发方式、Write 权限和账户 |
| 环境隔离 | 都在任务级独立工作区中运行 Agent | 环境创建、依赖安装和生命周期管理方式不同 |
| 问题复现 | 都允许 Agent 通过测试、命令和仓库工具调查问题 | ClawSweeper 对 strict_bug 强制先复现或建立失败测试；OpenHands 默认没有修改前失败的硬 Gate；Symphony 由 WORKFLOW.md 定义 |
| 代码修复 | 都使用 Agent Action-Observation Loop | 模型、工具、最大轮次和恢复机制不同 |
| 质量验证 | 都把测试、检查或 Review 放在 Agent 完成声明之后 | ClawSweeper 的确定性 Gate 最完整；OpenHands 依赖 Hooks、CI 与人工 Review；Symphony 依赖仓库执行契约 |
| 交付与反馈 | 都将执行结果回写外部系统，并允许失败或反馈进入下一轮 | PR 创建、自动重试和合并策略不同；Symphony 不规定统一的 PR/合并实现 |
（来源：〔外部调研〕§1.3）

### §4.5 Human-on-* 框架

1. 三种标准模式定义：Human-in-the-loop（人的输入或批准是主链路必要步骤，系统必须等待）；Human-on-the-loop（系统自动执行、人持续观察并在关键边界批准/纠偏/终止）；Human-on-exception（正常路径完全自动化，仅在无法复现、缺少权限、需要决策或触发风险规则时找人）。（来源：〔外部调研〕§2.1）
2. 为描述这些项目另设的分析标签（原文明确"并非项目官方术语"）：Human-on-state、Human-on-trigger、Human-on-feedback、Human-on-approval。（来源：〔外部调研〕§2）

### §4.6 三项目人类触点对比

| 项目 | 任务启动 | 运行中介入 | 反馈后再执行 | 最终交付 | 主要模式 |
|---|---|---|---|---|---|
| Symphony | Scheduler 可自动领取符合条件的 Tracker 工单，不要求逐个由人触发 | 进入 Blocked 时等待信息、授权或审批；进入 Human Review 时停止自动修改 | 人修改 Tracker 状态或补充信息后，由 Reconcile 恢复或终止 | PR Review 与 Merge 由 WORKFLOW.md 和仓库流程规定 | Human-on-state + Human-on-exception |
| ClawSweeper | Issue 可经严格 Gate 自动排队，也允许 Maintainer 显式创建 Repair Job | 自动完成计划、复现、修复和验证；无法复现、需要产品决策或触发安全边界时停止 | 自动执行有限 Exact-head Review、CI Repair Loop；Blocked 后由人补证据或作决策 | Issue-to-PR 和 autofix 由维护者评审、合并；automerge 必须预先显式授权 | Human-on-exception + Human-on-approval |
| OpenHands Resolver | 每次任务必须由有 Write 权限的人添加 Label 或输入 @openhands | Conversation 启动后 Agent 自动分析、修改、测试、Commit、Push 并创建 Draft PR | Review 意见或 CI 失败后，需要人再次输入 @openhands 才创建新 Conversation | 由维护者 Review、Merge、发布、监控和回滚 | Human-on-trigger + Human-on-feedback |
（来源：〔外部调研〕§2.2；三项目的精确时间线见 §2.3）

### §4.7 对 BugFix Bot 自动化边界的四条启示（原文）

1. 正常路径不应逐步等人：从任务准入到验证完成的 Draft PR 可以无人值守执行。
2. 人应在语义和风险边界出现：无法复现、预期行为不明确、缺少权限、涉及安全或产品决策时再升级。
3. 异常必须结构化：升级给人时应同时提供已尝试步骤、失败证据、当前假设和需要回答的单一决策问题。
4. 合并策略需要分级：Issue 自动修复默认人工合并；只有低风险、证据完整并经仓库显式授权的任务才考虑自动合并。
（来源：〔外部调研〕§2.4）

### §4.8 Symphony 关键机制

1. 定位：调度与运行 Agent——从问题跟踪系统持续领取工单，在隔离工作区中启动 Codex，并根据工单状态协调继续执行、重试、人工评审与清理；如何复现和验证 Bug 由仓库的 WORKFLOW.md、测试、E2E、日志和环境脚本共同定义。（来源：〔外部调研〕附录 1）
2. WORKFLOW.md：项目仓库内随代码版本管理的执行契约；YAML Front Matter（tracker/polling/workspace/hooks/agent/codex）+ Markdown 正文（工单 Prompt 模板，可读 `issue`、`attempt` 变量）。（来源：〔外部调研〕附录 1.2.1）
3. Tracker：与外部工单系统的适配层——候选工单获取、状态刷新、终态查询、数据标准化为统一 Issue 模型、`tracker.kind` 配置入口。（来源：〔外部调研〕附录 1.2.2）
4. 调度概念链：Poll（按 interval 周期查询）→ Candidate（本轮候选）→ Dispatchable（通过状态、标签、阻塞关系和并发额度检查）→ Claim（内存预占，避免同一工单重复启动/重试/并发执行）。（来源：〔外部调研〕附录 1.2.3）
5. Workspace 与 Hooks：单工单独立执行目录，重试可复用；`after_create` / `before_run` / `after_run` / `before_remove` 生命周期脚本。（来源：〔外部调研〕附录 1.2.4）
6. Agent Runner：在 Workspace 内启动 Codex App Server，通过标准输入输出发送初始化请求和 Workflow Prompt，持续读取会话事件、运行状态、Token 用量、日志和验证证据。（来源：〔外部调研〕附录 1.2.6）
7. Reconcile 结果状态：Continuation（Turn 正常结束但工单仍 Active，继续下一轮）、Stalled（超时无事件，进入失败重试）、Blocked（需人工输入/授权/审批）、Human Review（停止自动修改）、Terminal（工单结束，停止并按策略清理）。（来源：〔外部调研〕附录 1.2.7）

### §4.9 ClawSweeper 关键机制

1. 定位：保守型维护自动化——持续审查 GitHub Issue、PR 和部分提交，把模型判断固化为可审计报告，再由确定性代码决定是否评论、打标签、创建修复任务、修改分支、创建 PR 或执行受控合并；由 Review、Apply、Issue Intake、Repair Worker、Validation、GitHub Mutation 和 Durable State 多条流水线组成。（来源：〔外部调研〕附录 2）
2. Read-only Review：Codex 对 main、Issue/PR 讨论、代码、测试和历史进行严格只读分析（禁止修改文件、安装依赖、执行产出性构建测试、提交代码或直接操作 GitHub，检出目录保持字节级干净）；输出结构化判断（保留/关闭、置信度、问题类别、复现状态、风险、修复边界、验证命令等）；Review 只提决策和工作建议，不拥有写凭证。（来源：〔外部调研〕附录 2.2.2）
3. 提案与写入分离：Codex 生成提案，TypeScript Applicator 决定提案是否仍可安全执行；Apply 在评论、标签或关闭前重新读取 GitHub 实时状态，检查 Snapshot Drift、标签、作者权限、关联 PR、仓库策略和目标是否仍开放。（来源：〔外部调研〕附录 2.2.3）
4. Implementation Gate：`strict_bug` 要求现有行为缺陷、reproduction_status=reproduced 且置信度高、work_candidate=queue_fix_pr 且置信度高、不需要新功能/新配置/产品决策；`vision_fit` 要求与 VISION.md 明确一致、复杂度小；宽松通道 `viable` 在 openclaw/openclaw 和 openclaw/clawhub 明确禁用。（来源：〔外部调研〕附录 2.2.4）
5. 复现契约：Review 阶段的"已复现"是基于主干路径和已有证据的结构化审查结论（Review Worker 本身禁止执行测试），不等同于运行环境重放；Repair 阶段 Prompt 明确要求严格 Bug 任务先复现 Bug 或先增加失败的回归测试，最新 main 无法复现则报告阻塞并停止、不创建 PR。（来源：〔外部调研〕附录 2.2.4）
6. Durable Job 与多层去重：确定性 Job Path、Cluster ID 和分支名构成稳定身份，重试复用同一逻辑任务；Intake 检查现有开放 PR、生成分支、Review Report 相关 PR、已有 Job、Intake Receipt 和同 Cluster 实现；正式入队前实时复查 Issue 是否开放/锁定/含安全标签/出现新实现 PR。（来源：〔外部调研〕附录 2.2.5）
7. Plan / Execute 分离：Plan Worker 校验 Job、检出目标仓库、经 Codex 形成结构化修复计划；Execute Worker 在固定 Base SHA 上执行复现、编辑和验证，不让 Codex 自行决定 GitHub 写操作；Codex Thread Cache 跨 GitHub Actions 尝试恢复。（来源：〔外部调研〕附录 2.2.6）
8. 验证闭环：执行 Review Report、Fix Artifact 和仓库规则提供的验证命令（OpenClaw 默认 `pnpm check:changed`）；编辑和本地验证围绕固定 Base SHA，主干移动由确定性 Final Base Sync 处理；验证失败可在固定 Base 重跑以区分修复引入的问题和主干原有失败；Exact-head Review 每轮修改后重新审查 PR 精确 Head SHA；完成条件 = 本地命令通过 + 精确 Head Review 无可执行 Finding + 必要 Checks 转绿 + GitHub Merge State 就绪。（来源：〔外部调研〕附录 2.2.7）
9. GitHub Mutation Boundary 与凭证隔离：GitHub App 按用途签发不同权限的短期 Token，不使用个人 PAT 作为写入降级方案；Codex 子进程环境清除 GitHub App 私钥、写 Token 等敏感凭证（模型无写凭证）；Commit、Push、PR、评论、标签、关闭和合并由确定性 Wrapper 在重新检查实时状态后执行；使用 Concurrency、Force-with-lease、Head SHA 检查和推送前等待窗口做并发保护。（来源：〔外部调研〕附录 2.2.8）
10. 合并策略分级：Issue-to-PR 创建的 PR 带 autogenerated/autofix 标签，通过修复闭环后仍保持开放，由维护者最终评审合并（永不自动合并）；`autofix` 修复验证既有 PR 但不执行合并；`automerge` 只有维护者显式授权且 Exact-head Review、CI、可合并性、安全、暂停标签、Review Thread 和仓库策略全部通过才执行受控合并；Blocked/No-op 可在不创建 PR 的情况下结束并把原因写入 Result Ledger。（来源：〔外部调研〕附录 2.1、附录 2.2.9）
11. 恢复机制：Runner 被替换、Source Head 漂移或 Thread 无法恢复时，通过稳定 Work Key、缓存、Requeue 和结果账本继续同一个逻辑任务。（来源：〔外部调研〕附录 2.2.9）

### §4.10 OpenHands Resolver 关键机制

1. 定位：由 GitHub Integration、V1 Conversation、Sandbox、Agent Server 与 MCP 工具组成的 Agent 修复入口——把 Issue、PR 评论或 Review Thread 转换为新会话，在隔离工作区完成调查、修改、测试与 Git 交付；"修改前必须复现失败、修改后必须留下通过证据"不是平台默认强制状态机，需通过项目 Skills、Hooks、测试脚本与 CI 补齐。（来源：〔外部调研〕附录 3）
2. 触发 Gate：Issue 添加 `openhands` Label / Issue 或 PR 新评论精确出现 `@openhands` / PR 行级 Review 新评论出现 `@openhands`；评论必须是 created 事件，机器人自身消息被过滤防回环；触发者必须对目标仓库有 Write 权限；GitHub App Token 用于 Reaction/评论，用户 Token 用于 Clone/Push/创建 PR。（来源：〔外部调研〕附录 3.2.2）
3. 会话模型：单次触发单次会话；PR 上再次触发会创建新会话并重新检出当前 PR Branch，跨轮连续性主要来自 Git 分支、Issue/PR 上下文和仓库配置。（来源：〔外部调研〕附录 3.2.1）
4. 仓库契约层：`.openhands/setup.sh`（Clone 后初始化）、`.openhands/pre-commit.sh`（安装为 Git Pre-commit Hook）、项目 Skills 目录（描述复现步骤、日志位置、E2E 入口）、`.openhands/hooks.json`（Tool/Session/Stop Hook，Stop Hook 可拒绝 Agent 完成）；这些机制只有仓库实际配置且成功加载时才形成约束。（来源：〔外部调研〕附录 3.2.5）
5. 复现与证据边界：复现路径由 Issue 信息、Prompt、项目 Skills、环境可用性和 Agent 推理共同决定，不是独立 Reproducer 服务预先生成；没有修改前失败的硬 Gate；没有"Base 失败、Patch 通过"的双态证据协议；命令与工具结果主要保存在 Conversation 事件中，只有 Agent 主动写入 PR 描述、测试或 Final Response 的内容才成为 GitHub 上长期可审阅的证据。（来源：〔外部调研〕附录 3.2.7）
6. 交付：Branch、Commit、Push 由 Agent 按 Prompt 通过 Git 命令完成；Issue 任务创建 `openhands/` 前缀分支并主动调用 MCP `create_pr`（默认 Draft PR）；PR 评论任务直接在原 PR Branch 上更新原 PR。（来源：〔外部调研〕附录 3.2.9）
7. 终态语义：Callback 仅在 `execution_status=finished` 时把 Final Response 写回原 Issue/PR/Review Thread；`finished` 代表 Agent 执行结束，不等于已验证测试、CI 或 PR 一定成功创建；Proactive CI 能识别失败 Actions 或冲突并建议使用 `@OpenHands`，但不会仅凭 CI 失败自动启动 Agent；合并、发布、监控和回滚属仓库原有研发流程。（来源：〔外部调研〕附录 3.2.10）
