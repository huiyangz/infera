现阶段系统不会自动修复报告中的所有问题，仍然需要研发人员阅读报告并自行处理。下一版本会继续建设自动修复入口，但自动修复不是简单地在 Review 中给出一小段 Patch 建议，而是一个更完整的项目级修复过程。

## 三、Bugfix 机器人如何接入审查结果

**受访人：** 自动修复闭环的基本思路，是把问题报告、代码仓库和必要上下文交给修复 Agent。修复 Agent 修改代码后，再进入 Code Review，形成“发现问题、修改代码、重新审查”的循环。

目前对方团队的机器人主要服务于他们自己的客户反馈场景。他们直接从客户群或反馈入口收集问题，然后在自己的系统中定位和修复。修复完成后，再把结果接到我们的代码审查能力中。

他们没有通过我们的业务系统接口读取报告，而是直接从代码托管平台读取审查结果。因为我们的报告本来就会回写到代码托管平台，所以他们只要拿到对应仓库和报告，就能继续处理。GitHub 也是类似的思路：通过原生接口或 `gh` 命令就能取得必要信息，不一定需要我们额外提供一套集成 API。

修复完成后，代码不会自动合并，仍然需要人工做最后检查。我们产品侧未来也可以提供更正式的自动修复入口，但具体产品设计还没有完成。

## 七、近期重点仍是提升审查质量

**访谈人：** 除了接入自动修复，你们在 Code Review 方面还有哪些计划？

**受访人：** 当前最主要的工作仍然是提升审查准确率、召回率、稳定性和成本表现。AI 审查可能一次产生大量问题，如果准确率不够，用户面对成千上万条结果就无法使用。因此，结果数量不是越多越好，必须控制噪声并提高有效问题比例。

系统支持用户配置部分审查规则和开关，也允许用户挂载自己的 Skill，覆盖或补充默认规则。整体上可以理解为：一个审查 Agent 配置若干工具和 Skill，由这些能力共同决定审查方式。

自动修复也会继续建设，但完整的项目级修复需要更强的上下文和服务能力，不只是把当前 Review 建议直接套用到代码中。

## 九、审查过程中的人工介入与多轮 Review

**访谈人：** 审查报告出来以后，你们内部会增加人工审批节点吗？

**受访人：** 我们的审查过程本身希望尽量自动化，一般不会在系统内部增加固定人工节点。但最终是否修改、是否合并，仍由使用团队决定。

系统支持多轮 Review。开发者修改代码并再次提交后，下一轮审查会带上上一轮报告和历史问题，同时重新检查整个仓库及本轮增量。新报告会说明哪些旧问题已经修复、哪些仍然存在，以及本次是否引入了新问题。

**访谈人：** 如果开发者在 Review Comment 下解释“这是故意这样写的，暂时不改”，系统会理解并在下一轮尊重这个决定吗？

**受访人：** 目前这部分还不成熟。用户反馈会被记录，但怎样可靠地把自然语言解释转成后续审查约束，还没有完全想清楚。用户不一定会认真回复，回复方式也不统一，因此反馈闭环仍需要继续设计。

这也是当前比较薄弱的部分：只有用户真正持续使用，系统才能收集足够反馈，判断哪些规则有效、哪些误报需要调整。

## 十、团队当前的 AI 开发方式

**访谈人：** 你们研发团队平常怎样使用 AI？会统一采用 SDD、TDD 等方式吗？

**受访人：** 没有统一模式。团队规模不大，每个人都有自己的习惯和经验，目前更像各自形成了一套工作体系。

我最近的做法是先阅读现有代码，写清楚任务指导和约束，再让 Agent 按脚本持续工作。遇到需要业务判断或架构决策的地方，Agent 会把问题交回给人；其余步骤尽量自动推进。过程中要求 Agent 做小粒度提交，这样如果某一步不合理，可以回退到对应提交。

任务可能持续运行一整晚。第二天我查看报告、决策点和提交记录，再决定继续、调整还是回退。对于已完成的部分，我还会在后续重新让 Agent 对照最初目标检查实现是否偏离。如果目标与实现不一致，就把差异整理成新任务，进入下一轮。

## 十一、大规模 AI 代码变更的风险

**访谈人：** 你为什么允许 Agent 一次提交上万行代码？如何判断这么大的改动是正确的？

**受访人：** 这确实是风险。AI 很容易过度设计，也可能产生异常大的 Diff。我们见过单次增删达到数万行的情况，其中相当一部分是没有必要的结构调整。

任务通常按需求拆分，但拆分和决策本身仍依赖有经验的人。如果缺少经验，Agent 给出的答案听起来很合理，实际上可能已经偏离目标，而使用者未必看得出来。过去不同职级承担不同层次的架构和方案决策；现在很多工作被 AI 拉平后，人仍然需要重新阅读核心代码和设计，识别哪些地方值得质疑。

因此，方案必须尽量写得让 AI 能理解，但也不能假设方案天然完整。AI 在实现或审查时可能发现方案漏洞，这时应回到人来判断：是补充方案、接受 AI 建议，还是坚持原设计。

## 十二、代码评分与外包验收场景

**访谈人：** 未来会不会给代码审查结果一个总分？

**受访人：** 有这个计划。现在有些客户已经通过自定义 Skill 给代码打分。他们把研发任务外包，收到代码后先用 AI Review 评分，再把报告退回给外包团队修改。

这种场景有明确价值：客户需要一种相对统一的验收标准。不过，评分规则也可能很激进，甚至出现负分。因此，评分是否可信仍取决于规则质量、模型能力和审查上下文。

## 十三、闭环落地依赖真实使用反馈

**访谈人：** 总体来看，我们确实需要一个大的生产闭环，代码审查是其中一环。当前最重要的可能不是先画出完整蓝图，而是让已有能力被真实团队用起来。只有进入实际项目，才能收集反馈，知道效果究竟好不好。

**受访人：** 对。现在除了产品能力本身，还有两个现实问题：模型调用稳定性和成本。内部服务偶尔不稳定，调用会中断；长任务的 Token 消耗也可能很高。如果成本统计不准确，团队很难判断真实投入。

## 十四、模型、上下文与成本问题

双方讨论了不同模型和接入方式的差异。使用 Codex Subscription、第三方模型服务或公司内部平台时，即使底层模型名称相同，上下文管理、自动压缩、工具调用方式和思考参数也可能不同，因此实际效果并不等价。

**受访人：** 上下文压缩是长任务的关键能力。系统可以自行压缩，但压缩超过能力边界后，效果会明显下降。当前一些客户使用的模型能力较弱，上下文窗口也小，导致 Agent 进行几轮分析后就容易丢失信息或得出浅层结论。

推理能力同样重要。如果模型没有开启足够的思考，代码审查很容易只看表面。内部使用时，我们可以优先选择更强模型和更合适的推理配置；交付客户时，则必须针对客户实际部署的模型做验证，不能只以内部最佳环境的效果为准。

## 十五、私有化部署的现实限制

很多客户采用私有化部署，使用较早采购的硬件和能力较弱的模型。旧硬件运行新模型时，吞吐量可能很低：内部环境十几分钟能完成的任务，在客户环境可能需要数小时。

因此，同一套 Agent 不能只做一种固定配置。不同模型在工具调用、上下文理解、指令遵循和推理方式上都有差异，可能需要分别调优 Prompt、工具说明和调用策略。公有模型可以参考官方资料，私有模型则往往只能到客户现场测试。

这不是单个产品的问题。代码审查、Bugfix 和其他 AI 产品都会遇到相同挑战，后续需要考虑是否由平台层沉淀模型适配、上下文管理和私有化部署能力，减少每个团队重复建设。
