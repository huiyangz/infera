## 1. 一页摘要（TL;DR）

**infera 是一个面向 FDE 团队的「Agent 主导的代码交付流水线」。**

FDE 工程师提一句需求，infera 上的多个专职 AI Agent 自动接力——写 spec、生成测试用例与单测、写实现代码、跑测试、做代码审核——把活一路推到一个可部署的 PR。整个过程是一条**带回环的迭代闭环**：测试不过、审核不过，都自动回到写代码的 Agent 反复改，直到通过。人只在两个地方介入：**定方向（提需求/澄清）** 和 **审核（spec 审批、代码最终批准）**。

核心特征：
- **Agent 主导**，人退到方向与审核（押注"未来一定是 Agent 主导"）
- **多专职 Agent**（Spec / Test / Coder / Reviewer），每个 stage 一个，优于一个通用 Agent
- **spec 是唯一信任源**，测试用例从 spec 生成（SDD + TDD 融合）
- **loop engineering**：所有验证不过，回到 Coder Agent 修复
- **执行可插拔**：默认云端 Agent 自动跑；人想自己上手时可接管某一步（自带 codex）
- **内部工具起步**，单租户，MVP 只做 Web

## 2. 背景：为什么做 infera

### 2.1 FDE 团队是谁
FDE（Forward Deployed Engineer / 前沿部署工程师）是面向交付的工程团队：核心工作是把需求快速变成可上线的代码——功能、bug 修复、集成对接。他们的特点是**项目驱动、节奏快、要的是"尽快交付"**。

### 2.2 当下交付的痛点
FDE 团队今天用 AI 编码工具（Claude Code、Codex 等）已经能大幅提速，但围绕"交付"本身还有几道没解开的结：

1. **每个 Agent 都是一个孤立的终端窗口**：会话一关就什么都不记得，同一段上下文一天讲四遍。Agent 越加越多，人越忙。
2. **没有流程，只有对话**：从需求到上线中间的 spec、测试、审核、部署，全靠人脑记忆和手工串联，容易漏、容易乱。
3. **上下文散落**：每个任务的背景、决策、代码改动分散在聊天记录、终端日志、个人脑子里，换人/换 Agent 就重来。
4. **测试和审核是被动的**：写完代码才想起测试，审核靠人肉，质量没保障，交付快了但不稳。
5. **Agent 各干各的，没有协作**：写代码的 Agent 不知道 spec 的约定，审核的人和写代码的 Agent 上下文对不上。

### 2.3 AI 趋势带来的机会
AI Agent 的能力正在快速逼近"能自主完成一整条交付"。方向已经清晰：**未来交付的主导者是 Agent，不是人**。但今天还差三样东西：一个让多 Agent 按流程协作的**平台**、一套把质量内建进流程的**方法论**（spec/测试/审核闭环）、一份让 Agent 工作可追踪可审核的**记录**。

### 2.4 infera 的回答
infera 把"交付"显式建模成一条**流水线**，让多个专职 Agent 在流水线上接力，把 spec、测试、审核、部署内建成流程的有机环节，并把每一步都留痕。**人不再串联流程，而是把握方向、审核结果。**

## 3. 产品定位

### 3.1 一句话定位
> **infera = FDE 团队的「Agent 主导的代码交付流水线」。**

### 3.2 是什么 / 不是什么

| infera 是 | infera 不是 |
|---|---|
| 一个让多 Agent 按流程接力交付代码的平台 | 一个聊天机器人 / 单机 Agent CLI |
| 一条带 spec/测试/审核/部署闭环的交付流水线 | 一个通用的任务看板（Jira/Linear 式） |
| Agent 主导、人审核的协作模式 | 一个全自动、人无需介入的"无人交付"系统 |
| 内部工具起步、可演进的产品 | 一个绑定单一模型厂商的封闭系统 |

### 3.3 给谁用
- **主要用户**：FDE 工程师——提需求、审核、必要时接管某一步。
- **次要用户**：技术负责人 / PM——看交付进度、审核 spec、把控质量。
- **MVP 范围**：单一 FDE 团队，内部使用。

### 3.4 核心价值主张
| 对谁 | 价值 |
|---|---|
| FDE 工程师 | 提一句需求，得到一个测过、审过、可部署的 PR；不用手工串联流程、不用反复交代上下文 |

| 组织 | 押注 Agent 主导的未来，从第一天起按这个方向建架构 |

## 4. 设计哲学（产品信念）

这些信念决定了一切"为什么"。理解它们比记功能重要。

1. **Agent 主导，人退到方向与审核。** 押注"未来一定是 Agent 主导"。Agent 干活、推进流程、自治迭代；人只定方向（提需求）、对结果负责（审核）。infera 不是"无人公司"——人是方向和质量的最终把关者。
2. **流程是领地，执行是引擎（可插拔）。** infera 拥有的是"流程"（spec → 测试 → 代码 → 审核 → 部署的闭环）。执行代码的引擎（云端 Agent / 人自带 codex）可换，但所有交付物最终回流到流程走完。
3. **spec 是唯一信任源（SDD）。** spec 是契约。后续所有阶段——测试用例、单测代码、实现代码——都回溯到 spec。spec 一定，下游就定了。
4. **测试驱动（TDD）。** 测试用例从 spec 生成，写在实现代码之前。测试不是写完代码才补的被动 gate，而是驱动代码生成的主动力量。测试用例 = 可执行的 spec。
5. **loop engineering（带回环的迭代闭环）。** 交付不是单向流水线。测试不过、审核不过，都回到写代码的 Agent 反复改，直到通过。loop 内部是 Agent 全自治，人不介入。
6. **多专职 Agent 优于通用 Agent。** 流水线上每个 stage 由一个专门配置的 Agent 负责（针对性 prompt / 模型 / 技能），比一个通用 Agent 包揽效果更好、更可控。
7. **静态编排先行，自主编排演进。** 当下 Agent 还不能靠谱地自主编排流程，MVP 先用静态模板 + 系统调度；架构上为"Agent 自主编排"留好空间，逐步演进。

## 5. 核心概念与术语表

| 术语 | 定义 |
|---|---|
| **Delivery（交付）** | 一次从需求到上线的完整推进实例。绑定一个需求来源 + 一个代码仓库 + 一个分支/PR。 |
| **Pipeline（流水线）** | 静态预定义的 stage 序列（需求→spec→…→部署）。MVP 内置一套固定模板。 |
| **Stage（阶段）** | 流水线上的一个节点，每个由一个专职 Agent 或系统负责。 |
| **Gate（人介入点）** | 需要人拍板的 stage：spec 审批、代码审核的最终批准。 |
| **专职 Agent** | 拥有独立配置、负责特定 stage 的 Agent。MVP 有 4 个：Spec / Test / Coder / Reviewer。 |
| **loop** | 流水线上的回环：验证不过时回到修复 hub（Coder Agent）重试。 |
| **spec** | 需求收敛后的契约文档，是整个 Delivery 的唯一信任源。 |
| **修复 hub** | Coder Agent。所有验证不过都回到它。 |
| **接管（Hand-off）** | 人在某个 stage 临时自己来（自带 codex），做完回流。v2 能力。 |

## 6. 产品架构（心智模型）

### 6.1 交付流水线总览

```
需求 ⇄ spec →〔spec 审批〕→ 用例生成 → 单测代码生成 → 代码生成 → 单元测试 →〔代码审核〕→ 部署
  (L1)         (人 gate)         (Test Agent)          (Coder Agent)         (人 gate)
                  ↑ SDD + TDD：用例/单测/代码都回溯到 spec
```

### 6.2 Agent 架构

**4 个专职 Worker Agent，MVP 由系统静态调度：**

| Stage | 专职 Agent | 职责 |
|---|---|---|
| 需求 → spec | **Spec Agent** | 需求澄清（L1）、写 spec（唯一信任源） |
| 用例生成 + 单测代码生成 | **Test Agent** | 从 spec 生成测试用例 + 写成可执行单测（TDD） |
| 代码生成 | **Coder Agent** | 写实现让单测过；所有 loop 回环的修复 hub |
| 代码审核 | **Reviewer Agent** | AI 预审，产出审核意见 |
| 单元测试运行 / 部署 | （系统，非 Agent） | 跑测试、合并 PR 触发部署 |

**控制层（谁推进 stage + 控制 loop）：**
- **MVP：系统静态调度**——按 stage 顺序依次叫起对应 Agent，loop 回环由系统硬编码触发。
- **v3：Supervisor Agent**——一个专门的"控制者 Agent"自主调度这些专职 Agent、控制 loop。

### 6.3 loop 工作机制

**统一规则：所有下游验证不过，都回到 Coder Agent 这个修复 hub。**

```
单元测试 ✗ ──→ Coder Agent
代码审核 ✗ ──→ Coder Agent     （改完 → 重跑单测 → 再审核）
```

- **L1（需求 ⇄ spec）**：Spec Agent 与人来回澄清，收敛成 spec。
- **L2（单测 ✗ → Coder）**：单测不过，Coder Agent 分析失败、改实现，重跑。
- **L3（审核 ✗ → Coder）**：审核不过（Reviewer 或人），Coder Agent 按意见改，重跑单测再审。
- **loop 边界**：连续不过 **3 次** → 停下升级请人（不无限重试，防死循环）。

### 6.4 数据与执行边界

| infera（平台侧） | 云端沙箱（执行侧） |
|---|---|
| Delivery / spec / 测试用例 / 状态 / 时间线 | Claude Code CLI 及其凭据 |
| 4 个 Agent 的配置 | 代码目录与本地文件 |
| Agent 每次执行的记录与结果 | 实际的文件修改与命令执行 |

代码在云端沙箱容器内执行（MVP 路线）。仓库通过 GitHub 同步进沙箱。

## 7. 流水线各 Stage 详解

每个 stage 按「目的 / 执行者 / 输入 / 输出 / 状态流转 / loop / 人介入 / 异常」说明。

### 7.1 需求
- **目的**：捕获一个待交付的功能 / bug / 任务。
- **执行者**：人（FDE）。
- **输入**：一句话描述（可附背景、相关链接）。
- **输出**：一条 Delivery 记录（初始状态）。
- **状态流转**：Delivery 创建 → 进入 spec stage。
- **人介入**：提需求本身即人介入。

### 7.2 spec（Spec Agent）
- **目的**：把模糊需求收敛成清晰的 spec（唯一信任源）。
- **执行者**：Spec Agent。
- **输入**：需求描述 + 仓库上下文 + 人的澄清。
- **输出**：spec 文档（功能描述、验收标准、约束、边界）。
- **loop**：**L1**——Spec Agent 追问不清楚的地方，人补充/澄清，直到 spec 收敛。
- **人介入**：人在 L1 响应澄清。
- **异常**：需求矛盾 / 技术不可行 → Spec Agent 标注，请人决断。

### 7.3 spec 审批（Gate）
- **目的**：人确认 spec 可作为唯一信任源。
- **执行者**：人。
- **输入**：spec 文档。
- **输出**：批准 / 打回（带意见）。
- **状态流转**：批准 → 进入用例生成；打回 → 回 Spec Agent（L1）改 spec。
- **人介入**：是（这是 Gate）。

### 7.4 用例生成 + 单测代码生成（Test Agent）
- **目的**：从 spec 生成测试用例 + 写成可执行单测（TDD）。
- **执行者**：Test Agent。
- **输入**：审批通过的 spec。
- **输出**：测试用例（描述性）+ 单元测试代码（可执行）。
- **状态流转**：产出单测代码 → 进入代码生成。
- **关键**：测试用例 = 可执行的 spec；单测在实现代码之前。

### 7.5 代码生成（Coder Agent）—— 修复 hub
- **目的**：写实现代码让单测通过。
- **执行者**：Coder Agent。
- **输入**：spec + 单测代码 + 仓库。
- **输出**：实现代码（分支 + commit + PR）。
- **角色**：所有 loop 回环（L2/L3）都回到这里。
- **异常**：连续 3 次修不好 → 升级请人。

### 7.6 单元测试
- **目的**：验证实现代码符合 spec（通过单测）。
- **执行者**：系统（自动运行）。
- **输入**：单测代码 + 实现代码。
- **输出**：测试报告（通过/失败 + 详情）。
- **状态流转**：通过 → 进入代码审核；失败 → **L2 回 Coder Agent**。

### 7.7 代码审核（Reviewer Agent + 人）—— Gate
- **目的**：审核代码质量与正确性。
- **执行者**：Reviewer Agent（AI 预审）+ 人（最终批准）。**两层。**
- **输入**：PR + 测试报告。
- **输出**：Reviewer 审核意见 + 人的批准/打回。
- **状态流转**：Reviewer 预审 → 人最终批准 → 进入部署；任一层不过 → **L3 回 Coder Agent**。
- **人介入**：最终批准（Gate）。

### 7.8 部署
- **目的**：交付上线。
- **执行者**：系统（PR 合并触发）。
- **输入**：已批准的 PR。
- **输出**：部署/合并完成。
- **状态流转**：Delivery 完成。

## 8. 端到端用户旅程

> 一个 FDE 工程师小王，从提需求到上线的完整故事。

1. **提需求**：小王在 infera 写「给登录页加忘记密码功能」。一条 Delivery 创建。
2. **spec 澄清（L1）**：Spec Agent 读需求 + 仓库，追问「走邮箱重置还是短信？邮件模板有吗？」。小王答「邮箱重置，用现有模板」。Spec Agent 产出 spec（含验收标准）。
3. **spec 审批**：小王看 spec，确认无误，点批准。spec 成为唯一信任源。
4. **生成测试（TDD）**：Test Agent 从 spec 生成测试用例（如「提交已注册邮箱→发重置邮件」「未注册邮箱→不发送但不提示不存在」），并写成可执行单测。
5. **写代码**：Coder Agent 写实现，开 PR。
6. **跑单测**：系统跑单测。第 1 次有 2 个用例失败 → **L2 回 Coder Agent**。Coder Agent 看失败详情，改代码，重跑 → 全过。
7. **代码审核**：Reviewer Agent 预审，给出意见（「密码重置 token 过期时间建议可配置」）。小王看 AI 意见，觉得有一条要改 → 打回 → **L3 回 Coder Agent**。Coder Agent 改完，重跑单测过，再审。小王批准。
8. **部署**：PR 合并，触发部署。Delivery 完成。

**全程**：每一步、每次 loop 迭代、每个 Agent 动作、每个人的审核，都记在 Delivery 时间线上，实时可见。小王中间几乎没动手——只在澄清、spec 审批、代码最终批准时介入。

## 9. 角色边界

### 9.1 人做什么
- 提需求、参与 spec 澄清（**方向**）
- spec 审批、代码审核最终批准（**审核 Gate**）
- loop 卡住（连续 3 次不过）时被升级请人（**兜底**）
- （v2）某一步想自己来时，接管那个 stage（自带 codex）

### 9.2 Agent 做什么
- **Spec Agent**：澄清需求、写 spec
- **Test Agent**：生成测试用例 + 单测代码
- **Coder Agent**：写实现代码、所有 loop 内的修复
- **Reviewer Agent**：代码预审

### 9.3 系统做什么
- 按 stage 顺序调度专职 Agent（静态编排）
- 自动运行单元测试
- 触发 loop 回环（单测/审核不过 → 叫 Coder Agent）
- 卡住检测与升级请人
- PR 合并触发部署
- Delivery 时间线记录与实时推送

## 10. 与参考产品的差异（自包含）

> 本节自包含解释，不假设读者了解这些产品。

### 10.1 vs 传统项目管理工具（Jira / Linear 类）
这类工具是**人驱动**的任务与项目管理：人建任务、人改状态、人推进。AI 是辅助。
- 它们**不跑代码**；infera 的 Agent 真的写代码、跑测试、开 PR。
- 它们是**看板/列表**为主；infera 是**交付流水线 + loop**。
- 它们以**人**为执行主体；infera 以 **Agent** 为执行主体，人退到审核。
- infera 借鉴它们的是：spec 文化（先写 spec 再动手）、PR 闭环、强观点的流程设计。

### 10.2 vs 单机 AI 编码工具（Claude Code / Codex 单独使用）
这类工具是**一个 Agent 一个终端窗口**：会话关了就忘，上下文散落，没有流程。
- 它们是**单 Agent 单点作业**；infera 是**多专职 Agent 接力**。
- 它们没有**交付流程**；infera 有 spec/测试/审核/部署闭环。
- 它们**不留痕**；infera 全程记录在 Delivery 时间线。
- infera 底层就用这类工具（Claude Code）作为 Agent 的执行引擎，但在上面加了流程、协作、多 Agent、留痕。

### 10.3 vs Agent 协作平台（外部任务源类）
这类平台把 AI Agent 作为团队里的"队友"，像派活给同事一样派给 Agent，强调 Agent 是一等协作者、本地运行时、可自部署。
- infera 借鉴其核心理念（Agent 主体、多 Agent、留痕、运行时抽象、触发机制），但**全自研**，专注 FDE 的**代码交付闭环**。
- 它们以 **issue 看板** 为中心；infera 以**交付流水线 + loop engineering** 为中心——这是 infera 的差异化。
- 它们默认**本地运行时**；infera MVP 默认**云端沙箱**执行。
- infera 额外内建了 **SDD + TDD**（spec 唯一信任源、测试从 spec 生成）和**多专职 Agent 按 stage 分工**。

### 10.4 infera 的独特位置
> infera = **面向 FDE 代码交付的、多专职 Agent 主导的、loop engineering 的交付流水线**。

既不是项目管理工具（不跑代码），也不是单机 Agent（无流程），也不是通用 Agent 协作平台（无交付闭环方法论）。它把"交付"做成一条质量内建、Agent 主导、人审核的闭环流水线。

## 11. MVP 范围

### 11.1 MVP 目标
验证「提一句需求 → 得到一个测过、审过、可部署的 PR」这条最短闭环，且 loop 能自治迭代、全程留痕。

### 11.2 ✅ 做

| 模块 | MVP 做到 |
|---|---|
| **Delivery** | 一个需求 = 一次 Delivery |
| **静态 Pipeline** | 内置固定模板（见第 7 节），不可自定义 |
| **4 个专职 Agent** | Spec / Test / Coder / Reviewer，各内置默认配置 |
| **系统静态调度** | 按 stage 顺序调度 Agent，loop 回环硬编码 |
| **TDD + SDD** | spec 审批后，Test Agent 从 spec 生成用例与单测 |
| **两个 Gate** | spec 审批（人）；代码审核 = Reviewer Agent 预审 + 人最终批准 |
| **loop** | 单测/审核不过 → 回 Coder Agent；连续 3 次不过 → 升级请人 |
| **Delivery 时间线** | 全程留痕 + WebSocket 实时推送 |
| **仓库集成** | GitHub（PR 闭环） |
| **Agent 引擎** | Claude Code，云端沙箱执行 |

### 11.3 ❌ 不做（延后）

| 不做 | 放到 |
|---|---|
| 多租户 / 计费 / onboarding | 已确认延后 |
| Pipeline 模板自定义 / 可视化编排 | v2 |
| 每个 stage 自动化挡位可配 | v2 |
| 自带 codex 的 per-stage 接管 | v2 |
| 多 Agent 引擎支持（MVP 只 Claude Code） | v2 |
| Agent 自定义管理（MVP 只内置 4 个） | v2 |
| Supervisor Agent（自主调度） | v3 |
| Agent 间协作（squad / escalation） | v3 |
| Insights / 分析 | v2 |
| 客户实体 / 客户请求 | v2 |
| 桌面端 / 移动端 | MVP 只 Web |
| 半动态 / 自主编排 | v4+ |

> **边界说明**：多专职 Worker Agent（每 stage 一个，系统静态调度）是 **MVP**；只有 Supervisor 自主调度 + Agent 间互相协作（squad）才是 v3。前者是静态编排（系统控制流），后者是 Agent 自主控制流。

### 11.4 MVP 成功标准
- 一个 FDE 提一句话需求，能在最少人工介入（仅 spec 审批 + 代码审核）下，得到一个**通过单元测试、经审核、可部署**的 PR。
- loop 能自治迭代（单测/审核不过自动回 Coder Agent），并在卡住时升级请人，不无限重试。
- 全程在 Delivery 时间线留痕，可回溯每一步决策与改动。

## 12. 演进路线

| 版本 | 重点 |
|---|---|
| **v1（MVP）** | 静态模板 + 4 专职 Worker Agent + 系统静态调度 + 硬编码 loop |
| **v2** | 模板可自定义 + 挡位可配 + 自带 codex 接管 + Agent 自定义管理 + 多引擎 + Insights |
| **v3** | Supervisor Agent 自主调度 + Agent 间协作（squad/escalation）+ 半动态编排 |
| **v4+** | Agent 自主编排 |

脚手架（pipeline）越来越松，Agent 的自主权越来越大——但 Agent 主导的核心地位从 v1 就立住。

## 13. 关键决策记录（带 rationale）

| # | 决策 | 选择 | 为什么 |
|---|---|---|---|
| 1 | FDE 交付物 | 代码/功能，Agent 是主力 | FDE 本质是工程师，交付代码；Agent 直接写代码、开 PR 价值最大 |
| 2 | 与参考产品关系 | 全自研 | 架构自主、可控；代价是周期长，所以 MVP 要极度聚焦 |
| 3 | MVP 北极星 | 「需求→PR」全自动闭环 | 最短、最高频、价值最集中的闭环 |
| 4 | 执行架构 | 执行可插拔，流程是领地 | 不绑死 Agent；交付物必回流流程，保住平台收口价值 |
| 5 | 平台主体 | Agent 主导 | 押注"未来一定是 Agent 主导"，架构从第一天起按此设计 |
| 6 | MVP 编排 | 静态模板 | 当下 Agent 不能靠谱自主编排；静态先行，自主演进 |
| 7 | 服务对象 | 内部单租户 | 先验证核心闭环，不做多租户/计费 |
| 8 | Agent 引擎 | Claude Code | 用户指定；MVP 单引擎 |
| 9 | 仓库 | GitHub | 用户指定；生态最熟 |
| 10 | 后端语言 | Go | 用户指定；并发/调度/Agent 进程管理强 |
| 11 | 流程形态 | loop engineering | 交付本质是迭代闭环，不是单向流水线 |
| 12 | spec 定位 | 唯一信任源，SDD+TDD | spec 是契约，测试 = 可执行的 spec，质量内建 |
| 13 | 回环规则 | 所有验证不过 → Coder Agent | 统一修复入口，简单可控 |
| 14 | Agent 架构 | 多专职 Agent（每 stage 一个） | 专职 Agent 针对性强，优于通用 Agent |
| 15 | 控制层 | MVP 系统调度，Supervisor 放 v3 | 静态编排先行，自主控制演进 |
| 16 | 代码审核 | Reviewer 预审 + 人最终批准 | AI 提效 + 人把关质量 |
| 17 | loop 边界 | 连续 3 次不过升级 | 防死循环，保留人兜底 |
| 18 | 人介入 gate | spec 审批 + 代码审核最终批准；过 = 部署 | 人只把握方向与质量的关键节点 |

## 14. 开放问题（待产品/工程明确）

1. **FDE 的精确定义**：是否等同 Palantir 式前沿部署工程师？团队规模？交付给内部产品还是外部客户？（影响后续 v2 的客户实体设计）
2. **4 个专职 Agent 的配置项**：指令 / 模型 / 技能 / 权限的最小集——MVP 先内置默认配置。
3. **代码同步与凭据**：GitHub 仓库如何同步进云端沙箱、凭据如何安全注入。
4. **测试范围与语言适配**：仓库已有 CI 还是 infera 自跑？用例/单测代码生成如何适配不同语言/框架。
5. **Reviewer 预审与人批准的交互**：人看到 AI 审核意见后如何批准/打回，UI 形态。
6. **通知通道**：spec 审批 / review 通知——MVP 先站内 + 邮件。
7. **loop 成本控制**：单条 Delivery 的 token/时长上限，避免无限消耗。
8. **部署的具体含义**：MVP 先简化为"PR 合并即触发部署"，真实 CD 形态待定。
