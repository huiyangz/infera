## 1. Multica 是什么（外部事实）

开源（Apache 2.0，约 8.6K stars）、self-host 的"人类 + AI Agent 团队项目管理平台"：Go 后端 + PostgreSQL 17 + WebSocket 实时推送；部署形态 Docker Compose / 单二进制 / K8s（单二进制成熟度一般，#1104 有反馈，优先 Docker Compose）。核心设计：**代码不经过服务器**——平台只协调任务状态、广播事件；执行全部发生在本机（或自有云）daemon 上，daemon 用 CLI 自身凭据调用已安装的 coding 工具。

### 1.1 数据模型：Issue 与 Task 分离

- **Issue**：目标、讨论、assignee、终态。
- **Task**：一次 agent 运行记录。同一 Issue 换 agent 或失败重跑，每次产生新 Task，历史不覆盖。
- Task 绑定其 runtime（机器），不迁移；runtime 离线时已入队 task 排队等待恢复，触发时已知离线则直接拒绝创建。

### 1.2 派发机制

- **agent 就是 assignee**，与人类成员同一下拉框。触发：assign/改派、状态变更、评论 @、聊天消息、Autopilot 调度、外部 webhook。
- 指派给**人类**只改 assignee，不触发任何 AI；**backlog 状态的 issue 被 assign 也不触发 run**。
- **Autopilot** = Runbook + assignee（agent 或 squad）+ 多个 trigger，有 create-issue / run-only 两种模式；这是它"自动准入"的原生形态。

### 1.3 执行：runtime/daemon

- daemon 自动检测 PATH 上已安装的 agent CLI（Claude Code、Codex、Cursor、Copilot、Kimi、Qwen、Grok 等 22+ 种），为每个注册 runtime；Multica 不自带模型。
- daemon 经 WebSocket 连服务器（默认 `ws://…:8080/ws`）；心跳 15s、轮询 30s、默认最大并发 20 task；工作区默认 `~/multica_workspaces`；每任务独立工作空间。

### 1.4 重试与阻塞状态机

- Task 生命周期：`deferred / queued / dispatched / waiting_local_directory / running / completed / failed / cancelled`。
- **无独立 blocked 状态**：阻塞表现为 `agent_blocked` 失败原因，agent 在 issue 评论中请求补充信息。
- 自动重试只覆盖瞬态故障（默认 2 次，网络中断最多 3 次）；agent 自身报错（配额、凭证、配置、模型失败）不自动重试。手动 retry 复用原 agent、保留已写文件、尽量恢复原会话。
- 超时：queued 2 小时无人认领即失败；dispatched 5 分钟；running 无上限但靠心跳判活（约 3 分钟判离线）。

### 1.5 人工门

- **没有原生的 plan/spec 审批 gate**。唯一人工控制点：工作落 PR review 而非直接进 main（"You decide what ships"），由人决定合并。
- issue 的 in_progress / in_review 状态迁移**由 agent 自己判断执行**，非服务端工作流控制器（discussion #815 确认为设计选择）；task 完成本身不改 issue 状态。

### 1.6 证据留存

- 带时间戳的 run 日志（可回放每个工具调用/命令/错误）；token 成本按 agent、按 issue 记账；intent / run / 决策 / diff 绑定同一 issue。
- **无**测试结果、截图、录屏等结构化证据的原生绑定（附件/评论可以承载，见 §2 内部实践）。

### 1.7 终态与 Git 集成：原生"合并成功才 Done"

Issue 置 Done 需同时满足：① 至少一个**已合并**的关联 PR 在正文使用紧跟标识符的 close intent（如 `Closes MUL-123`）；② 无其他关联 PR 处于 Open/Draft；③ issue 尚未终态。PR 关闭未合并不算完成；只在分支名/标题写标识符只建立链接不触发完成。GitHub 集成走 GitHub App，PR 卡片原生展示 CI 结果与 mergeability。

注意事项：
- 曾有 daemon 把"会话结束"误判为完成、绕过合并规则的 bug（#3187，2026-06 由 PR #4257 修复）——自部署需 pin 修复后版本。
- GitHub↔Multica **无双向镜像同步**（#1120 请求过，无实现关闭）；已关联 PR 的状态快照与 merge-to-Done 联动正常。

### 1.8 Squad 机制：issue 内的"负责 agent"原生形态（2026-08-20 补充调研）

分配给 **squad** 时不是全员齐跑，而是 **leader 先跑**：Multica 只为 leader 入队一个 task，向其系统提示注入 Squad Operating Protocol（**硬编码规则集，不可编辑**）、Roster 和 Instructions（可配，`multica squad update --instructions`）。Leader 读上下文、发一条 delegation comment（用 roster 里的精确 mention markdown @ 选中的成员）→ 每个被 @ 成员起一个新 task；**leader 只路由不实现**，且每轮须把 evaluation 写入 issue 活动时间线（`multica squad activity`）。

**反馈路由规则（谁被唤醒）——这是"反馈是否经过负责 agent"的直接答案：**

| 评论来源 | 触发 leader？ |
|---|---|
| 非成员（人类/外部 agent）评论 | **是**——用户追问会唤醒 leader |
| 成员不带 @ 的进度更新/结果反馈 | **是**——leader re-evaluate 是否需要下一步 |
| 显式 @ 某个 agent/成员/squad/@all | **否**——@ 是明确路由信号，"leader gets out of the way" |
| leader 自己的评论 | 否（防循环 guard） |
| 只含 issue 交叉引用的评论 | 是 |

- 成员完成、sub-issue 或 stage barrier 关闭时 leader 被 **re-trigger**：可派下一步、升级、把父 issue 移 `in_review`、或沉默。这就是〔录音143337〕§十二"Lead Agent 汇总进度再分配"设想的原生近似。
- 防重：leader 在该 issue 已有 queued/dispatched task 时，新触发不重复入队。
- 单 agent 直派（非 squad）时**没有这层**：反馈评论触发的是当前 assignee（实现 agent），想走"负责 agent"须显式 @（不改 ownership，assignee 有约 5 分钟延迟回退 run，被 @ 者及时回应则取消）或改派（改 ownership、起新 run）。
- 评论触发细节（两种形态通用）：run 进行中的后续评论**不打断**，等当前 run 结束合并为一次 follow-up run；`/note` 开头不触发任何 agent；`@all` 通知全员且关闭本条评论的自动触发。
- 边界：squad 只解决**单个 issue 内**的协调；跨 issue/多阶段流水线编排仍无原生物（#1943 仍 open）。

### 1.9 对话集成

- **原生 Slack bot**（Socket Mode 免公网回调）：DM/频道 @ 触发、`/issue` 命令创建 issue、附件传给 agent、一次性绑定链接；限制：一个 Slack app 只映射一个 agent。
- **无飞书/Lark 集成**。飞书侧须自建 bridge（改源码或 sidecar，见 §4）。

## 2. 内部实际用法（〔录音143337〕）

### 2.1 链路形态

问题反馈群（人工触发建卡）→ 任务卡（描述/截图/上下文）→ 受理与方案 Agent 澄清（要解决什么/是否该做/方案/验收标准）→ **人在任务卡评论中确认方案** → 研发 Agent 建代码修改任务（最新代码上建分支/改码/提交）→ 触发 E2E → **测试结果/截图/视频回写任务卡** → 人确认通过与否；不通过则继续修改重验。

### 2.2 Agent 组织

- 早期三 Agent（受理 / 交互分析 / 研发）→ 因受理与交互分析重叠，**合并为两个**：通用"受理与方案处理 Agent"（统一入口 + 意图路由）+ 研发执行 Agent。合并后速度明显提升。
- 路由不能只靠模型临时判断，需要**人员地图**（什么问题找产品/UI/研发/审批人）可被系统查询。

### 2.3 确定性工具封装

建分支、取最新代码、建 Commit、建 MR、打包/发布构建产物、触发测试、回写任务卡状态——封装为确定性工具，避免 Agent 每次自行探索命令（慢且易错）。这与 Multica"平台管状态、本机 CLI 执行"的分工互补：工具封装在内部系统层完成。

### 2.4 效果与痛点

- 解决率：从较低水平提升到约 60%，目标 80%（录音自标注数字有识别不确定性，量级可信）。
- 最大痛点：**报告/问题数量过多**——需要聚合分级（总数/高优先级/必须处理/建议/提示），摘要先行、详情折叠；"围绕人的信息消费能力设计"。
- **编排缺口**（§十二，与外部事实互证）："外层还没有非常完善的统一编排平台"；需要状态变化触发固定脚本、完成后自动通知负责人、按状态分配下一执行者、异常时停止并保留现场；提出 Lead Agent + Hook 的"团队"协作模型设想。
- 测试环境：倾向用发布/构建基线分支预置依赖镜像，避免每次重装环境。
- 边界共识：**不自动合并**，人负责最终合并与责任确认；问题无法解决时停在明确状态并说明缺什么，不反复尝试或默默失败。
- 灰度策略：Bugfix 场景稳定后再逐步接小需求与更完整 SDLC；其他产品（如 DeepMap）按领域复用通用能力（受理/路由/方案确认/修改/E2E/回写），带走的资产是角色定义、领域 Skill、MCP 工具、任务状态、审批与介入规则。

## 4. 对蓝图的修订建议与决策点

1. **审批动作发生地（新决策点，源自现状对照）**：方案审批现状发生在 Multica 任务卡评论；蓝图迁到飞书方案卡。若飞书批准后仍需写回 Multica（评论/状态），存在两个审批入口的风险——建议拍板"唯一审批入口 + 另一侧只读投影"，与蓝图"飞书不维护第二套可写执行状态"原则对齐（审批是决策动作而非状态，但动作落库路径必须单向）。
2. **证据挂载点**：E2E 截图/视频现状回写 Multica 任务卡；蓝图 Gate 2 卡片展示证据 → 按"读 Multica 投影到飞书"实现即可，不必搬运；需定义投影的字段协议（结果摘要/截图链接/候选版本号）。
3. **通知闭环（蓝图 §3.6 TODO）与编排层合并建设**：Multica 无跨 issue 的原生 hook/工作流（#1943 open），录音 §十二 的状态 Hook/Lead Agent 需求同源；但 **issue 内的 Lead Agent 协调已有原生近似（squad，§1.8）**，建议先建一个两成员 squad（受理+方案 / 研发）实测录音设想，再决定是否自建。跨 issue 编排可选路径：(a) sidecar 订阅 Multica 事件（WebSocket/API）→ 飞书卡片 + 固定脚本；(b) 改 Multica 源码（Apache 2.0）；(c) 用 infera 11 阶段编排引擎承担外层编排，Multica 退为执行/状态底座——与〔05-MVP〕"Multica Issue 角色由 infera Delivery+Demand 分层承担"的既有决策正面相关，需一次选型对齐。
4. **候选池实现**：Multica backlog 状态天然承载"候选不触发执行"；但蓝图候选池在飞书项目侧——飞书项目 ↔ Multica Issue 的创建/关联 bridge 需自建（参照 GitHub 无镜像同步的前车之鉴 #1120，勿假设双向同步存在）。
5. **Gate 2 卡片设计约束（新增）**：按录音 §十/§十一 的阅读负担教训，交付验收卡必须摘要 + 分级（必须处理/建议/提示）+ 折叠详情，先给"最需要处理的几件事"。
6. **部署与版本**：self-host 优先 Docker Compose；pin #4257（修 #3187 自动 complete bug）之后的版本。
