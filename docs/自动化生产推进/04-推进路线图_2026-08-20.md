## 一、路线图总览

### 一.1 总目标与总口径

1. **总目标**：把可行域——"Bugfix 型单交付闭环（人工门禁版）"（〔03-§五.1〕）——从"两侧已建成、中间可演示"推到"真产品真仓库常态化运行"，并以平台侧指标支撑业务硬指标（修复批入率 50%→80%，〔01-§1.5〕）。
2. **总口径**：发布口径为**每日候选版本 + 人工放行**（〔03-§六.D3-A〕）；合并与发布节奏由人工 Gate 决定，"每日发布（全自动）"为否决项（〔03-§四.1〕），任何阶段不得引入。
3. **形态口径**：infera 只做**编排 + 门禁治理 + 证据**这一层（〔03-§四.5〕，D2-A）；执行绑小鱼儿、审查绑 infReview、准入/验收按三 Gate 模式，不自建执行/审查/模型适配能力。

### 一.2 与 0818 Phase 0-6 的重排映射

重排原则（依 03 结论）：①**可复用内部现成能力的环节前置**——小鱼儿执行段（已落地，〔01-§1.2〕）→ 阶段二集成真跑；infReview 审查段（已落地，〔01-§2.1〕）→ 阶段一预研、阶段二绑定；飞书三 Gate 模式（蓝本，〔01-§3.9〕）→ 阶段二验收门、阶段三人工准入。②**纯新建环节后置或转跟踪**——Signal 聚合、policy 载体只保留最小版（阶段三）；需求控制面主体、发布物料/部署、系统化知识库、无人值守循环全部转入前提跟踪（阶段四，无时点）。

## 二、阶段划分

> 每阶段含：目标／范围与交付物／验收标准（可度量）／依赖与资源／退出或止损线／依据。凡条件项，口径与〔03-§三〕所列条件一一对应。

### 二.1 阶段一：决策拍板 + 执行内核补强 + Bugfix 模板化

1. **目标**：把"能演示"的执行内核补到"可信"——消除假绿与盲区（TEST_CMD、P2-P5、usage、PR 状态），确立 Bugfix 为第一类交付模板，完成全部前置决策拍板。本阶段全部工作在 infera 自身工程范围内，无外部拍板依赖（〔03-§五.2〕）。
2. **范围与交付物**（= 子集甲全量）：
   1. **决策拍板包**：D1/D2/D3/D7/D10 五项拍板并落版本化决策记录（候选与推荐已备好，〔03-§六〕）；D9 禁区清单出草案（正式版留阶段三前）。
   2. **runner 集成缺口修复 P2-P5**（〔02-§四.3〕）：http 可配鉴权 header（P2）、docker 透传环境变量（P3）、cli 失败落 agent 输出（P4）、http 超时可配（P5）。
   3. **TEST_CMD 语义真实化**（〔03-§三.13.1〕条件①）：未配置真实命令不得伪装通过（显式 blocked/失败，非默认 `true` 假绿，〔02-§四.1.2〕）。
   4. **usage 计量入 Agent 契约**（〔03-§三.7〕条件①）：Agent 契约扩展 usage 回传；StageRun 记时间 + usage 双口径（〔02-§三〕）。
   5. **PR/CI 状态跟踪**（〔03-§五.2.1〕，D7-A 口径：GitHub + CI 状态跟踪、止于合并）：PR 创建失败可阻断可重试；CI/check 状态可见；合并动作留人工。
   6. **Bugfix 交付模板**（〔03-§五.2.2〕）：以"问题描述→复现→修复→验证"为 infera 第一类交付模板；复现契约与"人只在语义/风险边界出现"参考〔01-§4.7〕〔01-§4.9〕。
   7. **infReview 集成预研**（〔03-§五.2.3〕）：报告经代码托管平台原生接口回读（〔01-§2.7〕，无需新 API）spike + findings 映射到 `infera-findings` 契约（〔02-§二.4〕）方案。
   8. **人工复盘机制**（〔03-§五.2.4〕降级形态）：双周复盘会 + 沉淀模板（沉淀去向：规则/Style/Prompt，小鱼儿式做法〔01-§1.7〕）。
3. **验收标准**：
   1. D1/D2/D3/D7/D10 拍板记录 5/5 落文档，含候选选择与理由。
   2. R11 问题清单 P2-P5 复核全部关闭（对照〔02-§四.3〕逐条）。
   3. 假绿率 = 0：dogfood 仓库（infera 自身）全部新交付 TEST_CMD 为真实命令；未配置即显式失败（〔03-§三.13.1〕口径）。
   4. usage 回传覆盖率 ≥95%（cli/http 两形态；docker 视 P3 修复后补测）。
   5. infera 自身仓库 ≥3 个真实 Bugfix 交付按模板走完 spec→PR（agent 可为占位/本机通道，验证的是模板与内核，不是模型质量）。
   6. infReview 回读 spike 报告 1 份：真实报告可取回、字段映射表完成。
   7. 复盘机制运行 ≥2 次，沉淀 ≥5 条且至少 1 条进入 spec/review prompt 模板。
4. **依赖与资源**：infera 推进方 2-3 人（工程）；决策拍板需产品/工程负责人到会（D1/D2/D10）；无外部系统依赖、无接入信息依赖。
5. **退出或止损线**：
   1. **拍板止损**：D1/D2/D10 若 4 周内未拍板 → 全线暂停（后续每阶段都以它们为口径前提；〔03-§六〕"推进前必须拍板"）；D3/D7 可宽限至阶段一末，逾期则阶段二验收门/PR 跟踪按现状口径冻结范围。
   2. **计量止损**：若内部模型服务确无可回传 usage（〔01-§2.12〕成本统计不准的现实），usage 条目转"时间口径先行 + usage 跟踪"，阶段三粗估降级为时间统计口径，不阻塞其余条目（〔03-§三.7〕条件②的退化）。
   3. **内核止损**：若 3 例模板交付中 >1 例因引擎缺陷（非 agent 质量）中断且不可恢复 → 暂停模板放量，先修内核可靠性（重启点火/事件留痕，〔02-§二.7〕）。
6. **依据**：〔03-§五.2.1-4〕〔03-§三.7〕〔03-§三.8.1〕〔03-§三.10.1/3〕〔03-§三.13.1〕〔03-§六.D1/D2/D3/D7/D9/D10〕。

### 二.2 阶段二：Bugfix 全链真跑 + 验收门 + PR/CI 跟踪

1. **目标**：真产品（小鱼儿执行段、infReview 审查段）+ 真仓库跑通 Bugfix 单交付闭环全链，落地 Gate 2 形态验收门与证据包，完成定义推进到"PR 创建 + 状态跟踪 + 人工合并"（D4-A）。
2. **范围与交付物**（= 乙.1 + 乙.3 + 甲.1 的 PR/CI 落地）：
   1. **三产品绑定真跑**（〔03-§五.3.1〕）：小鱼儿绑执行节点、infReview 绑 code_review/双道审查节点（经 http + 鉴权通道，阶段一 P2 修复后）、真仓库真 Bugfix 输入。
   2. **验收门（Gate 2 形态）**（〔03-§三.11.1〕）：验收证据包绑定固定代码版本，代码变更则旧证据与旧批准失效（蓝本〔01-§3.10.1〕）；验收失败回流同一交付重修（〔01-§3.9.7〕）。
   3. **版本总结**：由既有 delivery/task 状态与 findings 数据派生"高优已解决/未解决"版本级总结（〔03-§三.11.1〕；〔02-§二.1/二.4〕）。
   4. **每日候选版本口径落地**（D3-A）：按日聚集候选交付与证据包，合并/发布由人工 Gate 决定——只做聚集与呈现，不做发布物料/部署（后者属丙，〔03-§三.11.2〕）。
   5. **PR/CI 跟踪生效**：PR 创建成功率、CI/check 状态、人工合并后交付终态回写（D4-A：完成=PR 创建+跟踪，合并属人工段）。
3. **验收标准**：
   1. 真产品 agent 全链（intake→PR）完成 ≥5 例真实 Bugfix；每例时间线/产物/门禁记录完整。
   2. 全链到达率 ≥60%（≥5 例中 ≥3 例到 PR；未到达例均有结构化阻塞原因——复现失败/缺权限/需决策，参考〔01-§4.7.3〕）。
   3. 证据包绑定率 100%（每验收交付证据含 commit SHA；代码变更后旧证据标记失效）。
   4. PR 创建成功率 ≥90%（dogfood + 目标仓库）；PR/CI 状态可见率 100%。
   5. 每日候选版本聚集视图上线且连续运行 ≥2 周；期间 0 例自动合并（红线，〔03-§四.1〕）。
   6. 单交付全链人工介入 ≤4 门 × 1 次（spec/design/tasks/code_review 基线；超出即记复盘项）。
4. **依赖与资源**：**三产品接入信息（唯一外部前提，〔02-§四.3〕B1；〔03-§三.9.1〕条件①）**——地址/命令/镜像/凭证；D4/D3 拍板（阶段一完成）；小鱼儿/infReview 侧各 1 名对接人；目标业务仓库的测试命令与测试资产（〔01-§1.9〕，第一版验收目标已明确）。
5. **退出或止损线**：
   1. **接入信息止损**：接入信息逾期 6 周未到位 → 真跑降级为 dogfood 真仓库 + 真 CLI agent（本机通道，〔02-§二.6〕）跑同口径验收，接入信息转为上报项每月跟进；验收门/PR 跟踪/版本聚集不依赖接入信息，照常推进。
   2. **真跑止损**：真跑 10 例中 0 例到 PR → 判定集成形态不成立，回退阶段一复查（runner 契约/超时/上下文组装），不得带病进阶段三。
   3. **质量止损**：真跑交付投人工合并后，人工合并拒绝率（=修复批入率的对偶）连续 2 周 >60% → 暂停放量，先修测试真实化与审查绑定质量（对照〔01-§1.5〕50% 基线）。
6. **依据**：〔03-§五.3.1/3〕〔03-§三.9.1〕〔03-§三.10.1/2/3〕〔03-§三.11.1〕〔03-§三.13〕〔03-§六.D3-A/D4-A〕。

### 二.3 阶段三：信号入口 + 治理最小版

1. **目标**：打开受控的需求入口——首个内部信号源自动入档粗库，人工准入（Gate 0 模式）+ 优先级人工签发（D6-A）；建成 policy 载体 v1（禁区清单）并在其上试低风险白名单自动放行最小版；粗估上线。**不含**分类体系、高质量需求库、语义聚类、AI 优先级、完整置信分流（均属丙，〔03-§五.4.1〕）。
2. **范围与交付物**（= 乙.2 + 乙.4 + 乙.5 + 确定性去重）：
   1. **首个信号源：infera 自身交付的 CI/E2E 失败回流**（D5-A；〔03-§三.1.1〕）：失败即 Signal 入档，复用小鱼儿已接信号形态而非重采（〔03-§三.1.1〕条件③）。
   2. **粗库（原始 Signal 存档）**（〔03-§三.3.1〕）：不可变存储 + 来源追踪（infera 新建 Signal 聚合最小版，〔02-§五.3.1〕零起步，只做存档不做分层）。
   3. **确定性去重**（〔03-§三.4.1〕）：多层确定性规则（蓝本〔01-§4.9.6〕），重复信号不重复建交付；小鱼儿去重机制仍列"待确认"观察项（〔01-§1.6〕），不作依赖。
   4. **人工准入 + 优先级签发降级形态**（〔03-§三.5.2〕〔03-§三.6.1〕）：Gate 0 模式人工卡片准入（蓝本〔01-§3.9〕），签发主体=交付负责人（D6 签发 A）；产品优先级上下文以人工输入注入，不新建聚合（〔03-§三.5.2〕条件②）。
   5. **policy 载体 v1 + 禁区清单**（D9-A+C）：版本化载体承载禁区清单（鉴权/计费/迁移/基础设施/安全策略永不过自动门）与放行策略；输入/结果/版本/人工覆盖留痕（载体现状为零，〔02-§六〕结语）。
   6. **低风险白名单自动放行最小版**（〔03-§五.3.4〕）：仅限"非禁区 + 低风险 + 证据完整"子集的**环节内**自动放行（如单任务重跑、非门禁环节续跑），4 道人工门本身不自动放行；完整置信度分流仍属丙（〔03-§五.3.4〕明示）。
   7. **待实现需求粗估**（〔03-§三.7〕）：以 StageRun 时间 + usage 统计（阶段一产出）出同类 Bugfix 成本区间（P50/P90），估算口径先定义后建设（〔03-§四.3〕"先定义、后建设、再放量"）。
3. **验收标准**：
   1. 信号自动入档率 ≥90%（infera 自身 CI/E2E 失败 24h 内成档 Signal）；粗库条目 100% 带来源与时间戳。
   2. 重复建交付率 = 0（同一信号源同一失败确定性去重命中后不再建新交付）。
   3. 准入决策全部可追溯：每条 Signal 有准入人/时间/结论四态之一（受理/补信息/延拒/合并，蓝本〔01-§3.9.4〕）。
   4. policy 载体 v1 上线：禁区清单版本化、每次自动放行决策留策略版本与输入快照。
   5. 白名单自动放行：运行 ≥4 周、**错误放行事故 0 起**（红线）；自动放行占比可配置且有上限（首期 ≤20%）。
   6. 粗估报表：按类型/仓库出 P50/P90 成本区间，回填预测误差可见。
