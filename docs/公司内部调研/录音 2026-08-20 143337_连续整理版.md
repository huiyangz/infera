## 一、当前 Bugfix 产品的整体定位

**访谈人：** 这次主要想了解你们当前 Bugfix 产品的完整流程、Agent 如何协作、目前已经做到什么程度，以及后续计划。公司希望把多个产品能力串成一个更大的软件生产闭环，而 Bugfix 是其中比较容易落地、也能直接产生价值的一环。

目前的重点不是一开始就解决非常复杂的研发问题，而是先把线上问题的处理流程跑顺：从问题受理、信息补齐、方案制定、代码修改，到测试验证和最终确认，都尽量自动化。这样可以直接节省处理线上问题的时间，也能暴露开发和产品流程中的其他问题。

## 二、当前流程：从问题受理到验证闭环

**受访人：** 现在我们内部有一个产品 Bug 反馈群。用户或内部同学提出问题后，系统会先创建一张任务卡。目前任务卡的创建还需要人工触发。

任务卡中会包含问题描述、截图、相关现象以及其他上下文。受理 Agent 会基于这些信息，先判断问题是什么、需要解决什么，以及验收标准是什么。

这个阶段会有 AI 参与。AI 会把来自不同地方的信息聚合起来，整理成结构化内容，包括：

- 当前要解决的问题；
- 问题的背景和影响范围；
- 计划采用的方案；
- 完成后的验收标准。

这个过程类似于先把需求或 Issue 澄清清楚，再进入后续执行。用户需要确认方案是否正确。如果方案不对，可以直接在任务卡中指出问题；如果方案通过，流程才会进入代码修改阶段。

## 三、方案审批是关键的人机协作节点

早期流程的问题是：用户只要给出一点信息，Agent 就直接开始执行，导致最终效果很差。现在增加了澄清和方案审批环节。

只有在以下信息基本明确后，系统才会创建后续开发任务：

1. 到底要解决什么问题；
2. 这个问题是否真的需要处理；
3. 采用什么方案解决；
4. 最终通过什么标准验收。

如果信息不完整，Agent 不能直接往下执行，而是需要继续追问，或者把问题转交给产品、设计或研发负责人。这样可以避免 Agent 在目标尚未明确时直接改代码。

方案确认以后，后续协作主要通过任务卡评论完成。相关人员可以在卡片中补充意见、提出修改要求或确认方案，Agent 再根据这些反馈继续推进。

## 四、Agent 的拆分与合并

早期流程中有三个 Agent：

1. **受理 Agent**：负责接收问题、澄清目标，并做意图路由；
2. **交互分析 Agent**：负责分析问题并形成解决方案；
3. **研发 Agent**：负责修改代码、提交变更并推进验证。

后来发现，受理和交互分析之间存在较多重叠。受理 Agent 本身已经需要理解问题、确认目标、判断是否处理并决定路由；交互分析 Agent 又会重复做一部分分析工作。因此现在倾向于合并为两个主要 Agent：

- 一个更通用的“受理与方案处理 Agent”；
- 一个负责代码修改和研发执行的 Agent。

受理 Agent 不只负责 Bug，也可以处理其他类型的小需求。它更像一个统一入口，先理解用户意图，再把任务分发给后续能力。

## 五、受理 Agent 的路由能力

受理 Agent 需要承担两类判断：

- 这个问题要不要做；
- 如果要做，应该采用什么方案、交给谁处理。

它会根据问题类型把任务路由到不同能力，例如 Bug 修复、产品小需求、研发分析或其他专项 Agent。未来如果需要接入更多产品能力，也可以继续扩展路由表。

但路由不能只靠模型临时判断。为了让流程稳定，需要有清晰的人员地图和职责关系：什么问题找产品，什么问题找 UI，什么问题找研发，什么问题需要负责人审批，都应该能够被系统查询到。

当 Agent 发现信息不足时，也不能让任务卡住或盲目继续，而应根据人员地图主动找到对应的人补充信息。

## 六、代码修改和确定性工具封装

方案通过后，研发 Agent 会创建代码修改任务，并在对应仓库和分支上工作。当前系统会自动找到最新的代码版本，在此基础上创建分支、修改代码并提交变更。

一些原本需要 Agent 通过命令行自行探索的操作，被封装成了确定性的工具。例如：

- 创建分支；
- 获取最新代码；
- 创建 Commit；
- 创建 MR；
- 打包或发布构建产物；
- 触发测试；
- 回写任务卡状态。

之所以要封装这些工具，是因为如果完全依赖 Agent 自己探索命令，它可能先寻找命令帮助、再判断参数、再逐步执行，整个过程很慢，也容易出错。确定性强的步骤应该由系统或工具直接完成，把 Agent 的精力留给真正需要理解和决策的部分。

## 七、E2E 验证、截图和视频

代码修改完成后，如果问题具备可验证条件，系统会触发 E2E 测试。

E2E 测试需要预先定义测试脚本，明确要验证什么场景。测试服务执行脚本后，会把测试结果、截图和视频回写到任务卡中。这样用户不用自己安装环境或手工复现，大多数情况下直接查看截图和视频就能判断问题是否解决。

完整链路大致是：

1. 明确问题和验收标准；
2. 生成方案并获得确认；
3. 创建代码修改任务；
4. 在最新代码版本上完成修改；
5. 提交代码并触发 E2E；
6. 生成测试结果、截图和视频；
7. 由用户或负责人确认是否通过；
8. 如果不通过，继续修改并重新验证。

如果某些场景无法自动创建或准备测试环境，仍然需要人工补充环境；但常规场景会尽量由系统自动准备和执行。

## 八、测试环境的准备方式

当前 E2E 环境有一个现实问题：如果每次运行都从头安装依赖和准备环境，速度会比较慢。

一种改进方式是利用每次发布或构建产生的基线分支，提前制作好包含依赖的镜像。测试时直接拉取对应镜像，而不是每次重新安装全部依赖。这样既能保证环境与代码版本匹配，也能缩短验证时间。

环境准备是 E2E 能否真正用于日常 Bugfix 的关键。如果测试本身每次都需要很长时间，自动化流程就很难发挥价值。

## 九、人工介入的边界

代码修改完成后不应该直接自动合并。AI 可以负责分析、修改和验证，但最终的合并和责任确认仍然需要人参与。

原因包括：

- AI 可能理解错需求；
- 某些修改会影响其他功能；
- 不同团队对风险和发布标准的要求不同；
- 代码合并需要明确负责人；
- 线上问题的责任不能完全交给 Agent。

因此，自动化的合理边界是：让 Agent 完成大量分析、执行和验证工作，把人集中到方案审批、异常判断和最终合并这些关键节点上。

如果问题无法解决，Agent 应该把任务停在明确的状态，并说明需要什么信息，而不是反复尝试或默默失败。之后由受理 Agent 或负责人重新分派任务。

## 十、当前效果与主要问题

目前这套流程已经能够真实落地，并且相比早期三个 Agent 互相交接的方案，合并为两个 Agent 后速度明显提升。

录音中提到，解决率已经从较低水平提升到约 60%，后续目标是达到 80%。原始语音中的具体数字存在一定识别不确定性，但可以确认的核心意思是：当前已经具备可用效果，下一阶段重点是继续提升成功率和稳定性。

最大的现实问题是报告和问题数量太多。AI 可能会把大量潜在问题全部写出来，但用户没有时间逐条阅读。报告过长会导致：

- 用户不知道哪些问题最重要；
- 研发不愿意阅读完整报告；
- 低价值问题掩盖高风险问题；
- 看报告本身变成新的工作负担。

因此，产品不应该只追求发现更多问题，而应该优先告诉用户“最需要处理的几个问题”。详细分析可以折叠到后面，用户有需要时再展开。

## 十一、审查结果需要更强的聚合和分级

当前 Code Review 或问题分析结果中，部分内容质量不错，但数量太多。更好的呈现方式可能是先给出：

- 问题总数；
- 高优先级问题数；
- 必须处理的问题；
- 建议处理的问题；
- 可能只是提示、不影响合并的问题。

用户先看摘要和重点问题，只有对某一项有疑问时再点开详细报告。

这也是 AI 系统能否真正被使用的关键。AI 生成报告的成本可能不高，但人的阅读和判断成本很高，产品必须围绕人的信息消费能力来设计。

## 十二、平台编排与 Hook 机制

目前 Agent 之间的协作主要依靠 Multica 自己的任务卡和流程能力。外层还没有非常完善的统一编排平台。

如果完全依赖多个 Agent 自由交接，流程容易不稳定：一个 Agent 完成后，另一个 Agent 未必能正确接手；任务状态、上下文和责任边界也可能丢失。

因此，需要补充更工程化的状态和 Hook 机制：

- 状态发生变化时触发固定脚本；
- 任务完成后自动通知负责人或 Lead；
- 根据状态自动分配下一个执行者；
- 在异常时停止流程并保留现场；
- 用固定工具处理确定性步骤。

有人提出类似“团队”的协作模型：多个 Agent 组成一个小队，由 Lead Agent 汇总进度并分配下一项任务。每个 Agent 完成任务后，通过 Hook 向 Lead 汇报，再触发下一阶段。

这类机制比单纯让多个 Agent 自由对话更稳定，也更容易追踪责任。

## 十三、为什么当前不宜强行接入完整研发流程

公司层面希望把整个研发流程都接入 AI，但当前 Bugfix 链路仍在快速迭代。受访人认为，暂时不适合马上把所有需求、设计和开发流程都接进来。

原因是：

1. Bugfix 是边界相对清楚、已经能落地的场景；
2. 普通需求的前置澄清和产品判断更复杂；
3. 研发流程还需要更多稳定的工具和状态机制；
4. 过早接入大流程会放大 Agent 之间的不稳定；
5. 当前首先要把线上支持和实际价值跑通。

更现实的方向是，先把 Bugfix 做成一个稳定产品，再根据实际经验逐步接入小需求或其他研发环节。

## 十四、DeepMap 等产品的接入方式

如果其他产品也有大量反馈问题，可以复用这套 Bugfix 流程。基本方式是：产品作为入口，先受理并明确问题；之后由后续 Agent 分析、修改、测试和回写结果。

这类产品不一定要复制整套流程，而是可以复用其中的通用能力：

- 问题受理；
- 上下文获取；
- 任务路由；
- 方案确认；
- 代码修改；
- E2E 验证；
- 结果回写。

未来如果外层平台能把这些能力统一起来，不同产品只需要提供自己的领域 Skill、工具和知识即可。

## 十五、上下文获取与独立工作空间

当用户只提交一句话或一个简单问题时，Agent 需要主动补齐上下文，不能只依赖用户输入。

系统会通过预先配置的工具和 MCP 能力，查询代码、日志、任务卡、相关文件和历史信息，再把这些内容汇总到当前任务中。

每个任务通常拥有独立的工作空间或沙箱，用于保存本次任务拉取的代码、临时文件和执行结果。这样可以避免不同任务互相污染，也方便保存测试截图、视频和中间产物。

上下文过长时，系统还需要负责压缩和整理。Agent 不应该把所有原始信息无差别塞进上下文，而应保留与当前问题直接相关的内容。

## 十六、模型和工具的选择

讨论中提到，当前系统有自己的 CI、代码工具和任务能力，也可以考虑接入外部模型或代码 Agent。

一个实际判断是：如果只是普通的代码修改和测试，内部封装的工具链可能更稳定；如果需要复杂推理，则可以选择更强的模型。但无论使用什么模型，核心能力都需要通过自己的工具和 Skill 固定下来，避免每次让 Agent 自己探索相同流程。

未来如果要将这套能力迁移到其他产品，可以带过去的主要不是某一次对话，而是：

- Agent 的角色定义；
- 领域 Skill；
- MCP 工具；
- 任务状态；
- 代码和测试工具；
- 方案审批与人工介入规则。

## 十七、后续方向与结论

这次交流形成的主要结论是：当前 Bugfix 流程已经具备较强的落地价值，适合继续作为 AI 软件生产闭环的样板，但暂时不宜直接扩展成覆盖所有研发活动的大而全平台。

后续重点包括：

1. 继续提升 Bugfix 的问题解决率和执行稳定性，向 80% 目标推进。
2. 保持两个主要 Agent 的结构，减少多 Agent 之间的重复交接。
3. 完善问题澄清、方案审批和人工责任确认机制。
4. 优化报告聚合和分级，优先呈现少量高价值问题。
5. 完善 E2E 环境镜像和基线管理，减少重复安装依赖的时间。
6. 增加任务状态、Hook、Lead Agent 和固定脚本机制。
7. 明确人员地图，让 Agent 能在信息不足或需要审批时找到正确的人。
8. 把通用的受理、路由、修改、测试和回写能力沉淀为平台能力。
9. 让 DeepMap 等其他产品按领域复用这套闭环，而不是各自重复建设。
10. Bugfix 链路稳定后，再逐步探索小需求和更完整的 SDLC 流程。
