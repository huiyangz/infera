## 1. 结论摘要（一页）

1. **全闭环"技术上分段存在、系统上整段缺失"**。执行段证据在 V4 后更加完整：小鱼儿已具备"受理澄清 → 方案审批门 → 研发执行（确定性工具封装）→ E2E 验证（截图+视频留证）→ 人工合并"的全链实践，且与 infReview 的 CR 结果已在消费（质量不错但**数量太多**）；但执行前的需求质量控制面（分类、聚类、优先级、Spec 质量）和执行后的发布反馈控制面（部署、灰度、回滚），以及横向治理（平台归属、成本、协同）基本为零。〔V3〕的核心判断与此前〔03〕的判定互相印证：**瓶颈不是技术，是高质量输入、业务知识资产、跨角色协作、可消费的平台设计**。
2. **四方共识高度一致，且与构想的方向性冲突已经明朗**：先 Bugfix 后需求开发（〔V1〕〔V3〕〔V4〕均给出明确理由）、保留人工门禁不自动合并（〔V1〕〔V2〕〔V4〕，V4 给出五条理由）、效果取决于输入/上下文质量、通用能力上平台、小场景真实验证再拼装。而〔构想〕的"全自动 + 每日发布 + 无人值守"与共识正面冲突——已有分析（〔03〕）判定其为否决项，可行域是 **"Bugfix 型单交付闭环（人工门禁版）"**。
3. **推进主轴（个人设想，详见 §3）**：按"多来源 → 筛选 → 聚类 → 分路径"处理各方产出的全部方向，聚成 6 条路径、分三档推进——
   - **一档（现在就做）**：A. Bugfix 端到端闭环常态化（解决率约 60%→80%，口径待对齐）；B. 小需求直达研发试点（受理 Agent 已是统一入口，路由小需求的基础设施部分已存在）；
   - **二档（局部试验）**：C. 设计→PRD→研发链路（HTML 反推 PRD）；D. 知识资产可消费 MVP（DeepMap）；
   - **三档（只规划不排期）**：E. 需求→交付全自动闭环（大功能全链，前提清单 + 触发条件制）；
   - **横切（持续）**：F. 平台通用能力沉淀与跨团队协同治理（V4 明确：外层统一编排平台缺失，当前协作靠 Multica 任务卡）。
4. **当前最近的坑**：① **报告噪声**——V4 称"最大的现实问题"：AI 全量输出问题，人的阅读判断成本成为硬约束（infReview 侧同样指出）；② **重复建设**——多团队并行做类似的事，协同机制未建立；③ **决策悬空**——共识无拍板主体，〔03〕的 D1-D10 候选无人拍。
5. **当前最缺的信息（P0 全清单见 §4）**：小鱼儿×infReview 联调实测数据、**指标口径对齐**（V1"批入率 50%"与 V4"解决率约 60%"两个数两种名称，V4 数字还需回听核对）、平台归属与 Multica 定位、报告聚合分级的归属、去重机制、上周分析报告催收。

## 2. 现有情况总结（访谈事实）

### 2.1 三个团队快照

**小鱼儿团队（Bugfix Agent，〔V1〕进展与方向 + 〔V4〕流程细节）**

- **全链流程（V4，比 V1 详细）**：产品 Bug 反馈群提出问题 → 创建任务卡（**目前仍需人工触发**）→ 受理 Agent 澄清并聚合多源信息为结构化内容（要解决什么 / 背景与影响 / 方案 / 验收标准）→ **方案审批门**（用户在任务卡确认或纠正，通过才进入代码修改）→ 研发 Agent 在最新代码上建分支、修改、提交 MR → 触发 E2E → 测试结果、**截图与视频**回写任务卡 → 用户/负责人确认 → 人工合并；不通过则继续修改重验。
- **方案审批门是关键演化**：早期教训是"用户给一点信息 Agent 就直接执行，效果很差"；现在四项信息（要解决什么 / 是否需要处理 / 什么方案 / 验收标准）基本明确才创建开发任务，信息不足则追问或按职责转交产品/设计/研发负责人。**V1 指出的"该不该修"决策缺口在 V4 中已收口为这道门。** 后续协作通过任务卡评论推进。
- **Agent 结构：3 → 2**。早期三个（受理 / 交互分析 / 研发），因受理与交互分析职责重叠，**已合并为两个**——"受理与方案处理 Agent"（统一入口 + 意图路由：Bug 修复 / 产品小需求 / 研发分析 / 专项 Agent，路由表可扩展）+ "研发执行 Agent"；合并后速度明显提升。**回答了 V1 遗留的"三 Agent 如何协作"待确认项。**
- **路由依赖人员地图**：要不要做、交给谁，不能只靠模型临时判断；需要系统可查询的人员与职责地图（什么问题找产品/UI/研发/审批人），信息不足时按地图主动找人。
- **确定性工具封装**：建分支、取最新代码、Commit、建 MR、打包构建、触发测试、回写任务卡等已封装为确定性工具，不让 Agent 每次命令行探索（慢且易错）；原则 = "确定性步骤交给工具，Agent 精力留给理解与决策"。
- **核心数据**：V1 称修复批入率约 **50%**、目标 80%；V4 称解决率"从较低水平提升到约 **60%**"、目标 80%（**V4 数字有识别不确定性，需回听核对；两口径定义待对齐**）。相对早期三 Agent 交接方案，两 Agent 结构速度明显提升。
- **自认当前最大问题 = 报告噪声**：AI 全量输出潜在问题，用户没时间读、研发不愿读、低价值掩盖高风险；应优先呈现"最需要处理的几个问题"，详细分析折叠。审查结果需要聚合分级（总数 / 高优 / 必须处理 / 建议处理 / 仅提示）。
- **其余缺口**：任务卡创建仍人工触发；E2E 每次从头装依赖太慢，方向是按发布/构建基线分支预制含依赖的镜像；任务卡创建后的流程缺工程化的状态与 Hook 机制（见 F 路径）。
- **上下文补全（V1 既定方向）**：已接内部测试日志、Langfuse Trace、群附件；待接视频内容、客户端日志。每任务独立工作空间/沙箱；上下文过长需压缩整理。模型策略：常规修改用内部封装工具链更稳，复杂推理才上强模型。
- **可迁移资产清单（V4 §十六）**：Agent 角色定义、领域 Skill、MCP 工具、任务状态、代码与测试工具、方案审批与人工介入规则——供其他产品按领域复用，而非复制整套流程。
- **其余流程仍传统（V1）**：需求评审 → 设计评审 → 开发；CR 已用机器人；设计环节可出 HTML。
- **测试建设（V1）**：1 名实习生把历史冒烟/回归用例转集成/E2E；第一目标 = 上版本合并后暴露的问题必须能被测出；两个扩展场景 = 合并阶段 AI 判断多需求关联并自动补测试、边缘环境覆盖。评估过直接用 InfTest，因其强依赖需求文档、接入流程长，暂先自建。

**infReview 团队（AI Code Review，〔V2〕）**

- **能力现状**：AI 探索仓库 + 分析 + 生成报告；问题分级（Critical/Major…），高优阻塞合并；多轮 Review 带历史（旧问题修复状态 + 新问题）；审查规则与 Skill 可配置。
- **与 Bugfix 闭环的接入已自然解决**：报告本来就回写代码托管平台，小鱼儿直接从托管平台读报告（原生接口 / `gh` 命令），**不需要新集成 API**；V4 侧证 CR 结果已在被消费且"部分内容质量不错，但数量太多"。
- **边界**：现阶段不自动修复；下一版本建"自动修复入口"——是项目级修复过程，不是 Review 里的 Patch 建议。代码不自动合并，人工做最后检查。
- **缺口**：① 需求文档未进审查上下文（无稳定收集入口，只能从代码变更反推意图）；② 对开发者 Comment（"故意这样写、暂不改"）的理解不成熟；③ 评分/总分功能计划中（已有外包验收客户用自定义 Skill 打分的真实场景）。
- **近期重点**：准确率、召回率、稳定性、成本；控噪声（"成千上万条结果用户没法用"——与 V4 的报告噪声问题同源）。
- **横向约束（对全闭环都成立）**：模型调用稳定性与 Token 成本计量；同名模型不同接入方式不等价；上下文压缩是长任务关键；私有化客户旧硬件吞吐低一个量级（内部十几分钟的任务到客户环境要数小时）；基于开源二开（Kilo Code）有上游跟进负担。

**需求研发线（神州项目 + DeepMap + 设计链路，〔V3〕）**

- **神州项目的核心教训**：自动开发效果**高度依赖输入文档质量**——3 个模块中文档质量好的 1 个效果好，差的 2 个怎么调都不行；输入须接近结构化、字段完整的 Spec。另有架构教训：50+ 接口自下而上先做单接口再组装，最后对不上。更大瓶颈在前端：核心系统上千模块、文档几十万字，业务人员写不出；AI 辅助生成文档的项目**已暂停**。
- **当前策略**：反对一次性设计大而全；从两类小场景切入——Bugfix + 很小的产品需求（新增按钮、文案）；**小需求由 Agent 完成技术上半无障碍，真正的障碍是团队流程与协作**（研发先行 Coding、产品节奏不同步）。
- **设计→研发链路现状**：已有 Design System + Skill 组件封装；流程 = AI 生成 HTML（统一 Design System）→ 设计稿 + 简短说明交研发 → 研发用 AI 还原前端 + 补逻辑。问题：说明与 HTML 无稳定关联、逻辑靠口头传递、返工多、缺全局业务视角。
- **HTML 反推结构化 PRD 的 Skill**（记录页面/模块业务联系、控件行为、输入输出异常、页面跳转关系）：内部试验**显著改善**研发理解与还原质量；**缺专人持续迭代**是唯一瓶颈。
- **DeepMap 定位**：从"代码建模"走向"研发资产管理与知识关联平台"——关联技术结构、业务逻辑、需求/PRD、负责人、变更历史；当前建模偏技术视角、未面向消费场景；近期应扩大信息覆盖 + 用最小 MVP 跑通一条真实消费链路，而不是雕琢图谱展示。小鱼儿侧（V4 §十四）也持相同观点：其他产品按领域复用闭环通用能力，平台统一受理/路由/修改/测试/回写。
- **需求分流 Agent**：设想产品每日约半小时打标分流（简单需求直发研发 Agent / 需设计需求进 Design System + PRD 链路 / 信息不足追问）；若 Agent 掌握行业、竞品、产品现状与规划，可先完成分析与方案草拟，产品只消费和调整。难点是知识持续积累。
- **双向溯源是客户共同刚需**：需求↔代码互查、新项目复用历史实现、Bug 追溯到引入变更；设想 PRD 入 Git 用版本记录关联任务/代码/负责人。
- **配套动作**：平台三层架构（基础资源调度 / Agent 能力编排 / 业务场景层 SDLC）；标准化产品需连接器接入 Jira 等工单系统；一位运营同学负责官网、用户反馈链路自动化、FDE 协同；探索小企业/小团队 PoC（局部场景快速验证，不以短期收入为目标）。

### 2.2 构想与现状的覆盖关系

〔构想〕= 多源采集 → 评估 Agent 初筛 → 粗库/需求库 → 聚类 + 优先级 → 置信度分流 → Spec 自动生成 → 排期执行 → CR/测试 → 版本聚集发布 → 复盘沉淀 → 知识库，外加无人值守联网自采与每日发布。

已有逐环节深度判定（〔03〕，此处只引结论）：**12 环节无一以构想原语义整体"能做"**；执行内核两侧已建成/落地，**执行前需求控制面与执行后发布控制面整段缺失**；"全自动、每日发布、无人值守"与内部"不自动合并、先 Bugfix 后需求"两项共识正面冲突，为否决项。可行域 = Bugfix 型单交付闭环（人工门禁版）= 子集甲（现在就可推进）+ 子集乙（单一外部前提到位即推进）；子集丙（需求控制面主体、发布反馈控制面、知识库、无人值守）前提未启动，只能跟踪。

〔V3〕〔V4〕为该判定补了新证据：① 需求侧输入质量问题的真实代价（神州 1 好 2 差）；② 需求→研发不是"没有能力"而是"流程协作跑不动"（小需求案例）；③ 知识资产（DeepMap）已有明确定位与第一阶段定义，是子集丙里前提最具体的一项；④ 小鱼儿的"方案审批门 + 人工合并"实践 = 三 Gate 蓝图中 Gate 0（准入澄清）/Gate 2（验收合并）形态的落地实证；⑤ V4 明确"暂不宜强行接入完整研发流程"（五条理由），与"先 Bugfix 后需求"共识再次互证。

### 2.3 跨团队共识与张力

**共识（多方一致，可直接作为推进依据）**：

1. **先 Bugfix、后需求开发**——输入明确、验证可得、有真实流量；V4 补足理由：普通需求前置澄清与产品判断更复杂、过早接入大流程会放大 Agent 间不稳定（〔V1〕〔V3〕〔V4〕）。
2. **保留人工门禁、不自动合并**——V4 给出五条理由（AI 可能理解错需求 / 修改可能影响其他功能 / 各团队风险标准不同 / 合并需明确负责人 / 线上责任不能交给 Agent）；人的角色收敛到方案审批、异常判断、最终合并；对应三 Gate 蓝图（Gate 0 工作准入 / Gate 1 方案批准 / Gate 2 交付验收）〔既有〕。
3. **效果高度依赖输入/上下文质量**——小鱼儿补上下文 + 四项澄清门、神州看文档质量、infReview 缺需求文档入口，同一个结论的多种表述。
4. **通用能力上平台、场景能力归业务团队**——模型适配、上下文管理、私有化部署、编排、治理应由平台沉淀（〔V1〕〔V2〕〔V3〕+ V4"把受理/路由/修改/测试/回写沉淀为平台能力"）。
5. **从小场景真实验证再拼装，反对先画完整蓝图**——"让已有能力被真实团队用起来"是收集反馈的唯一途径（〔V2〕〔V3〕〔V4〕）。
6. **双向溯源/知识关联是刚需**——客户反复提出，且同时服务 Bug 定位、需求审查、历史复用（〔V3〕，与〔V2〕需求文档诉求同源）。
7. **（新增）人的阅读与判断成本是硬约束**——AI 生成报告成本低、人消费成本高；产品必须围绕"最需要处理的几个问题"设计，全量输出等于不可用（〔V2〕§七 + 〔V4〕§十/十一，双方各自独立提出）。

**张力（需要在协同机制里解决）**：

1. **全自动程度**：构想要全自动无人值守 vs 三方都要人工门禁——已按否决项处理，替代口径 = 每日候选版本 + 人工放行。
2. **通用 vs 定制**：infReview 走通用能力、小鱼儿深度绑定自己业务；"标准平台脱离业务知识只是演示"（〔V3〕）——平台与业务的边界要拍。
3. **产品闭环 ≠ 流程闭环**：面向客户的演示销售闭环 vs 公司内部真实提效闭环，目标不同、互相促进（〔V3〕§十五），汇报和考核要分开算。
4. **重复建设**：小鱼儿、需求方向同学、平台、各产品线都在做类似的事（〔V1〕点名、〔V2〕建议对齐接口与责任边界、V4 建议"复用通用能力而非各自重复建设"）——目前只有"先分聊再大讨论"的意向，无机制。
5. **编排平台缺失**：V4 明确"外层还没有完善的统一编排平台"，当前协作靠 Multica 任务卡与流程能力；多 Agent 自由交接不稳定（状态、上下文、责任边界易丢失），需要状态/Hook/Lead Agent 机制——这既是缺口也是平台归属问题的焦点（谁建：Multica？平台团队？）。
6. **节奏冲突**：内部项目进度紧，全项目改造要等阶段结束增量试验（〔V3〕）；样板团队要选协作成本低的（〔V3〕建议 + 我方团队 FD 一体、结构简单，是天然候选〔V1〕）。

### 2.4 对全闭环都成立的横向约束（〔V2〕〔V4〕为主）

模型调用稳定性与中断；Token 消耗与成本计量不准；长任务上下文压缩的边界；私有化旧硬件与弱模型的分层适配；AI 大 Diff / 过度设计风险；经验依赖——拆分与决策仍需有经验的人；人的阅读判断成本（报告噪声）；多 Agent 自由交接的不稳定性（需状态与 Hook 机制兜底）。

## 3. 推进思路（含个人设想）

### 3.1 方法：多来源 → 筛选 → 聚类 → 分路径

把四次访谈 + 构想 + 既有底账产出的全部"可做事项"当作输入，先筛选再聚类，不追求一条主线通吃。筛选用五条标准（全部来自访谈证据）：

1. **输入结构化程度**（Bugfix 输入明确 ✓ / 需求输入弱 ✗——神州教训）；
2. **验证是否闭环**（E2E 留证已有 ✓ / 需求验收难自动化 ✗）；
3. **人工介入是否可控**（介入点清晰 ✓ / 跨角色协作复杂 ✗——小需求案例）；
4. **是否已有真实使用与数据**（解决率有基线 ✓ / 全链无使用方 ✗）；
5. **前提依赖数量**（无外部前提 / 单一前提 / 前提未启动——对应子集甲/乙/丙）。

注：这套"来源→筛选→聚类→分流"的方法与〔构想〕的信号处理思路同构，只是作用对象是"推进事项"而非"产品需求"——把它先用在这份报告上，本身就是对构想可行性的一次小规模预演。

### 3.3 一档：现在就落地

**A. Bugfix 闭环落地包（最优先）**

- **目标口径**：真实 Issue 流水上解决率 60%→80%（**先对齐口径**，见 §4-P0）；链路常态化 = 反馈群→任务卡→受理澄清（四项明确）→方案审批→修复→infReview 回读→E2E 截图/视频留证→**人工合并**；发布口径 = 每日候选 + 人工放行（不引入自动合并）。
- **动作**（V4 之后多数是小鱼儿既定方向的收口，不是新发明）：
  1. 上下文补全续接：视频内容、客户端日志（〔V1〕既定）；
  2. **固化方案审批门**：四项明确才放行的实践已在跑，动作改为定期复盘沉淀审批规则/Style/Prompt + 明确人员地图（V4 既定方向），不再需要"补决策点"；
  3. 入口自动化：任务卡创建去人工触发（反馈群/监控信号 → 自动建卡）；
  4. 小鱼儿×infReview 从内部测试转正式联调：读报告→修→再审循环；**同步做报告聚合分级**（总数/高优/必须处理/建议/提示 + 折叠详情），并明确做在小鱼儿任务卡侧还是 infReview 报告侧——V4 称这是当前最大现实问题；
  5. 测试资产第一目标落地（上版本合并暴露的问题必须能被测出）+ E2E 环境镜像基线（按发布/构建基线分支预制含依赖镜像，V4 既定方向）；
  6. 建统一指标：解决率/批入率（统一定义）、误修/回退率、CR 报告有效率（噪声率）、单件成本（Token/时延）。
- **验收**：连续若干周真实流水上的解决率趋势 + 人工合并保留。
- **风险**：指标口径未对齐前不能对外承诺 80%；报告噪声不解决则用户不读、闭环等于没闭环；60→80 的提升路径未经验证；上下文补全边际收益可能递减。

**B. 小需求直达研发试点（在我方团队先跑）**

- **依据**：〔V3〕"小需求 Agent 完成技术上半无障碍，障碍在流程协作" + 〔V3〕建议选协作成本低团队做样板 + 我方团队 FD 一体、设计/开发/测试同肩（〔V1〕），是天然样板位。**V4 新增：小鱼儿受理 Agent 本就是统一入口、路由表含"产品小需求"，B 的基础设施部分已存在。**
- **动作**：
  1. 圈定需求类型白名单（文案、按钮、小交互、局部修复）；
  2. 在受理 Agent 路由表中开"我方团队小需求"通道，分流先用人工打标（对齐〔V3〕"产品每日半小时"设想），**不做** AI 优先级评估；
  3. 明确产品验收节奏与介入点，防止研发先行失同步（〔V3〕指出的核心障碍）；
  4. 每单留证据（diff、验收记录、返工次数），为后续扩路径积累数据。
- **边界**：不做语义聚类、不做置信度自动分流（前提未启动，属三档）。

### 3.4 二档：局部试验（不排大期，出结论即止）

**C. 设计→PRD→研发链路**：给 HTML 反推 PRD 的 Skill 配专人迭代（当前唯一瓶颈就是缺人）；PRD 入 Git 起版本、关联任务与代码（双向溯源最小版，同时是 D 的数据来源）。验收 = 一个真实需求从 HTML→PRD→还原的返工率下降。

**D. DeepMap 可消费 MVP**：不再雕琢图谱展示，选**一条**真实消费链路先跑通——候选：Bugfix 的问题背景理解 / 变更影响分析 / 需求分流的知识底座。第一阶段字段对齐〔V3〕定义：技术结构 + 业务逻辑 + 负责人 + 变更历史。接入方式按 V4 §十四：复用小鱼儿闭环的通用能力（受理/上下文/路由/方案确认/修改/验证/回写），DeepMap 只补领域 Skill 与知识。

### 3.5 三档：难落地、先规划出来（E = "大功能从需求到交付"的全链自动化）

规划产物固定为五件（不承诺时点，触发条件制）：

1. **前提清单 + 触发条件**：需求资产规范化、Issue/需求分类体系、知识库、跨角色协作机制、验证体系、成本预算——每项写清"谁启动、什么状态算就绪"；
2. **分段蓝图**：Bugfix 型 → 小需求 → 带设计的中需求 → 全链，每段以人工门收口（三 Gate 已有设计〔既有〕，小鱼儿方案审批门是 Gate 0/2 形态的首个落地实证），逐段放权；
3. **否决项显式化**：每日发布（全自动）、无人值守自动循环不做；替代口径 = 每日候选 + 人工放行；
4. **神州教训转设计约束**：输入质量门（Spec 完备度检查，不达标不进流程）；场景自上而下组装（先业务场景串联、后单接口实现）；文档生成环节的前提方案（AI 辅助文档项目已暂停，需重启条件）；V4 的第五条理由也入约束——编排与状态机制不稳前，不放大流程接入面；
5. **决策点清单**：直接复用〔03〕D1-D10（候选、影响、推荐已备好），找到拍板主体即可用。

### 3.6 横切 F：平台能力与协同治理（个人设想为主）

- **平台归属确认仍是第一悬空项，且 V4 把问题问得更具体了**：三方共识"平台承接通用能力"，但平台是谁未确认；V4 明确外层统一编排平台缺失、当前靠 Multica 任务卡，且需要状态/Hook/Lead Agent 机制——**第一个要问的问题变为：Multica 是否承接编排层与通用能力层？边界在哪？**（§4-P0）
- **通用能力清单**（候选，待平台认领）：模型适配与分层验收、上下文管理、私有化部署、Agent 编排与状态/Hook 机制、确定性工具封装范式（V4 的建分支/Commit/MR/打包/测试/回写模式）、成本/权限/安全治理、外部连接器（Jira、代码托管平台）。
- **协同机制**：延续"先分聊透、再大范围讨论"（〔V1〕收尾的既定意向），建议补一次跨团队对齐会，议题固定四件——谁做通用/谁做场景、Multica/平台边界、接口与数据协议（报告回读已自然解决，可作范式）、重复建设清单合并。
- **决策机制**：D1-D10 需要一个拍板主体与节奏；没有它，共识会长期停留在"都认同、都没动"。
