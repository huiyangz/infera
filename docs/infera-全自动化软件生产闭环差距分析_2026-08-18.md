# Infera 全自动化软件生产闭环差距分析

日期：2026-08-18  
分析对象：当前 `infera` 代码库与《全自动化软件生产闭环流程设计构想》  
结论口径：基于当前工作树中的代码、迁移、测试和设计文档；“已有设计”不等同于“已经实现”

## 1. 执行结论

当前项目与构想不是完全不一致，而是只实现了构想中间的一段。

当前 Infera 的准确定位是：

> 一个以人工录入 Delivery 为起点，以代码分支/PR 为终点，带 Spec 审批、Agent 编排、测试回环和需求拆分能力的单需求代码交付引擎。

构想要求的定位则是：

> 一个从外部信号发现、需求决策、规划执行、版本发布、线上观测到知识反馈的自主软件生产控制平面。

当前已经具备的主链路是：

```text
人工创建 Delivery
  -> 获取代码工作区
  -> Spec Agent
  -> 人工规格审批
  -> 测试生成 Agent
  -> 实现 Agent
  -> 单元测试（失败回实现，最多 3 次）
  -> Reviewer Agent + 人工代码审批
  -> commit / push / 尝试创建 GitHub PR
  -> Delivery completed
```

构想中的完整闭环是：

```text
多源信号
  -> 清洗/分类/聚类/去重
  -> 需求评估和产品优先级决策
  -> 人审或置信策略放行
  -> 预算、排期和依赖规划
  -> Spec/设计/任务/实现/测试/评审
  -> 版本聚合、验收、发布物料、部署和回滚
  -> 线上观测、故障和反馈采集
  -> 复盘、知识沉淀和策略校准
  -> 产生下一轮信号
```

因此，最大的差距不在“再增加几个 Agent”，而在两个系统端点和一个横向底座：

1. **执行前缺少需求控制面**：没有 Signal/Demand、来源接入、聚类去重、评估、产品上下文、优先级、置信分流、成本估算和排期。
2. **执行后缺少发布与反馈控制面**：当前止于 PR，没有合并队列、Release、验收、部署、渐进发布、健康检查、回滚、线上反馈与复盘。
3. **横向治理不足**：当前执行契约、权限、安全、持久任务、预算和评测能力，尚不足以承载多日、无人值守和可审计的生产闭环。

## 2. 当前能力基线

### 2.1 已实现

- `Project`、`Delivery`、`StageRun`、`Artifact`、`Event` 的持久化模型。
- 7 阶段交付图：`intake -> spec -> spec_approval -> test_gen -> code_gen -> unit_test -> code_review`。
- Spec 和代码两个人工门禁，支持批准、驳回和反馈回注。
- 单元测试失败回到代码实现，连续失败上限为 3。
- Delivery 独立 workspace，记录基线 commit，并有重启恢复入口。
- 大需求可拆成子 Delivery，按 wave 执行，父 Delivery 增量合并；冲突可人工修复后恢复。
- Agent 注册表与项目级/全局节点绑定。
- CLI、HTTP、Docker runner；`local` runner 目前是停车占位语义。
- 实现产出可 commit、push，并在 GitHub + token 条件满足时尝试创建 PR。
- 时间线、产物存储和 WebSocket 事件更新。
- 前端包含项目列表/详情、Delivery 详情、门禁审批和 Agent 绑定编辑。

### 2.2 只有设计、尚未落地

`docs/superpowers/specs/2026-08-17-sdd-stages-design.md` 描述了 11 阶段 SDD：

```text
intake -> spec -> spec_approval
  -> design -> design_approval
  -> tasks -> tasks_approval
  -> test_gen -> code_gen -> unit_test -> code_review
```

其中还包括复杂度分流、按设计边界拆分、按任务逐条实现和任务进度恢复。当前运行时图仍只有 7 阶段；`design`、`tasks` 仅有前端文案和设计稿，不能算现有能力。

### 2.3 当前关键限制

- Agent 契约只有 `{role, prompt, workdir} -> output string`，输出主要是自由 Markdown。
- `TEST_CMD` 默认值为 `true`，默认配置并不执行真实项目测试。
- 当前完成语义是“人工批准代码后 Delivery completed”，不是“合并、部署并线上验证完成”。
- PR 创建失败不阻断 Delivery 完成；系统也不跟踪 PR 后续状态。
- 认证是单一共享密码和内存 session，没有用户、角色、审批权限分离和完整审计主体。
- WebSocket 当前公开挂载，且允许任意 Origin，属于 MVP 安全边界。
- 长任务由进程内 goroutine 和互斥锁驱动。已有阶段记录与恢复能力有价值，但不等于持久工作流调度器。
- 数据域只有 Project/Delivery 及执行记录，没有需求、版本、部署、反馈或知识对象。

## 3. 端到端能力差距矩阵

状态定义：

- **已有**：当前代码存在可执行主路径。
- **部分**：存在局部能力，但尚不能满足构想语义。
- **设计**：有设计文档或前端占位，运行时尚未实现。
- **缺失**：当前数据模型、API 和执行图均无对应能力。

| 构想环节 | 状态 | 当前基础 | 主要差距 |
|---|---|---|---|
| 人工需求输入 | 部分 | 可手工创建 Delivery | 直接进入开发，没有需求候选池、来源、证据和评估过程 |
| 故障/反馈/新闻/项目动态采集 | 缺失 | 无 | 连接器、Webhook/轮询、原始载荷、游标、限流、重放、来源可信度 |
| 信号清洗与分类 | 缺失 | 无 | 标准化 schema、语言/噪声处理、敏感信息处理、分类体系 |
| 粗库 | 缺失 | Event/Artifact 不是信号库 | 原始不可变 Signal 存储、来源追踪、保留策略 |
| 聚类与相似性分析 | 缺失 | 无 | embedding、近邻检索、去重、聚类版本、人工纠错 |
| 高质量潜在需求库 | 缺失 | Delivery 不能替代 Demand | Demand 生命周期、证据聚合、集群、状态和追踪关系 |
| 质量/价值/风险评估 | 缺失 | 无 | 评估维度、结构化结论、证据引用、校准数据 |
| 产品优先级判断 | 缺失 | Project 仅有仓库信息 | 产品目标、路线图、客户/收入/风险上下文、策略规则 |
| 置信度人机分流 | 部分 | Spec/代码固定人工门 | 没有置信模型、风险等级、动态门禁和可审计策略 |
| 时间/token/成本粗估 | 缺失 | StageRun 只记时间 | 估算器、token/cost 计量、历史基线、误差校准 |
| 依赖、容量和排期 | 部分 | 子需求 wave | 无跨 Demand/Delivery 依赖图、资源预算、优先队列、配额 |
| Spec 自动生成 | 已有 | Spec Agent + 人审 | 输出非结构化，缺证据引用、schema 校验、评测和版本语义 |
| 设计与任务拆解 | 设计 | 已有 11 阶段设计稿 | 运行图、存储、API、Agent 绑定、UI 和测试均需落地 |
| 单/多 Agent 执行 | 部分 | 可按节点绑定不同 runner，子 Delivery 可并行 | 不是任务级多 Agent 协作；缺租约、预算、取消、超时、能力声明 |
| 测试失败回环 | 已有 | unit_test 失败回 code_gen | 默认测试为空操作；缺测试发现、多层测试、覆盖率和质量策略 |
| Code Review | 部分 | Reviewer Agent + 人工门 | 缺结构化 finding、严重级别、增量复审、必修项闭环和策略门 |
| 版本聚集 | 缺失 | 无 Release 对象 | Delivery 到 Release 的选择、冻结、依赖和状态机 |
| PR 合并和队列 | 缺失 | 只尝试创建 GitHub PR | CI 状态、review/check、merge queue、更新基线、冲突和回滚 |
| 发布验证/人工验收 | 缺失 | code_review 不是发布验收 | staging 环境、验收清单、证据、签发角色和超时升级 |
| 文档/Changelog/版本总结 | 缺失 | Artifact 可存文本 | 生成规则、受影响文档发现、版本级聚合、发布物料审批 |
| 部署上线 | 缺失 | 无 | 环境、制品、部署提供商、审批、密钥、发布窗口 |
| 灰度、健康检查和回滚 | 缺失 | 无 | rollout 策略、SLI/SLO、自动判定、补偿动作 |
| 线上故障和用户反馈回流 | 缺失 | 无 | telemetry/incident/feedback 接入，生产版本关联 |
| 复盘与知识沉淀 | 缺失 | Artifact 仅按 Delivery 查 | 知识条目、溯源、检索、有效期、反馈和再评测 |
| 无人值守循环 | 缺失 | 单 Delivery 可异步推进 | 缺完整闭环以及自治边界、停机开关和运营治理 |

## 4. 不应直接沿用的建模方式

### 4.1 不要把所有环节继续塞进 Delivery

`Delivery` 已经适合表示“一个被批准、准备实现的交付单元”。如果同时让它表示原始反馈、需求候选、路线图事项、版本和线上事故，其状态机会迅速失真。

建议使用彼此独立、可追踪关联的生命周期：

| 聚合 | 负责什么 | 典型状态 |
|---|---|---|
| `Signal` | 外部/内部原始观察，不可变留档 | received, normalized, rejected |
| `DemandCluster` | 相似信号的聚合及聚类版本 | active, split, merged, archived |
| `Demand` | 可决策的候选需求 | candidate, evaluating, triage, approved, deferred, rejected |
| `Delivery` | 已批准需求的工程实现单元 | queued, active, blocked, completed, cancelled |
| `Release` | 一组可共同晋级的 Delivery/PR | planning, frozen, validating, approved, released, failed |
| `Deployment` | 某 Release 到某环境的一次发布 | pending, running, healthy, unhealthy, rolled_back |
| `Observation` | 发布后的指标、反馈、故障证据 | open, correlated, resolved |
| `KnowledgeItem` | 可复用结论、决策和经验 | draft, verified, stale, superseded |
| `EvaluationRun` | Agent/策略版本的离线或线上评测 | queued, running, passed, failed |

关键追踪链应能回答：

```text
Signal -> DemandCluster -> Demand -> Delivery -> PR/Artifact
       -> Release -> Deployment -> Observation/Incident -> KnowledgeItem
```

### 4.2 “置信度”不能只有一个 LLM 自报数字

建议拆成可解释的路由特征：

- schema 是否有效；
- 证据是否完整、引用是否可访问；
- 去重/聚类确定性；
- 用户影响与商业影响的证据强度；
- 需求新颖度和产品目标匹配度；
- 实现复杂度、变更范围和安全风险；
- 测试充分度、review finding 和发布风险；
- 历史同类任务中该模型/提示/策略的实际准确率。

自动放行应由**版本化策略**决定，例如“低风险 + 证据完整 + 评测达标 + 预算内”，而不是由某次模型输出的单一分数决定。策略输入、结果、版本和人工覆盖都要记录。

### 4.3 “每天自动发布”应是结果指标，不应是无条件动作

更合理的目标是：

> 符合白名单、风险低、验证证据充分的变更，可以在发布窗口内自动晋级；其余变更按风险进入人工门禁。

需要同时设定：变更风险分类、blast radius、渐进发布、健康判定、回滚时限、冻结窗口、紧急停止开关。否则“每日发布”会把频率当成安全性替代品。

## 5. 建议目标架构

不建议一开始拆成大量微服务。当前阶段可保持模块化单体 + 独立 worker，在领域边界稳定、负载或团队所有权需要时再拆服务。

```text
[Source Connectors]
  GitHub/GitLab, issue, feedback, incident, telemetry, news/research
          |
          v
[Signal & Demand Control Plane]
  raw signal -> normalize -> classify -> dedup/cluster
  -> evaluate -> product-context priority -> policy routing
          |
          v
[Planning Control Plane]
  approved demand -> dependency graph -> estimate/budget
  -> queue/capacity/waves -> create Delivery
          |
          v
[Delivery Execution Kernel]        <- 当前 Infera 的主要基础
  spec/design/tasks -> implementation -> tests -> review -> PR
          |
          v
[Release Control Plane]
  merge queue -> release aggregation -> staging/acceptance
  -> docs/changelog -> deploy -> canary/health -> rollback
          |
          v
[Observation & Knowledge Plane]
  runtime evidence/incidents/feedback -> correlation -> retrospective
  -> knowledge/index -> evaluation/policy calibration -> new Signal

横向底座：durable workflow、policy engine、identity/RBAC、audit、secrets、
artifact/object storage、vector/search、cost/telemetry、evaluation registry。
```

### 5.1 持久工作流

当前 StageRun、事件和恢复机制可以保留并演进，但无人值守闭环还需要：

- 任务租约、heartbeat 和失联接管；
- 幂等 key、重复投递去重和 exactly-once effect 的外部动作保护；
- timeout、重试退避、取消、暂停和人工恢复；
- 外部 callback、定时器和跨天等待；
- compensation，例如部署失败后的自动回滚；
- worker 并发、租户/项目配额和优先级；
- workflow/schema 版本升级和在途实例兼容。

可评估 Temporal、Restate 或类似持久执行框架；若自研，以上能力本身就是一个独立的大工作包。

### 5.2 Agent 执行契约

建议从纯文本输出升级为带版本的结构化 envelope：

```json
{
  "schema_version": "1",
  "status": "succeeded",
  "result": {},
  "evidence": [],
  "confidence_features": {},
  "usage": {"input_tokens": 0, "output_tokens": 0, "cost": 0},
  "model": "...",
  "prompt_version": "...",
  "warnings": [],
  "retryable": false
}
```

同时加入输入/输出 schema 校验、输出修复、能力声明、工具权限、最大预算、deadline、取消信号、幂等键和完整 trace。Markdown 可以继续作为人类可读 artifact，但不应承担机器决策协议。

## 6. 分阶段实施路线

以下顺序按依赖关系排列，不建议同时铺开所有环节。

### Phase 0：产品边界、指标与评测基线

目标：先把“系统决定什么、人工决定什么、什么叫成功”写成可执行规则。

工作：

- 定义上述聚合、状态机和端到端 trace ID。
- 定义产品目标、优先级维度、风险等级和人工签发矩阵。
- 定义自治白名单/黑名单、预算、发布窗口和 kill switch。
- 建立 50-200 条历史需求的评测集，包含去重、优先级、Spec、实现结果和发布结果。
- 建立指标：需求采纳准确率、自动放行率、人工推翻率、交付成功率、逃逸缺陷率、回滚率、lead time、token/成本。

验收：对任一历史案例，系统边界、风险级别、所需门禁和成功指标均可复现；后续模型或策略变更能跑回归评测。

工程量级：`M`，约 2-4 人周，产品/工程/质量共同参与。

### Phase 1：加固当前 Delivery 执行内核

目标：让现有“需求到 PR”成为可信的生产内核。

工作：

- 实现已设计的 design/design_approval/tasks/tasks_approval 和复杂度分流。
- Agent 结构化输出、schema 校验、prompt/model/version/usage 记录。
- 项目级 Test Profile：测试发现、unit/integration/lint/typecheck/build、安全扫描和覆盖率门槛。
- 将默认 `TEST_CMD=true` 改为显式配置或可靠检测，未配置不得伪装成测试通过。
- 持久 job、lease/heartbeat、超时/取消、幂等重试和并发配额。
- 结构化 code review finding、必修项和复审闭环。
- 用户/服务身份、RBAC、审批职责分离、审计日志、CSRF/WS 鉴权、密钥托管。
- 失败分类、可重试/不可重试语义、运行监控和告警。

验收：进程在任意节点重启不会重复产生外部副作用；真实仓库必须执行规定质量门；每次自动决策和人工签发可追溯到主体、输入、策略及产物。

工程量级：`XL`，约 8-14 人周。

### Phase 2：需求控制面 MVP

目标：从“人工直接创建 Delivery”升级为“信号进入、候选需求被决策后才创建 Delivery”。

工作：

- 建立 Signal、Source、Cursor、DemandCluster、Demand、Evaluation、Decision 数据模型/API/UI。
- 先接 2-3 个高价值来源，例如 GitHub issue、内部反馈入口、告警/事故系统。
- 原始 payload 不可变存储、标准化、来源去重、重放和 dead-letter queue。
- embedding 检索、重复候选、聚类及人工 merge/split 纠错。
- 结构化评估：问题、用户、证据、影响、产品匹配、风险、建议动作。
- 产品上下文库：目标、路线图、当前版本、约束和明确不做事项，并保留版本。
- Triage Inbox：接受、合并、延期、拒绝、补证据；先以人审为主。
- 决策通过后才创建/关联 Delivery，保留全链路 provenance。

验收：来自指定来源的信号可稳定重放；重复项不会反复创建 Delivery；人工能够看到证据和聚类依据；Demand 到 Delivery 的转化可审计。

工程量级：`XL`，约 10-16 人周，连接器数量会显著影响范围。

### Phase 3：规划、估算与调度

目标：把“优先级高”转化为受容量、依赖和预算约束的执行计划。

工作：

- Demand/Delivery 依赖图、阻塞关系和循环检测。
- 历史相似项估算 + 变更范围分析；记录时间/token/cost 的预测区间而非单点。
- 项目/团队/模型预算，worker 并发、速率和每日额度。
- 排队策略、优先级老化、wave、发布窗口和人工插队。
- 估算误差回填与校准 dashboard。

验收：调度不会突破预算和并发限制；依赖未满足不启动；预测误差可按项目、Agent、任务类型复盘。

工程量级：`L`，约 5-9 人周。

### Phase 4：Release 与部署控制面

目标：将完成语义从“PR 已建立”延伸到“版本已安全上线并验证”。

工作：

- Release、ReleaseItem、Environment、Deployment、Approval、HealthCheck 模型。
- Git provider 抽象，跟踪 PR/CI/review/check 状态和 webhook；merge queue 与冲突处理。
- 版本聚合、冻结、依赖校验、版本号和制品追踪。
- staging 部署、自动验收、人工 UAT 证据和签发。
- Changelog、版本总结和受影响文档生成/校验。
- 首批只支持一个部署目标；实现 canary/渐进发布、SLI 判定和自动回滚。
- 将 Release/Deployment 结果反写到 Delivery/Demand。

验收：一个低风险 Release 可从合并队列到 staging、签发、生产灰度、健康确认完整运行；任一步失败可暂停或补偿；所有版本与制品可追溯。

工程量级：`XXL`，约 12-20 人周，部署平台和环境标准化程度是最大变量。

### Phase 5：观测、反馈和知识闭环

目标：让上线结果真正改变下一轮需求判断和执行策略。

工作：

- 接入 runtime metrics/log/trace、incident 和用户反馈。
- 将 Observation 与 Release/Deployment/Delivery/Demand 自动关联。
- 版本后观察窗口、异常归因、回滚/修复 Demand 自动建议。
- 版本复盘：目标达成、未完成高优项、缺陷、成本、人工介入和策略偏差。
- KnowledgeItem：证据、来源、有效期、owner、superseded 关系、全文/向量检索。
- 离线评测、线上 shadow、prompt/model/policy 对比和逐步发布。

验收：线上故障能追溯到部署和原始需求；复盘结论进入后续检索；策略升级前有评测，升级后能观察人工推翻率与生产结果。

工程量级：`XL`，约 8-14 人周。

### Phase 6：受限自治

目标：在有数据证明安全的范围内逐步减少人工门禁。

工作：

- 仅对白名单仓库、变更类型和低风险级别开启自动晋级。
- 先 shadow decision，再建议模式，再自动执行；每级都有回退条件。
- 按 Agent/项目/变更类型设自治额度和错误预算。
- 异常熔断、全局 kill switch、人工接管和在途任务冻结。
- 按实际成功率、逃逸缺陷率、回滚率逐步扩大范围。

验收：自治范围、依据和停止条件明确；人工可以即时接管；自治组的质量和恢复指标不劣于人工基线。

工程量级：`L`，约 4-8 人周；前提是前五阶段数据与治理已就绪。

## 7. 总体工作量判断

这是从“交付执行工具”扩展为“软件生产控制平面”，不是当前流水线增加若干节点的量级。

在以下假设下：首期单租户、单 Git provider、2-3 个信号来源、单部署平台、复用成熟工作流/向量库/可观测组件，不自研基础设施：

- **可用的闭环 MVP（Phase 0-2）**：约 20-34 人周。
- **包含规划和单平台发布（Phase 0-4）**：约 37-63 人周。
- **包含反馈、评测和受限自治（Phase 0-6）**：约 49-85 人周。

这是净工程量级，不是日历承诺。若由 3-5 人稳定团队推进，完整受限自治通常仍是多季度项目。多租户、多个 Git/部署平台、企业合规、自研持久工作流，都会明显放大范围。

建议不要以“全闭环功能全部存在”作为第一里程碑。更有价值的首个纵向切片是：

```text
GitHub Issue / 内部反馈
  -> Signal
  -> 去重并形成 Demand
  -> 人工 triage
  -> 创建 Delivery
  -> 真实质量门并开 PR
  -> 人工合并
  -> 单一 staging 环境验证
  -> 结果回写 Demand
```

它会最早验证四个核心假设：信号是否值得采、评估是否减少人工、Delivery 内核是否可靠、生产结果能否反向校准决策。

## 8. 建议立即启动的工作包

按优先级建议先做以下 8 项：

1. **冻结领域边界**：确认 Signal、Demand、Delivery、Release、Deployment、Knowledge 的职责和转换条件。
2. **确定首个纵向场景**：指定一个仓库、一个信号来源、一个 staging 目标和允许自动化的低风险变更类型。
3. **建立评测集**：从历史 issue/需求/PR 中选择代表案例，形成可重复基线。
4. **补真实质量门**：Test Profile、未配置失败、结构化测试证据，先消除 `true` 默认值带来的假绿。
5. **实现 11 阶段 SDD**：完成设计稿已有的 design/tasks 链路，但保持它属于 Delivery 内核，不承担需求评估。
6. **升级 Agent 契约**：结构化输出、usage、evidence、版本、timeout、budget 和 idempotency。
7. **做 Demand Control Plane 的最小模型/API**：先支持人工录入和一个 connector，再做去重与 triage UI。
8. **选择持久工作流方案**：做一次故障注入 PoC，验证重启、重复 callback、跨天门禁和补偿动作。

这 8 项完成后，项目会从“能演示自动开发流程”跨到“可以承载真实需求输入并可靠交付”的阶段。发布自动化和无人值守应建立在这个基线上。

## 9. 需要产品负责人确认的关键决策

- 首期是“服务 Infera 自身开发”，还是“服务任意软件项目”？前者可以显著缩小产品上下文、部署和权限范围。
- 首个信号来源是什么，谁对其质量负责？
- Demand 的最终优先级由谁签发，哪些风险等级允许策略自动放行？
- 首期支持哪个 Git provider、CI 和部署平台？
- “完成”的定义是 PR 创建、合并、staging 验收，还是生产健康窗口结束？
- 哪些代码区域永不允许无人审批，例如鉴权、计费、数据迁移、基础设施和安全策略？
- token/现金预算和允许的最大并发是多少？
- 知识库中哪些内容允许发送给外部模型，哪些必须本地处理或脱敏？

这些决策会直接改变架构和工程量，应该在 Phase 0 固化为版本化 policy，而不是散落在 prompt 中。

## 11. 最终判断

当前代码最值得保留和强化的是 **Delivery Execution Kernel**：workspace、阶段运行记录、artifact/event、门禁、Agent 绑定、测试回环、拆分 wave 和合并恢复，这些都是构想中段的有效资产。

下一步不应把完整构想压成一条更长的 Delivery 状态机。应在现有内核两侧分别建立 **Demand Control Plane** 和 **Release/Observation Control Plane**，并用持久工作流、策略、身份审计、评测与成本观测作为横向底座。

真正实现构想的标志，不是系统能自动写更多代码，而是它能够基于可追溯证据做出受约束的需求和发布决策，并能用生产结果纠正下一轮决策。到这一步，闭环才成立。
