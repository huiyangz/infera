# 飞书 x 小鱼儿 bot 自主交付架构设计评审

## 1\. 背景



目前用户可以在飞书话题群记录问题，需求 Bot 会在飞书项目中创建需求或缺陷；用户还需要再次 @小鱼儿，才会进入 Bug 修复或需求实施。登记和执行是两条依赖人工记忆连接的链路。



未来进入 AI 研发流程的问题主要来自三处：

1. 飞书项目中已有的需求或缺陷；

2. CI、E2E 和定期巡检发现的技术债；

3. 飞书内部反馈群中的问题和需求信号。



这些渠道只是把需求或问题收集起来，并不代表 AI 可以马上开始改代码。如果来一个就自动做一个，可能重复处理同一件事，也可能把时间花在不重要的事情上，甚至在没人确认的情况下改错地方；但如果每一步都要人手动转发和盯进度，AI 又无法真正独立完成交付。

ClawSweeper 的调研提供了一个可借鉴的原则：事件、Issue、评论和 CI 结果只是输入信号，自动化必须经过 Intake、明确授权和 Gate，才能逐步获得 Review、Repair 和 Merge 权限。



本蓝图因此采用：

> **飞书承载候选工作和人类决策，Multica 管理已准入工作，AI 完成高频执行，Git/CI/E2E 提供验证事实。**



## 2\. 需求与边界

### 2\.1 目标

5. 候选事项经过明确准入后，才进入已受理工作池，由 Multica Issue 承载。

6. 每个已受理的 Multica Issue 都是一项可独立交付的工作，并一对一绑定飞书话题群中的一个话题。

7. AI 在修改代码前生成修复方案或需求 Spec，并由人批准。

8. 方案批准后，AI 自主完成开发、测试、E2E、Review 和失败修复。

9. AI 形成绑定固定代码版本的交付证据包，并通过小鱼儿请求用户验收。

10. 验收失败时，用户补充上下文，同一 Issue 回到 AI 修复阶段。

11. 验收通过后，只允许合并被批准的候选版本。

12. 只有合并成功，Multica Issue 才进入 `Done`。

13. 飞书展示状态和承载决策，但不维护第二套可写的执行状态。

### 2\.2 非目标



1. 本阶段不决定 Webhook、Bridge、插件或 API 的实现方式。

2. 不定义数据库、事件 Schema 和部署结构。

3. 不默认允许 AI 自动合并、发布或部署。

4. 不把完整 Agent transcript 和工具日志同步到飞书。

5. 不让飞书和 Multica 同时维护一套可写的 Issue 执行状态。

6. 不为每个临时子 Agent 创建独立飞书机器人身份。

7. 不在本阶段确定全部低风险任务的自动准入策略。



## 3\. 方案设计

### 3\.1 总体分工

|参与方|主要责任|不承担的责任|
|---|---|---|
|飞书项目|候选需求、缺陷和业务上下文|AI 派发和执行状态|
|飞书话题 / 卡片|讨论、准入、方案批准、阻塞决策和验收|成为第二套任务状态源|
|需求 Bot|从反馈归纳并创建或关联飞书项目工作项|派发 Agent|
|小鱼儿|推送 Multica 卡片、收集决策、展示状态和证据|独立维护另一套 Issue 状态|
|Multica|Issue、Task、派发、重试、阻塞、证据和最终状态|未经授权决定业务优先级|
|AI Agent|调研、规划、开发、测试、E2E、Review 和修复|绕过批准直接合并|
|Git / CI / E2E|保存代码版本和验证事实|判断产品意图和业务价值|



### 3\.2 候选工作来源

所有候选工作统一进入飞书项目。工作准入通过后，系统创建 Multica Issue，并按类型绑定对应话题群中的一个话题。

|来源|进入候选池前的处理|准入后的话题群|
|---|---|---|
|飞书项目需求或缺陷|直接进入候选池|需求 \& 缺陷话题群|
|飞书内部反馈|需求 Bot 归纳、澄清和去重，创建或关联飞书项目工作项|需求 \& 缺陷话题群|
|CI、E2E 和定期巡检|将问题清单拆分或合并为可独立交付的技术债候选|技术债务话题群|

候选事项只表示问题已记录；未经工作准入，不创建执行承诺，也不授权 AI 修改代码。



### 3\.3 话题群与交付单元

已受理工作使用固定的一对一关系：

> **一个已受理工作项 = 一个可独立交付的 Multica Issue = 一个飞书话题。**

这里的“工作项”指业务交付单元，不是 Multica 内部拆分的 Task，也不是 Agent 的某一次 Run。一个 Issue 可以包含多个 Task、多次 Run 和多个候选版本，但整个交付生命周期始终在同一个飞书话题中协作。

初步规划两个话题群：

|话题群|问题来源|一个话题代表什么|
|---|---|---|
|需求 \& 缺陷话题群<br>|飞书项目需求、飞书项目缺陷、内部反馈归纳出的需求或 Bug|一项可以独立验收的需求或 Bug<br>|
|技术债务话题群<br>|CI、E2E、定期巡检及其他工程质量问题|一项可以独立验证和交付的技术债修复|

工作准入通过时，Multica Issue 与对应话题同时建立或完成绑定。方案卡、阻塞决策、状态摘要和交付验收卡都进入这个话题。

如果一个候选事项包含多个可以分别验收的目标，应在准入阶段拆成多个 Issue 和多个话题；Agent 内部拆分 Task、重试 Run 或更换执行者，不创建新话题。

话题是人类协作和决策入口，Multica Issue 仍是执行状态的事实源。

三个 Gate 都通过飞书卡片请求人工决策。卡片只展示当前决策所需的信息，并明确批准对象、授权范围和交付负责人。

### 3\.5 四阶段主流程

#### 阶段一：工作准入

\*\*核心问题：\*\*这件事是否值得成为组织承诺推进的研发交付？

Gate 0 根据事项类型展示不同的最小准入信息：

- **需求**：交付目标、价值或影响；

- **缺陷**：实际行为、预期行为、影响或证据。

准入人同时指派一名交付负责人。该负责人在一期默认负责 Gate 1 的方案批准和 Gate 2 的交付验收。Gate 0 的结果包括：

- **受理并指派**：建立 Multica Issue 和飞书话题，允许 AI 调研和规划；

- **信息不足**：补充上下文后重新审核；

- **延后或拒绝**：保留事项和决策原因；

- **合并**：关联到已有事项，避免重复工作。



#### 阶段二：方案批准

\*\*核心问题：\*\*准备怎样做，范围、风险和验收方式是否正确？

AI 生成修复方案或需求 Spec，包括目标、范围、非目标、实施思路、影响面、验证计划、验收标准和待决风险。小鱼儿把方案卡推送到飞书，由交付负责人批准实施、要求修改、补充信息或取消。

只有方案批准才授权 AI 修改代码。



#### 阶段三：AI 自主完成

\*\*核心问题：\*\*AI 能否独立形成可信的候选交付？

```Plain Text
开发
→ 单元测试、类型检查、Lint、构建
→ E2E 与真实行为验证
→ 独立 Review
→ 候选交付

```

测试、E2E 或 Review 失败时，AI 自动修复并重新验证。只有缺少业务判断、权限、关键上下文，或多次修复不能收敛时，小鱼儿才请求人的决策。

阶段产物是绑定固定代码版本的证据包，包括行为变化、验收标准、测试/E2E 结果、Review 结论、已知限制和验收入口。



#### 阶段四：交付验收

\*\*核心问题：\*\*这个候选版本是否满足真实需求？

小鱼儿推送 Gate 2 交付验收卡，集中展示：

- 单元测试、CI、E2E 和独立 Review 的结果摘要；

- E2E 验收截图或录屏；

- 直接进入当前候选版本的验收环境链接；

- 本次人工验收目标。

交付负责人查看证据，并进入验收环境完成 Review 和验收：

- **验收通过**：授权该候选版本进入合并；

- **验收失败**：用户补充实际表现和期望结果，同一 Issue 回到 AI 自主完成阶段。

E2E 截图、录屏、验收环境和人工验收结论都绑定同一个候选版本。候选代码变化后，旧证据和旧验收批准同时失效。只有被批准的版本成功合并，Multica Issue 才进入 `Done`。
