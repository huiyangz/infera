## 一、结论速览

1. **构想全闭环不可作为整体目标推进**。"全自动语义"环节（AI 优先级评估、置信度自动分流、自动发布、无人值守循环）在 01/02 事实基线下全部为"不能做"或与内部安全共识正面冲突。
2. **可行域是一个严格真子集**：Bugfix 型单交付闭环（人工门禁版）。其执行内核两侧均已建成——infera 平台 11 阶段 + 4 道人工门 + MCP 驾驶 + 本机通道（〔02-§五.1〕），内部生态 Bugfix 执行 / E2E 验证 / AI Code Review 已落地（〔01-§1.2〕〔01-§1.4〕〔01-§2.1〕）。瓶颈不在执行内核，在两端控制面与治理前提（〔02-§三〕小结）。
3. 12 环节逐项判定无一以构想原语义整体"能做"；真正现在就能做的，是既有能力的**退化/集成形态**（Spec 单需求生成、CodeReview 集成、粗库存档、人工复盘沉淀）。
4. "每天都有版本发布"在可见周期内不可承诺；可执行的替代口径是**每日候选版本 + 人工放行**（§四.1 论证）。
5. 推进前必须拍板 10 项决策（§六）：4 项为本篇新增，6 项承接〔02-§六〕并为每项补齐候选选项与影响。

## 二、差距矩阵（12 环节 + 2 附加项）

### 二.1 口径

1. 判定词表：**能做**（以已有能力为基础即可推进，无未决前提）／**条件能做**（技术路径存在，但必须先满足列出的具体条件）／**不能做**（存在当前无法绕过的阻断：能力为零、决策未定、与既有共识冲突，三者居其一即为阻断）。判定详单与理由见 §三。
2. 难度词表（本文评估，非源文档转述）：**低**＝配置/集成级工作；**中**＝单团队开发，有既有代码或蓝本可扩；**高**＝需新数据模型 + 治理决策 + 跨团队协同；**极高**＝整段新建且多项前提未定。
3. 成熟度：内部生态沿用〔01-§5.1〕词表（已落地/内测中/建设中/设计中/意向/无对应/待确认）；infera 沿用〔02-§一.1〕档位（已有/部分/缺失）。表中按归属并列标注。
4. 现状归属词表：小鱼儿／infReview／infera／飞书蓝图／缺失（5 份源文档与 infera 仓库均无对应物）。

## 三、逐环节可行性判定（12 环节 + 2 附加项）

> 判定词表见 §二.1。凡"条件能做"，条件均列至可拍板/可开工粒度；凡"不能做"，理由均落到 01/02 事实。

### 三.1 环节 1：多源信息采集 —— 条件能做（内部信号源子集）／不能做（外部联网采集子集）

1. 内部子集条件：①拍板首个信号源及其质量负责人（〔02-§六.2〕，对应本文 §六.D5）；②拍板承接形态——基于蓝图候选池（设计中，〔01-§3.6〕）或 infera 新建 Signal 聚合（零起步，〔02-§五.3.1〕），二者取一（关联 §六.D2）；③复用小鱼儿已接入信号（测试日志/Trace/附件，〔01-§1.3〕）而非重采。
2. 外部子集不能做理由：5 份源文档无对应物、蓝图三处候选来源全为内部信号（〔01-§5.3〕〔01-§3.1〕），且该子集从属于"无人值守循环"整体判定（§三.14）。

### 三.2 环节 2：评估 Agent 初筛 —— 条件能做

1. 降级形态现在可行：人工准入（蓝图 Gate 0 卡片，〔01-§3.9〕）+ 小鱼儿式简单类型判断（界面/逻辑/效果，〔01-§1.6〕）。
2. 完整形态（体系化 Agent 初筛）条件：①先建分类体系（现状无——提议的分类维度未被采纳为现状，〔01-§1.6〕）；②先有信号存量（依赖 §三.1）；③初筛产出与"部分直接进人工审核"的分流标准需先定义（构想未定义，〔构想-§四〕）。

### 三.3 环节 3：粗库→高质量需求库 —— 能做（粗库=原始 Signal 存档）／不能做（高质量需求库）

1. 粗库子集：只是原始信号存储，无语义前提，可与 §三.1 内部信号源同批推进（infera 需新建聚合，〔02-§五.3.1〕）。
2. 高质量需求库不能做理由（三重前提皆未启动）：①需求资产未规范化——"有必要做，但目前还没有完成"，直接给历史需求怕干扰（〔01-§1.6〕）；②无正式分类体系（〔01-§1.6〕）；③分层标准与数据模型构想自身未展开（〔构想-§六〕；〔01-§5.2〕）。

### 三.4 环节 4：自动聚类与相似性分析 —— 条件能做（确定性去重）／不能做（语义聚类）

1. 确定性去重条件：①先有粗库存量（§三.3）；②规则蓝本直接可参考外部调研的多层确定性去重（〔01-§4.9〕）；③小鱼儿去重机制属"待确认"（〔01-§1.6〕），只作观察项、不作依赖。
2. 语义聚类不能做理由：依赖向量/检索底座（infera 为零，〔02-§五.3.5〕）+ 高质量需求库（§三.3 不能做），数据与底座双缺。

### 三.5 环节 5：优先级评估 —— 不能做（AI 自动评估）／条件能做（AI 建议 + 人工签发降级形态）

1. AI 自动评估不能做理由：①与内部共识正面冲突——蓝图分工明确 Multica 不承担"未经授权决定业务优先级"（〔01-§3.5〕），Gate 0 由准入人人工判断（〔01-§3.9〕）；②优先级评估模板构想自身尚未定义（〔构想-§六〕；〔01-§5.2〕）；③签发主体未拍板（〔02-§六.3〕）；④平台无产品上下文对象（〔02-§五.3.1〕）。
2. 降级形态条件：①拍板签发主体（§六.D6）；②产品优先级上下文暂以人工输入（prompt/表单）注入——现无载体，不新建聚合。

### 三.6 环节 6：人审/置信度自动分流 —— 条件能做（人审关口）／不能做（置信度自动分流）

1. 人审关口：infera 4 道人工门 + AI 建议预填已是可执行路径（〔02-§三〕），平台侧能做；生态侧蓝图三 Gate 设计中且已排期两项落地动作（〔01-§3.12〕），按其节奏推进。
2. 置信度自动分流不能做理由：①阈值判定标准构想自身未明确（〔构想-§六〕）；②无置信特征、风险分级、版本化放行策略（〔02-§五.2.4〕）；③仓库无任何 policy 载体（〔02-§六〕结语）；④与三 Gate 全人工设计相悖，蓝图唯一自动口径（bot 自派发）仍在待讨论（〔01-§3.11〕）。

### 三.7 环节 7：待实现需求粗估 —— 条件能做

条件（按序）：①Agent 契约扩展 usage 回传（现契约无 usage 字段，〔02-§四.1〕；属 §五.子集甲工程）；②以 StageRun 既有时间记录 + 新增 usage 做统计口径粗估（StageRun 已记时间，〔02-§三〕）；③估算方法先定义（构想未展开，〔构想-§六〕）；④Token 成本统计不准的现实痛点须先以计量解决（〔01-§2.12〕）。决策联动：预算上限（〔02-§六.7〕，§六.D8）。

### 三.8 环节 8：Spec 自动反向生成 —— 能做（单需求形态）／条件能做（"全局反向生成"批量形态）

1. 单需求形态能做：infera spec 阶段 + spec_approval 人工门是可执行主路径（〔02-§五.1.1〕），与构想"人类确认审核后进入待提交需求"（〔构想-§四〕）语义一致。增量缺口（schema 校验/证据引用/版本语义）为工程内可补项（〔02-§三〕）。
2. 批量/全局形态条件：需求库先行（环节 3，§三.3 不能做）——故该形态被前置阻塞，列入 §五.子集丙。

### 三.9 环节 9：排期与执行 —— 条件能做（执行）／不能做（排期）

1. 执行条件：①三产品接入信息到位（唯一外部前提，〔02-§四.3〕B1）；②runner 集成缺口 P2-P5 修复（〔02-§四.3〕）；③TEST_CMD 真实化（〔02-§四.1〕）；④真实测试资产到位（建设中，第一版验收目标已明确，〔01-§1.9〕）。内部生态侧小鱼儿执行已在 Bugfix 范围落地（〔01-§1.2〕）。
2. 排期不能做理由：依赖优先级（§三.5）、粗估（§三.7）、容量约束三项产物，而 infera 无跨需求依赖图/资源预算/优先队列（〔02-§五.2.5〕）；构想文本亦未定义排期主体与机制（〔构想-§四〕）。

### 三.10 环节 10：CodeReview 与测试验证 —— 能做（CodeReview 生态集成）／条件能做（infera 平台侧绑定与测试验证）

1. CodeReview 集成能做：infReview 已落地（AI 审查 + 分级阻塞 + 多轮带历史，〔01-§2.1〕〔01-§2.2〕〔01-§2.3〕）；与小鱼儿链路打通处于内测（〔01-§2.7〕）；集成无需新 API——报告回读走代码托管平台原生接口（〔01-§2.7〕）。
2. infera 平台侧条件：双道审查已有但只呈现不拦截（〔02-§五.2.3〕）；将 infReview 绑定为审查 agent 需接入信息（〔02-§四.3〕B1）+ http 鉴权通道（P2，〔02-§四.3〕）。
3. 测试验证条件：①TEST_CMD 配置真实命令（默认 `true` 假绿，〔02-§四.1〕）；②测试资产建设到位（历史冒烟/回归用例转自动化进行中，〔01-§1.9〕）。

### 三.11 环节 11：版本聚集、发布物料与人工验收 —— 条件能做（验收与版本总结）／不能做（发布物料自动化与部署上线）

1. 验收与版本总结条件能做：蓝图 Gate 2 证据包设计完整（证据绑定固定代码版本、代码变更则旧证据与旧批准失效，〔01-§3.9〕〔01-§3.10〕）——蓝本已有，infera 侧为工程实现；"高优已解决/未解决"版本总结可由 infera 既有 delivery/task 状态与 findings 数据派生（〔02-§二.1〕〔02-§二.4〕）；前提是完成定义拍板（〔02-§六.5〕，§六.D4）。
2. 发布物料（产品文档/Changelog/发布日志）与部署上线不能做理由：无对应物（〔01-§5.2〕）+ infera 执行后控制面整段为零、PR 创建后状态不跟踪（〔02-§五.3.2〕〔02-§四.1〕）+ Git/CI/部署选型未拍板（〔02-§六.4〕）+ 与"不自动合并/发布"共识的关系须先按 §四.1 处理。

### 三.12 环节 12：复盘与知识沉淀 —— 能做（人工复盘 + 规则沉淀降级形态）／不能做（系统化知识库）

1. 降级形态能做：小鱼儿既有做法即定期复盘处理过的问题、沉淀到规则/Style/Prompt（〔01-§1.7〕）；infReview 依赖持续使用收集反馈调整规则（〔01-§2.10〕）。
2. 系统化知识库不能做理由：知识库对象为零（〔02-§五.3.1〕）+ 脱敏边界未拍板（〔02-§六.8〕）+ 向量/检索底座为零（〔02-§五.3.5〕），且"服务后续聚类分析"依赖环节 4 语义聚类（§三.4 不能做）。

### 三.13 附加项 1：环节自动串联与人工介入 —— 条件能做

1. 串联机制本身能做：infera 11 阶段自动推进 + 4 道人工门 + MCP 驾驶 + 本机通道是可执行主路径（〔02-§五.1〕）；"验收失败回流同一 Issue"蓝图已设计（〔01-§3.9〕）。
2. 条件：①TEST_CMD 真实化——否则"测试结果决定回流"语义空转（回环机制已有但默认空转，〔02-§四.1〕）；②真实 agent 接入（〔02-§四.3〕B1）；③长链路受非 durable workflow 限制（〔02-§四.1〕）——单交付日内闭环可绕开，"每日循环"形态不可绕开。

### 三.14 附加项 2：无人值守自动循环（每天发布 + 联网自采）—— 不能做

理由（聚合）：①与内部安全共识正面冲突且质量前提不满足（§四.1 完整论证）；②执行后发布反馈控制面整段为零（〔02-§五.3.2〕）；③自治治理整段为零——白名单/预算/并发额度/kill switch/运营治理均无（〔02-§五.3.3〕）；④联网自采无对应物（〔01-§5.3〕）。四项中任一项单独都足以阻断，当前四项同时成立。

## 四、必须正面论证的关键反例

### 四.1 反例一："每天都有版本发布" vs 内部全线不自动合并 + 批入率仅 50%

**事实链**：①infReview：修复完成后的代码不会自动合并，仍需人工最后检查（〔01-§2.7〕）；②小鱼儿：同一链路人工检查；当前修复批入率约 50%、目标 80%，且"进入减少人工参与模式"的前提就是从约 50% 提升到 80%（〔01-§1.5〕〔01-§1.8〕）；③飞书蓝图：非目标明确"不默认允许 AI 自动合并、发布或部署"，验收通过后也"只允许合并被批准的候选版本"（〔01-§3.4〕〔01-§3.10〕）；④外部最激进的项目同样分级：Issue 自动修复默认人工合并，仅低风险 + 证据完整 + 仓库显式授权才考虑自动合并，ClawSweeper 的 Issue-to-PR 永不自动合并、automerge 须显式授权且全部检查通过（〔01-§4.7〕〔01-§4.9〕）；⑤infera：PR 创建失败不阻断、不跟踪 CI/review/合并状态，部署面为零（〔02-§四.1〕〔02-§五.3.2〕）。

**论证**：三个内部产品没有一方做自动合并——这不是能力缺口，而是共同的安全设计选择（蓝图将其写进非目标；外部最成熟实践也只做到"受控合并"）。"每日发布"要求发布管道无人值守可用，其质量前提是自动化产物可信；而当前批入率 50% 意味着约一半产物需要人工返工，此时放开自动合并等于把 50% 的错误率直接推向生产。同时发布所依赖的执行后控制面（Release 聚合、CI 跟踪、部署、回滚）在 infera 为整段零。**结论**："每天都有版本发布"不可作为目标承诺（列入 §六.D3 否决项）；可执行的替代口径是**每日候选版本 + 人工放行**——每日聚集候选交付与证据包，合并与发布节奏由人工 Gate 决定。该口径与蓝图 Gate 2、外部"受控合并"分级完全兼容。

### 四.2 反例二：需求开发自动化 vs 需求资产未规范化 + 负责人明示先跑通 Bugfix

**事实链**：①小鱼儿当前只做 Bugfix 不做需求开发，理由是需求场景要调研→产品方案→UI 方案→技术方案，参与人员与前置步骤多；Bugfix 闭环跑通后再探索需求开发（〔01-§1.1〕）；②需求资产"有必要做，但目前还没有完成"规范化整理，直接给历史需求怕干扰（〔01-§1.6〕）；③无正式分类体系（〔01-§1.6〕）；④其团队自身研发流程中需求评审/设计/设计评审仍为传统方式（〔01-§1.10〕）；⑤infera 已建成的恰是需求开发流水线（spec→design→tasks→…，〔02-§五.1.1〕），但执行前需求控制面为零（〔02-§五.3.1〕）。

**论证**：构想主链路以"需求"为对象（需求库→优先级→Spec），而内部最成熟的实践方明示从 Bugfix 切入、需求开发后置探索——差别在输入明确性。这造成一个结构性倒挂：**infera 的成熟面（需求开发流水线）与内部生态的成熟面（Bugfix 执行）没有对齐**，构想要自动化的恰是双方都最不成熟的那一段。**结论**：需求开发自动化不能作为首期推进对象；首个交付对象域应为 Bugfix 类（输入明确、内部共识、外部调研 strict_bug 通道最完善三者交集，〔01-§1.1〕〔01-§4.9〕），infera 需将"问题描述→复现→修复→验证"模板化为第一类交付。此判定固化为 §六.D1。

### 四.3 反例三：Spec 自动生成 / 置信度分流 / 优先级模板 / Token 粗估 vs 构想自身未定义

**事实链**：①置信度阈值判定标准、优先级评估模板、时间/token 粗估方法、粗库分层标准四项，构想自身在"待确认/需澄清"清单中列为未明确/未展开（〔构想-§六〕）；②Spec 生成诉求表述较明确（〔构想-§四〕），但"全局自动反向生成"的机制、质量标准与验收口径未展开；③平台侧对应现状：Spec 单需求生成已有可执行主路径（〔02-§五.1.1〕），置信特征/放行策略为零（〔02-§五.2.4〕），usage 计量为零（〔02-§四.1〕），产品上下文对象为零（〔02-§五.3.1〕）。

**论证**：这四项的差距不能只记为"平台能力缺失"——其中三项连**目标形态**都未定义，无法写出验收标准；把它们直接排进建设计划等于为未定义目标写代码。且定义本身依赖数据而非仅设计：置信度阈值需要先有置信特征与历史准确率数据（〔02-§五.2.4〕为零）、粗估需要先有 usage 计量（〔02-§四.1〕为零）——数据积累又是前置工程。**结论**：四项一律"先定义、后建设、再放量"：Spec 单需求形态例外（已有实现，直接可用）；其余三项的目标定义是推进前置物，且定义工作依赖 §五.子集甲中的计量/数据工程先行。

### 四.4 反例四：模型稳定性 / Token 成本 / 私有化弱模型约束

**事实链**：①内部模型服务偶尔不稳定、调用会中断；长任务 Token 消耗高；成本统计不准（〔01-§2.12〕）；②上下文压缩超过能力边界后效果明显下降；弱模型/小窗口几轮分析即丢信息或得出浅层结论（〔01-§2.12〕）；③私有化客户旧硬件 + 弱模型：内部十几分钟的任务客户环境需数小时；不同模型需分别调优 Prompt/工具说明/调用策略；私有模型往往只能到客户现场测试（〔01-§2.12〕）；④该挑战被明确表述为跨产品问题，需由平台层沉淀模型适配/上下文管理/私有化部署能力（〔01-§2.12〕〔01-§2.14〕⑨）；⑤infera：Agent 契约无 usage/model 字段（〔02-§四.1〕）、http 超时固定 10min 不可配（〔02-§四.3〕P5）、长任务为进程内 goroutine 非 durable workflow（〔02-§四.1〕）。

**论证**：构想闭环是长链路多 Agent 任务，正好同时踩中三个约束：链路越长，单点中断的复合失败率越高（infera 现靠 30min 总超时 + 重启点火，无租约/幂等 effect，跨天任务不可靠，〔02-§四.1〕〔02-§二.8〕）；无计量则粗估/预算/成本观测全部空转（〔02-§五.3.5〕）；弱模型下同一套 Prompt/工具说明不可复用，质量与吞吐均不可控。**结论**：任何多环节串联推进必须先过三关——分段驾驶或 durable 化（消除单点长链）、usage 计量（成本可见）、按目标模型分层验证；模型适配/上下文管理/私有化部署按内部共识归平台层承接（〔01-§2.12〕），infera 不自建（约束 §六.D2）。

### 四.5 反例五：多团队重复建设与"平台团队承接通用能力"共识对自建范围的影响

**事实链**：①多个团队在做类似事情、需考虑协同；双方共识"平台团队承接通用能力更合适"，业务团队探索最终可能纳入平台整体建设；当前安排人做首先是为解决现场人力接不过来的实际问题（〔01-§1.11〕）；②infReview 与小鱼儿方案未系统对齐，infReview 更偏通用能力（〔01-§2.8〕）；③双方后续动作明确：与已落地 Bugfix 机器人的团队对齐接口和责任边界、避免重复建设（〔01-§2.14〕②）。

**论证**：该共识直接划定 infera 的自建边界——凡内部已有落地物的环节（CodeReview=infReview、Bugfix 执行=小鱼儿），infera 不应重建执行能力，而应做集成与驾驶；恰好 infera 的 Agent 注册表 + 四类 runner + MCP 五工具就是为集成形态而建（〔02-§二.3〕〔02-§二.5〕）。通用底座（模型适配/上下文压缩/私有化）按共识归平台层（§四.4）。**结论**：infera 的差异化定位只能落在**编排 + 门禁治理 + 证据**这一层（与〔02-§三〕小结"差距不在再增加几个 Agent"一致）；05 的设计范围不得超出此层自建执行/审查/模型适配能力（约束 §六.D2）。

## 五、整体分阶段结论（子集划分，非路线图）

> 本文只划定"哪些子集现在就可推进、哪些依赖什么前提"；阶段顺序、里程碑与排期是 04 的职责，且必须从本节子集出发。

### 五.1 总体结论

**构想全闭环（12 环节全自动串联 + 每日发布 + 无人值守）不可作为整体目标推进；可行域是"Bugfix 型单交付闭环（人工门禁版）"这一严格真子集。** 依据：执行内核两侧已建成/落地（〔02-§五.1〕；〔01-§1.2〕〔01-§2.1〕），而执行前需求控制面与执行后发布反馈控制面整段缺失、横向治理为零（〔02-§五.3〕），且"全自动语义"与内部不自动合并共识、先 Bugfix 后需求的共识正面冲突（§四.1/§四.2）。构想不是被整体否定——环节 8/10/13 的核心机制已有真子集；被否定的是"全自动 + 每日发布 + 无人值守"的包装语义。

### 五.2 子集甲：现在就可推进（前提全部在自身工程范围内，无外部拍板依赖）

1. **infera 执行内核补强**：runner 缺口 P2-P5 修复（〔02-§四.3〕）、TEST_CMD 语义真实化（〔02-§四.1〕）、usage 计量入 Agent 契约（〔02-§四.1〕〔02-§五.2.1〕）、PR/CI 状态跟踪（〔02-§四.1〕）、验收证据包实现（蓝本〔01-§3.9〕〔01-§3.10〕）。
2. **Bugfix 交付模板化**：以"问题描述→复现→修复→验证"为 infera 第一类交付模板；复现契约与"人只在语义/风险边界出现"参考〔01-§4.7〕〔01-§4.9〕。
3. **与内部产品集成预研**：infReview 报告经代码托管平台原生接口回读（〔01-§2.7〕，无需新 API）；http 形态契约已线上真实验证（〔02-§五.2.8〕）。
4. **降级形态机制即时可用**：人工准入（蓝图 Gate 0 设计且已排期，〔01-§3.12〕）、AI 建议预填门（〔02-§三〕）、人工复盘沉淀（〔01-§1.7〕）。

### 五.3 子集乙：依赖单一外部前提，前提落地即可推进

1. **Bugfix 全链真跑** ← 三产品接入信息（唯一外部前提，〔02-§四.3〕B1）。
2. **内部信号采集 + 粗库** ← 首个信号源拍板（〔02-§六.2〕，§六.D5）+ 来源系统配合（蓝图三项排期落地节奏，〔01-§3.12〕）。
3. **验收门（Gate 2 形态）落地** ← 完成定义拍板（〔02-§六.5〕，§六.D4）。
